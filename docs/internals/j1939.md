## Implemented features and assumptions

The stack uses no external J1939 library. The API may still change. It currently provides:

- Identifiers and PGNs
- Single-frame transmission and reception
- Responses to Request (PGN 59904)
- Acknowledgement (PGN 59392)
- Timers
- NAME and Address Claim (including arbitrary address selection, the address table, Commanded Address handling and address violations)
- Transport protocol (BAM and RTS/CTS, 9–1785 bytes)
- A toolbox for building protocol parts (`Subscription`, `Timer`, `Node::attach`)
- A read-only observation API (`Observer`)
- The protocol parts DM13 (broadcast suppression), diagnostics (DM1, DM2, DM3, DM11, DM22) and identification
- For ECU applications: periodic transmission (`PeriodicSender`), sending Requests and waiting for the response (`Requester`), reception monitoring (`Monitor`), sending Commanded Address (`AddressCommander`), and commands and responses of custom protocols (`Exchange`)

There is no ETP. A node without a NAME works at the fixed address given when it is created (for tests).

The stack makes 2 assumptions:

- It depends only on `vehicle_sil::can` (no SIL Kit). It has no threads and does not read a clock. `Network` is a `Steppable`, and the host runs it in each step.
- Times are `SimTime`. The time of a received message is the time of its frame (in virtual time, the sender's step time). The time of a send is the time of the step that sent it.

## Division of responsibility (engine, toolbox, protocol parts)

Before you add a feature, decide which of these 3 places it belongs in. Do not put a feature in the engine only because the standard contains it.

| Place | What goes there |
|---|---|
| Engine (`Network` and `Node`) | What makes J1939 communication work; the state of the node as a whole and the correctness of its communication; communication resources that several parts share; anything that would cause conflicts or inconsistencies if each part kept its own |
| Toolbox | Small common functions for writing parts safely and concisely (RAII for event registration, virtual-time timers, node ownership of parts) |
| Protocol parts | Features that have their own procedures or state machines, do not change the state of the node as a whole or shared resources directly, and can be added and removed independently of other parts (periodic transmission, sending a Request and waiting for the response, diagnostics, functional safety communication, Memory Access, custom protocols and so on) |

All of the following existing features are in the engine:

- Identifiers and PGNs
- Transmission, reception and delivery
- NAME, addresses and Address Claim
- Receiving Commanded Address
- Request delivery and NACK
- Sending Acknowledgement
- Transport protocol sessions, timeouts, aborts and transmit queues
- Statistics and the counting of port events

Add to the toolbox only what several parts need in common, where the existing API is not safe or concise enough, and what contains no processing of a particular protocol.

Protocol parts follow these rules:

- A part is built only from the public API of the node and the toolbox.
- A part has no threads or event loops and runs only within steps.
- Do not add a public API whose only purpose is to manipulate engine internals.
- Do not build the same feature in both the engine and a part.
- A part does not use `on_any_request` (it would take away the default NACK for PGNs that have no responder).
- There is one responder per PGN (if a PGN has several, only the one registered first is called).

Split a feature that crosses the boundary: the part that guarantees consistent communication goes in the engine, and the protocol procedure goes in a part.

| Feature | Engine | Part |
|---|---|---|
| Request | Delivery | Issuing, waiting for the response, timeout |
| Commanded Address | Changing the address on reception, and keeping transport protocol sessions consistent | Sending |

What goes in neither the engine nor a part, and what the engine does not do:

- PG and SPN definitions (signal layout, scaling, special values) go in neither the engine nor a part. Typed messages (`vehicle_sil::j1939_codec`) handle only the conversion to and from bytes. The engine and the parts handle bytes.
- The engine does not stop broadcasts for DM13, because it cannot tell which sends are "broadcasts". A part (`BroadcastSuppression`) holds the suppression state, one per node, and the parts that broadcast periodically on their own (such as DM1) read it. Messages that the application sends directly with `Node::send()` are not suppressed.

## Value types

- `Pgn` is 18 bits (extended data page, data page, PF, PS). A PGN whose PF is below 240 (PDU1) has a destination, and the PS of the PGN is 0. A PDU1 value with a non-zero PS and a value over 18 bits are invalid. The reserved bit (extended data page) is treated as part of the PGN; frames with it set are not dropped.
- `Identifier` holds the fields of the 29-bit identifier. In PDU1, PS is the destination; in PDU2, the destination is always global (255). `encode()` throws `std::invalid_argument` for an invalid PGN, a priority of 8 or more, or a PDU2 identifier with a destination other than global.
- Address 254 means no address has been claimed, and 255 is the global destination. Node addresses are 0–253.

## Network and Node

`Network` is the set of this process's nodes (`Node`) on one CAN channel. Create nodes with `add_node()`. The `Network` owns them (they stay valid for the lifetime of the `Network`).

### Adding nodes

| Where `add_node()` is called | Result |
|---|---|
| Outside a step | Allowed. |
| In the application processing of the host | Allowed. The node joins from the next `begin()` of that `Network`. |
| In a handler of another `Network` on the same host | Allowed. The node joins from the next `begin()` of that `Network`. |
| From another host | From the point of view of that `Network`, this is outside a step, so the node joins from the next step (decided by the order in which the hosts run). |
| In a handler, responder or timer of its own `Network` | A usage error. |

A node added during a step receives nothing and does not start Address Claim until the next `begin()` of its `Network`. This holds regardless of the order of registration with the host.

`Node::address()` is the current address (Address Claim changes it). `Node::requested_address()` is the address given when the node was added (`NodeOptions::address`).

### Receive dispatch

- These frames are ignored and counted: 11-bit frames, frames from source 255, and frames from source 254 (a node without an address) other than Address Claimed and Request.
- Each node gets only frames whose destination is its own address or global (PDU1 frames to other addresses are not passed to it).

### Local loopback

- A frame sent by a node of the same `Network` reaches the other nodes in the next step, but only if the port accepted it (`Accepted`).
- It does not reach the node that sent it.
- Nodes with the same address receive each other's frames too.

### Handlers (`on_message`, `on_any_message`)

- The data of the `Message` passed to a handler is valid only during the call.
- A handler registration takes effect when delivery of the current frame ends (the handler is not called for that frame).
- Unregistration takes effect immediately, even during delivery: the handler is not called for the rest of that frame (the handler's function object itself is destroyed at the end of the delivery).
- Destroying a function object (the destructors of its captures) may unregister or register other handlers.

## Processing in one step

### Order of received frame processing

`process()` processes the frames received from the port and the local loopback frames of the previous step in time order. Frames with the same time are taken in the following order (an approximation of CAN arbitration):

1. Build one queue per source address. Within a queue, frames are in arrival order; for the same time and the same address, external frames come before loopback frames.
2. Take one frame at a time from the queue whose head has the smallest CAN ID.

So the order of each sender is preserved, and the result depends neither on the arrival order at the port nor on the step size. Frames sent at the same time by different senders that use the same address (during an address conflict), however, go into one queue, in arrival order.

### Timer firing

There are 2 kinds of timer.

| Kind | Fires |
|---|---|
| Timeout | Just before a frame whose time is after the deadline is processed, or at the end of the step if deadline < now (a frame with the same time as the deadline comes first) |
| Scheduled | In the first step with deadline ≤ now |

- Both kinds fire before a frame if their deadline is before the frame's time.
- Timers that can fire at the same time fire in order of (deadline, start order).
- When the deadline is exactly now, only scheduled timers fire. A timeout with the same deadline fires in the next step.
- Timeout decisions do not depend on the step size.
- `next_deadline()` returns the earliest deadline (a timeout fires in the first step after its deadline).

A timer started inside a timer is handled according to its deadline.

| Deadline of the started timer | Fires |
|---|---|
| After the deadline of the timer that started it | In the same firing round (in order of deadline, then start). |
| Equal to or before that deadline (such as a restart with the same deadline) | Not until the next firing round (before the next frame, or at the end of the step; at the end of the step, that means the next step). |

So a period that restarts from its deadline fires once for every deadline within the step, even if the period is shorter than the step size, and lateness does not accumulate. After a long stall in real time, the missed deadlines are caught up in one step.

### Transmit order (`flush()`)

Frames sent from handlers, Request responders and timers are passed to the port in the `flush()` of that step. `flush()` passes them in this order:

1. Control frames (Address Claimed, Acknowledgement, transport protocol TP.CM)
2. The data queue
3. Transport protocol data packets (TP.DT)

The data queue and TP.DT together are limited to `max_frames_per_step` per step. The rest is passed in the next step.

| Port result | Handling |
|---|---|
| `QueueFull` | The frame and those after it are kept and passed again in the next step (preserving order). |
| `Failed` | The frame is dropped and counted. The following frames continue. |

## Transmission

- `Node::send()` sends up to 8 bytes as a single frame, and 9–1785 bytes with the transport protocol (below).
- You can send only within a step (handlers, responders, timers, the application processing of the host). Outside a step, sending is a `std::logic_error`.
- `Node::request(pgn, destination)` sends a Request (3 bytes, priority 6). The requester's procedure, such as waiting for the response and retrying on timeout, is not in the engine but in a part (`Requester`).

`Node::send()` returns its result. The return values are `Ok`, `QueueFull` and these 4:

| Return value | When |
|---|---|
| `TooLong` | 1786 bytes or more |
| `InvalidArgument` | An invalid PGN, a priority of 8 or more, a single-frame PDU2 to one destination, destination 254 |
| `NoAddress` | The node has lost its address |
| `Busy` | See "Transfer types and concurrent transfers" in "Transport protocol (J1939-21 TP)" below |

`Node::can_send_now()` is true when what the node sends goes out from its own address right away.

| Node state | `can_send_now()` |
|---|---|
| No NAME, `Claimed`, `Claiming` without the wait | true |
| During the wait after a claim, before the first claim, without an address | false |

The value changes only with a change of address or state (`on_address_change`), so a part that sends on its own starts and stops on that notification.

## Request and Acknowledgement

### Handling received Requests

- A node handles Requests to its own address or to global.
- A Request shorter than 3 bytes is ignored and counted. For a Request longer than 3 bytes, the first 3 bytes are the requested PGN.
- A Request from source 254 gets no response, except a Request for Address Claimed (PGN 60928).
- A Request for Address Claimed is answered by the Address Claim procedure (below), with neither NACK nor ACK. A node without a NAME does not answer it.
- If there is no responder, a destination-specific Request gets a NACK, and a global Request gets nothing. Whether the node has seen the requester's address claim (Address Claim) is not a condition.

### Responders (`on_request`, `on_any_request`)

If there is a responder (`on_request(pgn, ...)`, `on_any_request(...)`), the node calls it. Per-PGN responders come first; if a PGN has several, the one registered first is called. The responder calls one of the following on `RequestContext`. If it calls neither, nothing is sent.

| Call | What it does |
|---|---|
| `respond(data)` | Sends the requested PG. A PDU1 PG requested by a destination-specific Request goes to the requester; anything else goes to global. |
| `acknowledge(code)` | Sends an Acknowledgement, only for a destination-specific Request. Nothing is sent for a global Request. |

- A `respond()` of 9 bytes or more is sent with the transport protocol (even for a PDU2 PGN, a destination-specific Request gets RTS/CTS to the requester; see "Transport protocol" below).
- `acknowledge()` also returns false when the control queue overflowed and the Acknowledgement was dropped.

### Answering later (`RequestContext::defer()`)

To answer after processing that takes several steps, keep the request as a value (`PendingRequest`) with `RequestContext::defer()`, and answer it later with `Node::respond(pending, data)` or `Node::acknowledge(pending, code)`.

- The destination and the transmission method are the same as when you answer through `RequestContext`.
- You can call them only within a step.
- If the node loses or changes its address in the meantime, the response is not sent and `NoAddress` is returned (`acknowledge` returns false), because the request was addressed to the old address.
- Passing the request of another node is a `std::invalid_argument`.

### Acknowledgement frames

- The frame sent: priority 6, global destination, data [control byte, 0xFF, 0xFF, 0xFF, requester's address, requested PGN (3 bytes, as received)].
- `parse_acknowledgement(message)` returns the fields of a received Acknowledgement (PGN 59392, 8 bytes or more) as an `Acknowledgement` (control byte, group function, address acknowledged, PGN), and empty for anything else. Only the engine knows the format; parts do not parse it themselves.

### Not verified against the standard (Request and Acknowledgement)

- Handling of an invalid requested PGN (a PDU1 value with a non-zero PS, over 18 bits): no responder matches, so a destination-specific Request gets a NACK
- Handling of frames with the extended data page bit set
- The values of bytes 2–4 of the Acknowledgement

## NAME and Address Claim

### NAME format (`Name`)

`Name` is the 64-bit NAME. Its fields, starting from the least significant bit:

| Field | Bits |
|---|---|
| Identity Number | 21 |
| Manufacturer Code | 11 |
| ECU Instance | 3 |
| Function Instance | 5 |
| Function | 8 |
| Reserved | 1 |
| Vehicle System | 7 |
| Vehicle System Instance | 4 |
| Industry Group | 3 |
| Arbitrary Address Capable | 1 |

- A smaller value has higher priority. A NAME with the most significant bit, Arbitrary Address Capable, set always has lower priority than a NAME without it.
- On the bus, the NAME is 8 bytes, least significant byte first.
- The Manufacturer Code `0x7F0` in the examples and tests is a placeholder. On a real ECU, set the value assigned to its manufacturer.

### Address claims and state

- A node with `NodeOptions::name` claims `address`.
- With an arbitrary address capable NAME, `address` can be 254. The node then claims the first free address in the arbitrary address range (below).
- `Node::address_state()` gives the state (`NotStarted`, `Claiming`, `Claimed`, `CannotClaim`; `Fixed` for a node without a NAME).
- Start: in the first step after the node joins, after the frames of that step are processed, the node sends Address Claimed (priority 6, global destination, data = NAME). It does not send a Request for Address Claimed first.

### Waiting after a claim

For 250 ms from the time of the step that sent Address Claimed (`Claiming`), the node keeps everything it sends (`send()`, `request()`, responses to Requests, ACK/NACK) in its hold area (`NetworkOptions::hold_capacity`, default 16 messages). In the step where the wait ends, it sends them with the address it has at that time.

| Condition | What happens |
|---|---|
| `send()` when the hold area is full | Returns `QueueFull`. |
| Frames of the Address Claim procedure (Address Claimed, Cannot Claim, Request for Address Claimed and its responses) | Not held. |
| A node that is not arbitrary address capable, with an address of 0–127 or 248–253 | Exempt from the wait (it sends right away, even while `Claiming`). |
| The data queue is full when the wait ends | Messages are dropped and counted (`held_dropped`), even if `send()` returned `Ok` for them. |

The end of the wait is a scheduled timer. If a competing Address Claimed with a time at or after the deadline arrives and is processed in the same step as the deadline, the step size decides whether the node sends its held messages and then loses, or loses first and drops them (see "Address Claim limitations" below).

### Contention

When a node receives another node's Address Claimed (8 bytes or more) for its own address, it compares the NAMEs.

| Own NAME | Node | What happens |
|---|---|---|
| Smaller | Any | Sends Address Claimed again. |
| Larger or equal | Arbitrary address capable, with a free address | Loses the address, picks a free address and claims again. |
| Larger or equal | Any other node, and an arbitrary address capable node with no free address | Loses the address and becomes `CannotClaim` (address 254). |

When the node wins, it sends Address Claimed only once for causes with the same time, because claims made at the same time reach each other. The count depends only on the frame times, not on the step size. The cause is one of:

- A competing Address Claimed
- An address violation
- The frame or Commanded Address that caused a move
- The first claim (its time is the time of that step)

When the node loses its address, it drops and counts:

- Held messages
- Frames put in the transmit queue before the address changed (dropped even after the node returns to its original address; this includes Cannot Claim and excludes only Requests from source 254)

An arbitrary address capable node picks the smallest address in the arbitrary address range (`NetworkOptions::arbitrary_address_first`–`arbitrary_address_last`, default 128–247) that is neither in the address table nor used by another node of the same `Network`. As soon as it picks one, it sends Address Claimed and restarts the wait (`Claiming`). It does not pick the address it lost, because the winning NAME is in the table.

A node that became `CannotClaim` sends Cannot Claim (Address Claimed from source 254) after `cannot_claim_delay(name)`.

- The delay is 0–153 ms in steps of 0.6 ms, a pseudo-random value derived from the NAME (the same NAME always gives the same value).
- The delay counts from the time of the frame through which the node learned that it lost.
- If there was no free address at the first claim, it counts from the time of that step.

### Request for Address Claimed

A node answers a Request for Address Claimed to global or to its own address according to its state.

| Node state | Response |
|---|---|
| `Claiming`, `Claimed` | Sends Address Claimed (to global), once per request. |
| `CannotClaim` | Sends Cannot Claim after the delay (merged into one with a Cannot Claim not yet sent). |

Requests for Address Claimed that a node sends itself:

- A node also answers a Request for Address Claimed that it sends itself (to global or to itself).
- A node before its first claim sends its Request for Address Claimed from source 254 and does not answer it itself (it claims right afterwards; its other sends are held).
- A node that has lost its address can send only Request for Address Claimed (from source 254).

A node that has lost its address receives no destination-specific frames (only global ones), and answers no Request other than Request for Address Claimed.

### Address violations

A node in `Claiming` or `Claimed` sends Address Claimed again when it receives a frame from another sender that uses its address as the source.

- Address Claimed and Request for Address Claimed do not count. An Address Claimed shorter than 8 bytes does count.
- The node sends again once per cause time (the same rule as the response to contention).
- The state does not change.
- The frame is delivered as usual.
- The count is `address_violations`.
- Nodes without a NAME do not detect violations.

### Receiving Commanded Address

A node handles a Commanded Address (PGN 65240: an 8-byte NAME and a 1-byte new address) to global or to its own address when the NAME is its own. Commanded Address is 9 bytes, so it arrives through the transport protocol (BAM or RTS/CTS).

| Condition | What happens |
|---|---|
| An arbitrary address capable node | Moves to the new address. |
| The new address equals the current address | Only sends Address Claimed again. |
| A NAME with higher priority holds the new address | Loses the contention and moves to a free address in the arbitrary address range. |
| A node that is not arbitrary address capable; not 9 bytes; a new address of 254 or 255; to a node before its first claim | Ignored and counted (`commanded_addresses_ignored`). |
| Shorter than 8 bytes | Not counted, because the NAME is unknown. |

When a node moves to a new address, it drops its held messages and the frames of the old address, sends Address Claimed and restarts the wait. A `CannotClaim` node moves too. A scheduled Cannot Claim is not sent.

### Address table (`Network::address_table()`)

The address table maps addresses to NAMEs for control functions other than the nodes of the same `Network` (`name_at(address)`, `address_of(name)`; fixed at 254 entries). Received Address Claimed messages (8 bytes or more) update it.

| Received or happened | Table update |
|---|---|
| The same NAME claimed a new address | The mapping of the old address is removed. |
| A local node claimed an address | A lower-priority NAME at that address is removed. |
| Cannot Claim received | The mapping of that NAME is removed. |
| Several NAMEs claimed the same address | The higher-priority (smaller) NAME stays, regardless of the order in which the claims arrived. |
| A claim for an address that a local node (`Claiming` or `Claimed`) holds, with a NAME larger than that node's (lower priority, so it loses) | Not added. |
| Address Claimed of a local node (loopback) | No update. |
| Address Claimed shorter than 8 bytes | Not treated as a claim; counted (`address_claims_malformed`). |

For a local node's claim, the lower-priority NAME is removed when the Address Claimed is put in the transmit queue. It stays removed even if that frame could not be sent. If the other control function claims again, it is added again.

### Looking up the current mapping (`Network::address_of(name)`, `Network::name_at(address)`)

- The lookup covers both the nodes of the same `Network` (`Claiming` or `Claimed`) and the address table.
- It works the same whether the other control function is a node in the same process or another participant.
- A received Address Claimed or Cannot Claim enters the table before the node's handlers are called, so the handlers see the new mapping.
- For a node of the same `Network`, the result changes when that node's state changes.

When another node of the same `Network` claims the address, the mapping may change only after that node processes the claim, that is, after the handler of your node. The change then becomes visible with that node's Cannot Claim, or with its Address Claimed (loopback) for the new address.

### State notifications (`Node::on_address_change`)

`Node::on_address_change(handler)` is called with an `AddressChange` (old and new state and address, cause time) each time the address or state changes. Like a handler, it is called within a step and can send. The rules for registering and unregistering are the same as for handlers.

### Not verified against the standard (Address Claim)

- Treating an Address Claimed from another sender with the same NAME as a loss
- The start of the Cannot Claim delay, and how the pseudo-random value is made
- Holding ACK/NACK during the wait
- The arbitrary address range, and picking the smallest free address
- How often the node responds to an address violation (once per cause time), and counting an Address Claimed shorter than 8 bytes as a violation
- Nodes that are not arbitrary address capable ignoring Commanded Address
- Keeping the smaller NAME in the address table when claims for the same address overlap (the NAME stays until a new claim, even if its control function is gone)

### Address Claim limitations

- The end of the wait is a scheduled timer, so a node can send its held messages and then lose, even to a competing claim that arrived at or after the deadline, if it is processed within the same step as the deadline. The `on_address_change` times are then Claimed followed by CannotClaim with an earlier time.
- The processing order of frames sent at the same time by different senders with the same address (not fixed with SIL Kit) does not change the frames on the bus or the result, but it can change the counts `held_dropped` and `address_violations`.
- The wait counts from the time of the step that put Address Claimed in the transmit queue, not from the time it left the queue.
- If the control queue overflows and Address Claimed is dropped, the state still advances (counted in `control_frames_dropped`).
- Each claiming node needs 2 from `timer_capacity` (if there are not enough, `add_node()` throws `std::invalid_argument`).
- An arbitrary address capable node that became `CannotClaim` does not claim again on its own, even if an address becomes free later (Commanded Address can move it).

### Not yet in Address Claim

- Removing nodes
- Handling after bus-off
- Removing control functions that do not respond from the table

An entry leaves the table only when its NAME claims another address, when it sends Cannot Claim, or when a local node claims its address and wins. Sending Commanded Address is a part (`AddressCommander`).

## Transport protocol (J1939-21 TP)

The transport protocol splits messages of 9–1785 bytes into TP.CM (PGN 60416, `kPgnTransportControl`) and TP.DT (PGN 60160, `kPgnTransportData`) frames to send them, and reassembles the messages it receives.

- The 2 constants are in `types.hpp`. Code that looks at frames uses them (to drop packets with fault injection, to filter the frames to record).
- Both kinds of frame have priority 7.
- TP.CM and TP.DT frames are not passed to handlers. The reassembled message is delivered through the same path as a single frame (`on_message`, `on_any_message`, Request and Commanded Address handling).
- The `Message::time` of a reassembled message is the time the transfer ended (the time of the last packet), not the time the sender started sending. To measure the sender's period from the message times on the receiving side, use single-frame messages.

### Transfer types and concurrent transfers

- A global destination uses BAM; a single address uses RTS/CTS.
- A PDU2 PGN is also sent with RTS/CTS when you give a destination (that is invalid for a single frame).
- `priority` is only checked, not used.
- A node can run one BAM, and one RTS/CTS per destination, at a time.

| Condition | `send()` returns |
|---|---|
| A send of the same type as a running transfer | `Busy` |
| No free transmit session (`bam_transmit_sessions`, `rts_transmit_sessions`, default 4 each) | `QueueFull` |

By default, a `send()` of 9 bytes or more returns `Busy` while a transfer of the same node is running. With `WhenBusy::Queue`, it waits in the same response queue as `respond()` (sharing its capacity) and starts after the previous transfer ends. This spares each part its own retry logic when several parts send long messages from the same node (for example, a DM1 BAM and a BAM with an identification response).

### Results of sent transfers (`Node::on_transfer_end`)

The result is reported to `Node::on_transfer_end(handler)` as a `TransferEnd`. A `TransferEnd` contains the PGN, destination, length, result, Abort reason, cause time, the transfer identifier `id`, and `all_packets_sent` (whether all data packets went out).

Every transfer for which `send()` or `RequestContext::respond()` returned `Ok` is reported exactly once (except transfers still running when the `Network` was stopped).

The result is one of `Completed`, `AbortedByPeer`, `Aborted` and `Cancelled`.

| Result | When |
|---|---|
| `Completed` | For RTS/CTS, EndOfMsgACK was received; for BAM, the last packet went out |
| `AbortedByPeer` | The receiver sent a Connection Abort (the reason is in `reason` of `TransferEnd`) |
| `Aborted` | This node sent an Abort |
| `Cancelled` | The transfer ended without sending a frame |

- `Cancelled` happens on the address changes described below and, rarely, when a transfer held during the wait after a claim could not be put in the control queue when the wait ended.
- A BAM's `Completed` is reported in the step after the last packet went out, with the time of the step in which the last packet went out. It is `Completed` even if the address changed in between.

Transfer identifiers follow these rules:

- When `send()` or `respond()` (of `RequestContext` and of `Node`) accepts a transfer, `Node::last_transfer_id()` right afterwards returns the `TransferId` of that transfer (it is empty after a single-frame send and after a call that was not accepted).
- IDs are unique within a `Network`.
- A transfer that waited in the response queue, or was held during the wait after a claim, ends with the ID it got when it was accepted.
- Even if the same node runs overlapping transfers with the same PGN and destination, their ends are never mixed up.

`all_packets_sent` tells you:

| `all_packets_sent` | Result | What it tells you |
|---|---|---|
| false | Any | The receiver could not reassemble the message (the transfer ended before the last packet, or never started). |
| true | Not completed (no EndOfMsgACK came, or the address changed in between) | Whether the receiver got the message is unknown. |

### Notification of incoming transfers (`Node::on_incoming_transfer`)

Incoming transfers are reported to `Node::on_incoming_transfer(handler)` as an `IncomingTransfer`. An `IncomingTransfer` contains start or end, ID, PGN, source, destination, length, the result and reason of the end, and the cause time.

| Transfer | Nodes notified |
|---|---|
| RTS/CTS | Only the destination node that accepted it |
| BAM | Every node present at the start, except the sender (nodes added later are notified of neither the start nor the end) |

- A transfer whose start was reported always gets exactly one end report (as long as the `Network` does not fail and is not destroyed first).
- An RTS that was not accepted because its CTS could not be put in the control queue gets neither a start nor an end report.
- IDs come from the same sequence as those of sent transfers.
- The handler rules are the same as for `on_transfer_end`, and the handler is called within a step.

The end result is one of `Completed`, `AbortedByPeer`, `Aborted`, `Lost` and `Cancelled`.

| End result | When, and what happens |
|---|---|
| `Completed` | The reassembled message is delivered right after this notification. |
| `Aborted` | This node sent an Abort (timeout and so on) |
| `Lost` | A missing BAM packet, or a timeout |
| `Cancelled` | An address change, a restart of the same transfer by the same source, or a CTS that could not be sent |

### Sending BAM

- From the step that sent the announcement, one packet goes out every `bam_packet_interval` (default 50 ms, 10–200 ms).
- The interval counts from the time of the step that sent the previous frame, so if it is not a multiple of the step size, it is rounded up (it never gets shorter).
- An Abort received for a BAM is ignored.

### Sending RTS/CTS

- Byte 5 of the RTS (the maximum number of packets that one CTS may allow) is `rts_max_packets_per_cts` (default 255 = no limit).
- The packets a CTS asks for all go out in the step that received the CTS.
- If the CTS allows more packets than remain, packets go out up to the last one.
- A CTS for 0 packets is a hold.
- An EndOfMsgACK that comes before all packets went out, and a CTS, EndOfMsgACK or Abort for another PGN, are ignored.

The sender sends an Abort in these cases:

| Condition | Abort reason |
|---|---|
| The next packet number in the CTS is 0, greater than the total, before the start of the last requested window, or after the highest number sent + 1 | 7 |
| The number of packets allowed exceeds byte 5 of the RTS | 250 |
| The next CTS arrives before the packets of the previous window have all gone out | 4 |
| T3 and T4 | 3 |

### Long responses to Requests

A `RequestContext::respond()` response of 9 bytes or more goes to the requester with RTS/CTS for a destination-specific Request, and with BAM for a global Request.

- If a transfer of the same type is running on the same node, or no session is free, the response goes into the network's response queue (`response_queue_capacity`, default 8) and starts at the beginning of `flush()`, in the order queued.
- If the response queue overflows, the result is `QueueFull`.
- Order is kept only within the response queue. A `send()` of the same node starts ahead of the queue if a session is free.

### Receiving BAM

One BAM per source.

| Condition | What happens |
|---|---|
| The announcement is to global, 9–1785 bytes, with a packet count that matches the size and a valid PGN | Received. |
| Any other announcement | Ignored and counted. A running BAM is not affected. |
| A new valid announcement from the same source | Drops the running BAM and replaces it. |
| A packet number other than expected (missing, duplicate, out of order, 0) | The message is dropped (a BAM cannot ask for retransmission; no Abort is sent). |
| The receive sessions are full (`bam_receive_sessions`, default 8) | The new announcement is ignored and counted. |

- The minimum interval between packets is not checked.
- A BAM is received even if the source's Address Claim has not been seen.

### Receiving RTS/CTS

One transfer per pair of source and destination. The destination is a local node that has an address (`Claiming`, `Claimed`, or fixed without a NAME). An RTS to global, and an RTS to an address with no local node, are ignored.

An RTS is rejected with an Abort in these cases:

| Condition | Abort reason |
|---|---|
| Over 1785 bytes | 9 |
| Under 9 bytes, a packet count mismatch, byte 5 is 0, an invalid PGN | 250 |
| The receive sessions are full (`rts_receive_sessions`, default 8) | 1 |
| An RTS for another PGN from the same source (the running transfer continues) | 1 |

An RTS for the same PGN drops the running transfer without sending a frame and starts a new one.

The number of packets a CTS allows is min(byte 5 of the RTS, `cts_window` (default 16), remaining). When a window has been received, the receiver sends the next CTS. When everything has been received, it sends EndOfMsgACK and delivers the message.

Packets are handled by number and data:

| Packet | Handling |
|---|---|
| The expected number | Received. |
| A duplicate of the previous packet, or a number before the start of the current window (a late packet of the previous window) | Ignored. |
| Anything else (a later number, 0, an old number within the window), and a packet with too little data (short DLC) | Treated as missing. |

- When a packet is missing, the receiver asks for retransmission from the first missing packet with a CTS when the packet with the last number of the window arrives. Packets after the missing one, up to the retransmission CTS, are dropped.
- Up to 2 retransmission requests are allowed until the window is complete. If a third is needed, the receiver aborts (reason 5).
- If the last packet of a window is missing, the transfer ends by T1.
- The receiver does not send a hold (a CTS for 0 packets).
- A CTS or EndOfMsgACK from the source is ignored.
- An Abort from the source ends the transfer without sending a frame.

### Reassembled messages

- The priority of the packets does not matter. The priority of the reassembled message is that of the RTS or the BAM announcement. Its time is the time of the last packet.
- A reassembled Address Claimed (PGN 60928) or Request (PGN 59904) is a single-frame PG, so it is counted and dropped, not delivered. Commanded Address and other PGNs are delivered through the same path as single frames.

### Transport protocol timers

Every timeout causes an Abort (reason 3). Only BAM reception drops the message without sending a frame.

| Timer | Value | Starts from |
|---|---|---|
| T1 for BAM reception | 750 ms | The time of the announcement or packet frame |
| T1 on the receiver (between packets) | 750 ms | The frame time of the last packet that reached the session (including ignored ones) |
| T2 on the receiver (first packet after a CTS) | 1250 ms | The time of the step that sent the CTS |
| T3 on the sender (after the RTS or the last packet of a window) | 1250 ms | The time of the step that sent it |
| T4 on the sender (after a hold) | 1050 ms | The frame time of the hold CTS (restarts while the hold continues) |

- A timeout is judged at times after the deadline (a frame exactly at the deadline is accepted). The judgement does not depend on the step size.
- Timers that start at a send count from the time of the step that passed the frame to the port (also when the port returned `Failed`).
- If the port keeps returning `QueueFull` and the frame keeps being passed again, the timer starts that much later.

### Address changes and transfers

A transfer sent during the wait after a claim reserves a session and waits. When the wait ends, it starts together with the other held messages, in the order they were held. A CTS for an RTS received during the wait also goes out after the wait ends.

When a node loses or changes its address, its sending and receiving transfers and its responses in the response queue end without a frame being sent (sent transfers end as `Cancelled`), because an Abort cannot be sent from the old address.

- TP.CM frames left in the queue are not sent either.
- The first claim does not end them.
- At the time of this notification (also for transfers held during the wait after a claim), `address()` and `address_state()` of the node already reflect the change. `on_address_change` is called after it.
- A transfer that an `on_transfer_end` handler sends again within that notification is not ended by the same address change (it is handled with the new address and state).

When the NAME at an address leaves the address table or is replaced by another NAME, the following end without a frame being sent (the time is that of the Address Claimed frame that caused it):

- RTS/CTS transfers with that address
- BAM reception from that source
- Responses to that address in the response queue

This does not apply to peers that are not in the address table (peers whose Address Claim was not seen) or to nodes of the same Network (they never enter the address table). For a transfer between nodes of the same Network, the session on this side ends by timeout even if the peer node's address changes.

If a TP.CM of a session that ended or was replaced is still in the queue, it is dropped without being sent and counted (`transport_stale_dropped`).

### Not verified against the standard (transport protocol)

- The sender sending an Abort (reason 3) on T3 and T4
- The number of retransmission requests (2 per window), and dropping the packets after a missing one and asking for retransmission at the end of the window
- Ignoring a duplicate of the previous packet and treating old numbers as missing
- Handling of packets with a short DLC
- How the reason for rejecting an RTS is chosen (250 for under 9 bytes, byte 5 of 0 and an invalid PGN; 1 for full sessions)
- The valid range of the next packet number in a CTS
- Reason 250 when the number allowed exceeds byte 5 of the RTS
- Replacing a BAM with a new BAM from the same source
- The checks on a BAM announcement (ignoring 8 bytes or less)
- Setting bytes 3–5 of an Abort to 0xFF
- The priority and time of reassembled messages

### Transport protocol limitations

- Transfers running when the network stops are dropped without a frame being sent (there is no mechanism to send Aborts and then stop).
- The receiver does not send holds.
- There is no mechanism to register the supported PGNs and reject RTS or BAM for others.
- There is no ETP (over 1785 bytes).
- Timers that start at a send, and the BAM interval, count from the time of the step that passed the frame to the port. If bus congestion delays the actual transmission, they start counting that much earlier, and the BAM interval on the bus can shrink.
- Transfers between nodes of the same Network go through the same procedure over local loopback (passed in the next step). For the difference when an address changes, see above.
- `next_deadline()` does not include flush work that has no timer, such as packets a CTS asked for.
- After a retransmission request, a late packet of the previous window whose number falls within the retransmission window (for example, the original 10 arriving after 5 was missing and 5–16 were requested) is treated as missing, so another retransmission request can be used up (the transfer still recovers; numbers before the start of the window are ignored).

## Toolbox (`Subscription`, `Timer`, `Node::attach`)

The toolbox is 3 protocol-independent mechanisms that let parts and applications be written safely (headers `vehicle_sil/j1939/toolbox.hpp` and `network.hpp`).

### Unregistering (`Subscription`)

`Subscription{node, node.on_message(...)}` holds the registration of a handler or responder (`HandlerId`) and unregisters it when it is destroyed or on `reset()`.

- After unregistration, the handler is not called, even in the middle of a delivery (whether inside its own handler or inside another handler).
- A `Subscription` can be moved.
- It is safe to destroy it after the `Network` is destroyed (it does nothing).

### Virtual-time timers (`Timer`)

`Timer(node_or_network, kind, callback)` is a virtual-time timer. It uses no OS clock and no threads. In real time, the driver sleeps until `next_deadline()` and then runs a step.

Slots are reserved as follows:

- On construction, a timer reserves one slot of `timer_capacity`; destruction returns it.
- `Network::timers_free()` gives the number of free slots.
- The free slots are `timer_capacity` minus 2 for each node with a NAME and 1 for each existing `Timer`. The timers of transport protocol sessions are separate and not counted.

Starting and firing:

- `start_at(t)` and `start_after(d)` restart a running timer.
- You can call them from anywhere: handlers, responders, timers, the application processing, and outside a step.
- A past deadline is accepted. The timer fires at the next firing round (before the next frame or at the end of the step, or else in the next step).
- A timer started during firing fires in the same round only if its deadline is after the deadline of the timer that started it (see "Processing in one step").
- A callback can restart, cancel and destroy timers, including its own.
- Destroying a timer after the `Network` is destroyed is safe; `start_at()` is then a `std::logic_error`.

`start_after(d)` counts from the time of the event being processed (`Network::event_time()`).

| Where it is called | Starting time |
|---|---|
| A handler (including responders) | The time of the received message |
| Notifications of an address change or a transfer end | The cause time (`AddressChange::time`, `TransferEnd::time`) |
| A `Timer` callback | Its deadline |
| Anywhere else | The step time (0 before the first step) |

- If parts also use this time to count intervals, their results do not depend on the step size.
- A period restarted with `start_after()` in the callback does not drift from its deadlines and fires the same number of times, regardless of the step size. Firing can be late by up to the step size. If the period is shorter than the step size, the timer fires several times in one step.
- To count an interval from the time a message was sent (such as a response timeout), use `start_at(*network.now() + d)`, because the message goes out in the `flush()` of that step.

### Part ownership (`Node::attach`)

`node.attach<T>(args...)` creates the part `T(node, args...)` and makes the `Network` own it.

- `node.find<T>()` returns the first `T` attached to that node (nullptr if there is none).
- You can call it from anywhere (the handlers of a part attached inside a handler are called from the next delivery).
- A part does not have to be attached: the application may own it instead (destroy it before the `Network`).

Parts that the application owns may be destroyed anywhere on the network's thread. This applies to the library's parts and to parts built with `Subscription` and `Timer`.

| Where it is destroyed | Handling |
|---|---|
| Inside a handler, responder or timer callback (of the same node or of another node) | Allowed. Afterwards, even for the rest of the same delivery, the handlers of the part's `Subscription`s are not called and the part's `Timer`s do not fire. |
| Inside a user function that a part calls (the Encoder of `PeriodicSender`; `accept`, `on_state` and `on_message` of `Monitor`; the matching and callback of `Exchange`) | Allowed. |
| Inside the callback of `AddressCommander` and the `on_clear` of `Diagnostics` | The exception: not allowed (processing of the same part continues after the call). |
| Inside an `Observer` | Not allowed. |

A part that can be destroyed inside a user function moves the function object it calls (and the buffer it passes to the Encoder) to local storage for the duration of the call, learns from a flag that it was destroyed, and does not touch itself afterwards. The mechanism is in the internal header `vehicle_sil/j1939/detail/user_call.hpp`.

### Destruction order

1. Destroying a `Network` first destroys the parts attached to all nodes, starting with the last attached (no handlers are called). Nodes and timers are still usable meanwhile.
2. Then the engine is destroyed.

- If part A uses part B, attach B first.
- The destructor of a part cannot send (it runs outside a step).

### Loops that notify the user

Loops in which a part notifies its user follow the same rules as the engine: a loop covers only the range present when it started, does not use references to elements after a notification, and settles its own state before it notifies.

## Protocol parts (`libs/j1939/parts`)

Each part is a separate CMake target and uses only the public headers of the engine (`vehicle_sil::j1939`) and the toolbox. The include paths of a part's target do not contain the engine's `src/`; the engine's internals are private.

| Target | Part | Contents |
|---|---|---|
| `vehicle_sil::j1939_broadcast_suppression` | `BroadcastSuppression` | The DM13 broadcast suppression state (one per node) |
| `vehicle_sil::j1939_diagnostics` | `Diagnostics`, `Identification`, `parse_dtc_list` | DTCs and DM1/DM2/DM3/DM11/DM22, identification, reading received DTC lists. Uses `BroadcastSuppression` |
| `vehicle_sil::j1939_periodic_sender` | `PeriodicSender` | Periodic transmission of one PG, following the node's address and DM13. Uses `BroadcastSuppression` |
| `vehicle_sil::j1939_requester` | `Requester` | Sending Requests; reporting responses, ACKs and timeouts; retries; piggybacking on identical requests and limiting their interval |
| `vehicle_sil::j1939_monitor` | `Monitor` | The latest reception of one PG, and message loss (source given by address or NAME) |
| `vehicle_sil::j1939_address_commander` | `AddressCommander` | Sending Commanded Address and confirming that the target moved |
| `vehicle_sil::j1939_exchange` | `Exchange` | Sends a command of a custom protocol to one peer and waits for the response (timeouts, retries, intermediate responses, cancellation, address changes of this node and the peer, transfers of long commands and long responses) |

### Boundary test (`j1939_parts.boundary`)

The CTest test `j1939_parts.boundary` checks the following.

| Checked | What it checks |
|---|---|
| Part sources | No include of internal headers, no test API (`detail::NetworkTestAccess`), no declaration that makes a class a friend (hidden friend functions are allowed), no `#define private` and the like |
| Part CMakeLists.txt | Adds no compile definitions or options |
| Part CMakeLists.txt | Adds only its own `include/` to the include paths |
| Part CMakeLists.txt | Links only `vehicle_sil::j1939` and the targets of other parts |

Parts do not set an `Observer`; `set_observer` is a forbidden word too. A `Network` has one `Observer`, which is for tests and recording. Parts take part through handlers.

### Where parts can be called, and threads

Where a part's API says "can be called from anywhere", it means anywhere on the thread that runs the steps (handlers, timers, the application processing, outside a step). Parts have no locks, so from other threads, hand the work over with the host's `post()` (see "Threads and queues" in [core.md](core.md#threads-and-queues)).

### Timers reserved by each part

Parts reserve the following numbers of timers from `timer_capacity`. Each part's constant `kTimers` gives the number (`Monitor::kTimers` applies when `timeout` is set; `Identification`, which uses no timer, has no such constant).

| Part | Timers |
|---|---|
| `BroadcastSuppression` | 3 |
| `Diagnostics` | 3 |
| `Identification` | 0 |
| `PeriodicSender` | 1 (per PG it sends) |
| `Requester` | 2 |
| `Monitor` | 1 (when `timeout` is set) |
| `AddressCommander` | 2 |
| `Exchange` | 2 |

- If a `PeriodicSender` follows DM13 at creation (`suppressible` is true, or unset with a global destination), it also attaches a `BroadcastSuppression` when the node has none, so it reserves those 3 as well.
- A node with a NAME and diagnostics needs 8, including the 2 for Address Claim (8 such nodes with the default 64).
- Raise `timer_capacity` for nodes with many periodic transmissions. If it is too small, creating the part throws `std::length_error`, and the message names `timer_capacity`.
- Each periodic transmission uses one timer so that the rules for ordering deadlines and for firing rounds live only in the engine's `Timer` (parts do not rebuild the same mechanism).

When you create a part inside a handler (for example, to start a periodic transmission for each request), first compare `Network::timers_free()` with the number the part needs, and reject the request if there are not enough. A `std::length_error` inside a handler fails the `Network`, so without this check, sending requests from many addresses is enough to stop the ECU's communication. No other processing on the same thread runs between the check and the creation.

### DM13 (`BroadcastSuppression`)

There is one per node. Parts that broadcast on their own refer to it and do not broadcast while it is `suspended()`.

- Create it with `BroadcastSuppression::of(node)` (which attaches one with default options if there is none) or `BroadcastSuppression::attach(node, options)`.
- Attaching a second one to the same node is a `std::logic_error`.
- The constructor takes a private key type, so there is no other way to create one: an instance you created yourself would be invisible to `of()` and to the parts, and would hold a separate state. This is detected at compile time.

DM13 from other nodes is handled as follows.

| Received DM13 | What happens |
|---|---|
| The command for its own network (`BroadcastSuppressionOptions::network`, default J1939 Network #1) is Stop | Broadcasts stop. |
| The command for its own network is Start | Broadcasts resume. |
| The command for its own network is neither Stop nor Start | The Current Data Link command is used. |
| Shorter than 8 bytes | Ignored. |

- While broadcasts are stopped, every received DM13 restarts the 6-second count. Unless it is Start, this applies even to a DM13 for another network or one with only a Hold Signal.
- If no DM13 arrives for 6 seconds, broadcasts resume.
- A DM13 that arrives exactly 6 seconds after the last one counts as arriving while broadcasts are still stopped.
- The Suspend Signal and Suspend Duration of a received DM13 are treated as the sender's announcement of its own suspension, not as an instruction to stop.

Suspending the node's own broadcasts:

- `suspend(duration, scope)` stops broadcasts and announces this at the next opportunity with a DM13 to global.
- The announcing DM13 leaves the commands for all networks and the Hold Signal unspecified, sets the Suspend Signal to full or partial suspension, and sets bytes 5–6 to the number of seconds (0xFFFF for no duration).
- Broadcasts resume when the duration has passed or on `resume()`. The resumption is not announced. An announcement not yet sent is cancelled.

Suppression affects only the broadcasts of the parts that read this state. Responses to Requests, Address Claim, Acknowledgement, transport protocol control frames and messages that the application sends directly with `Node::send()` do not stop.

### Diagnostics (`Diagnostics`)

#### DTC

- A DTC is identified by SPN (19 bits) and FMI, and has the lamps it lights and their flash rate.
- `set_active(dtc, active)` makes it active or inactive (you can call it from anywhere; DM1 goes out at the next opportunity).
- The number of DTCs is limited to `DiagnosticsOptions::dtc_capacity` (1–445; a DM1 with 445 DTCs fits in one BAM). Beyond that, `std::length_error`.
- The occurrence count (1–126) increases each time the DTC becomes active.
- A DTC made inactive stays as "previously active".

#### Periodic DM1

DM1 (active DTCs) is sent to global every second while the node has an address (Claimed, or no NAME). It starts when the node gets an address and stops when the node loses it.

- When the state of a DTC changes, DM1 is sent right away, at the next opportunity.
- Sends caused by changes of the same DTC are limited to one per second. Changes within that second go into the next DM1.
- After such a send, the period counts from the time of the change. If 1 second from that time has already passed, as for a change inside a `Timer` started with a past deadline, the period counts from the step time.
- While `BroadcastSuppression` suppresses broadcasts, nothing is sent (the period advances, and missed sends are not made up later).
- A DM1 of 9 bytes or more is a BAM that waits for the previous transfer of the same node to end (`WhenBusy::Queue`).
- The next DM1 BAM does not start until the previous DM1 BAM has ended.

#### Responding to DM1 and DM2 Requests

Requests for DM1 and DM2 (previously active DTCs) are answered even while broadcasts are suppressed.

| Response length | Request | Sent as |
|---|---|---|
| 8 bytes or less | Either | One frame to global |
| 9 bytes or more | Destination-specific | RTS/CTS to the requester |
| 9 bytes or more | Global | BAM |

- A response to global is sent once for several requests that arrived at the same time, and is not sent again while a BAM for the same PGN is in progress.
- The 1-second limit and the duplicate-response check count by event time, so the result does not depend on the step size.
- Whether a DM1 or DM2 BAM is in progress is tracked by the transfer ends of that node (PGN and global destination).
- If the application sends DM1 or DM2 as a BAM from the same node, this tracking goes wrong (on a node with diagnostics, the application is assumed not to send these 2).

The data format:

- 2 bytes of lamp status and lamp flash (combined from the DTCs included; for flashing, fast > slow > on)
- 4 bytes per DTC (SPN, FMI, occurrence count)
- 4 bytes of 0 if there is no DTC
- Data shorter than 8 bytes is padded with 0xFF.

#### DM3 and DM11

DM3 clears previously active DTCs. DM11 makes active DTCs previously active.

- A destination-specific Request gets a positive ACK when clearing is done (even if there was nothing to clear). A global Request gets none.
- With `DiagnosticsOptions::on_clear`, the application decides whether to clear, to reject (NACK) or to clear later.

Clearing later works as follows:

1. The part keeps destination-specific requests, up to `deferred_capacity` (any beyond that get an ACK of "cannot respond").
2. The application calls `complete_clear(kind, cleared)` (also allowed from inside `on_clear`).
3. At the next opportunity, the part sends a positive or negative ACK.

If the node changes its address in the meantime, the kept requests are not answered.

#### DM22

- DM22 is handled only when it is addressed to this node (8 bytes or more). The part clears one DTC (an active one becomes previously active; a previously active one is deleted) and answers the requester with DM22.
- The negative reasons are that the DTC does not exist, or that active and previously active were mixed up.
- Several DM22 in the same step are answered in processing order.

#### Reading received DM1 and DM2 (`parse_dtc_list()`)

Read received DM1 and DM2 with `parse_dtc_list()` (`DtcListView`: it reads the data format above in reverse, allocates nothing and only points into the bytes you pass). For its rules, see "Read other nodes' DTCs (DM1, DM2)" in [j1939-guide.md](../j1939-guide.md#read-other-nodes-dtcs-dm1-dm2). It does not use the part's handlers, so it also works on nodes without `Diagnostics`.

### Identification (`Identification`)

The part answers the following Requests.

| Request | Contents |
|---|---|
| Software ID | The number of fields, and each field terminated by `*`. 8 bytes of 0xFF if not set |
| ECU ID | Part number, serial number, location, type, manufacturer |
| Product ID | Code, brand, model |
| Diagnostic protocol ID | J1939-73 only |

- Responses shorter than 8 bytes are padded with 0xFF. Responses of 9 bytes or more go with RTS/CTS to the requester for a destination-specific Request, and with BAM for a global Request.
- A second response to the same requester starts after the transfer of the first has ended.

### Periodic transmission (`PeriodicSender`)

Create it with `node.attach<PeriodicSender>(pgn, period, data_or_encoder, options)`. `PeriodicSenderOptions` selects the destination (one address for PDU1), the priority, the handling of missed deadlines, whether to follow DM13, and `max_length`. Data of 9 bytes or more uses the transport protocol.

#### Supplying data

| What you pass | Behavior |
|---|---|
| Bytes | The part keeps them. Replace them with `set_data()`. |
| `Encoder` | Called for every send. It writes into the part's buffer and returns the length. The buffer is allocated at creation with `max_length` bytes, default 8. |
| `VectorEncoder` | Called for every send. It appends to a `std::vector<std::uint8_t>&`, which is passed empty; its size is the length. |

- The part owns the vector of a `VectorEncoder` and reserves `max_length` bytes of capacity at creation, so appending alone does not allocate on each send.
- If a `VectorEncoder` appends nothing, a frame without data is sent.
- Build messages whose length changes from send to send with a `VectorEncoder`.
- A function that cannot be called with a span, takes a `std::vector<std::uint8_t>&` (not by value or by const&) and returns nothing is accepted as a `VectorEncoder`.
- A function that can be called with a span is accepted as an `Encoder`. If it does not return a length, it is a compile error.

#### Starting and stopping

- The part sends only while `Node::can_send_now()` is true. It does not send during the wait after a claim, so that the engine does not hold the messages and send them all at once 250 ms later.
- In the notification that the node can send, the part sends once right away (the frame goes out in that step) and counts the period from there.
- If the node can already send at creation, the part starts at the next opportunity.
- When the node loses or changes its address, the part stops, and it starts again when the node can send.

#### Deadlines and step size

Deadlines count by the `Timer` deadline (the event time), so they stay on the grid (start time + k × period) regardless of the step size. The part sends in the first step at or after the deadline, and the frame's time is the time of that step.

If the step size is the period or less, a step contains at most one deadline, so the number of sends and the deadlines do not depend on the step size (verified by tests). This claim is about a period that started from the notification that the node can send.

When `trigger()`, `resume()` or creation mid-run restarts the period, and the period has already passed at the first firing, the period is counted again from that step (neither coalescing nor catching up). This happens when you restart from the application processing or outside a step, and when the step size is the period or more. So the times and number of sends that include a restart can depend on the step size.

A missed deadline is the case where the step size is longer than the period and one step contains several deadlines. `MissedDeadlines` selects how it is handled.

| `MissedDeadlines` | Behavior |
|---|---|
| `MissedDeadlines::Coalesce` (default) | Sends once for all of them (the number coalesced is `statistics().coalesced`). The next deadline is the first grid point after that step. |
| `CatchUp` | Sends once per deadline, so frames with the same time line up (for 9 bytes or more, the send returns `Busy` until the previous transfer ends, and is counted as a failure). |

#### Following DM13 (`suppressible`)

| `suppressible` | Behavior |
|---|---|
| true | Does not send while `BroadcastSuppression::of(node).suspended()` is true. |
| false | Does not use `BroadcastSuppression`. |
| Unset (default) | Follows DM13 if the current destination is global (`kGlobalAddress`), and not if it is one address. Decided again when the destination changes. |

- Not sending while suppressed includes the first send when the node becomes able to send. Deadlines advance, and missed sends are not made up. The count is `statistics().suppressed`.
- Whether DM13 should stop a destination-specific periodic transmission is not verified, so the user chooses (see "Not verified against the standard (parts for ECU applications)" below).

To change a transmission created for one address (not following DM13) to global with `set_destination(kGlobalAddress)`, the part uses the node's `BroadcastSuppression` (`node.find()`). It does not attach one on the spot, because that would take a timer inside a handler, and the new instance would not know of earlier DM13 messages either. If the node has none, the call is a `std::logic_error` and nothing changes. In that case, attach `BroadcastSuppression::of(node)` during setup, or set `suppressible`.

#### `trigger()`, `pause()`, `resume()`

`trigger()` sends at the next opportunity and restarts the period from there. The next opportunity depends on where you call it.

| Where `trigger()` is called | Step that sends |
|---|---|
| In a handler | That step |
| In a `Timer` callback | That step or the next one (a timer started with the same deadline as the firing timer fires in the next round) |
| In the application processing, or outside a step | The next step (to send right away from the application processing, use `Node::send()`) |

`pause()` and `resume()` stop and resume the transmission.

#### Changes after creation

| Function | When it takes effect |
|---|---|
| `set_period(period)` | The new period counts from the call (the time of the event being processed; the same start as `Timer::start_after()`). |
| `set_destination(address)`, `set_priority(priority)` | From the next send. The deadline grid does not change. |

- The next send after `set_period()` comes one period later (to send right away, also call `trigger()`).
- A pending "next opportunity" send (`trigger()`, `resume()`) is kept, and the new period counts from it.
- You can call all of these while paused and while the node cannot send. The part uses the new values when it resumes.
- Invalid values (a period of 0 or less, the same destination checks as the constructor, a priority of 8 or more) are a `std::invalid_argument`, and the state does not change.
- `destination()` and `priority()` read the current values.

Do not call `set_period()` from inside an `Observer`. While the timer of the `PeriodicSender` is running, the call is a `std::logic_error` that fails the `Network`, and the period does not change. While the timer is not running, the call only stores the period.

#### Transmit failures

- Send failures (`SendStatus`) are counted (`statistics().failures`, `last_failure`), and the part sends again at the next deadline. They do not raise exceptions.
- An exception from the Encoder, and a length over `max_length`, fail the `Network` (the message gives the PGN, the length and `max_length`).
- The Encoder may destroy its `PeriodicSender` (one that the application owns). That message is then not sent (`out` stays valid until the Encoder returns).

### Sending Requests (`Requester`)

Make a request with `Requester::of(node).request(pgn, destination, callback)`.

#### Creation and options

- There is one `Requester` per node. It is attached to the node, and parts and the application share it (piggybacking and interval limiting are per node).
- `of()` attaches one with default options if there is none.
- To choose options, attach it with `Requester::attach(node, options)` before anything uses `of()`. Attaching a second one is a `std::logic_error`.
- The constructor takes a private key type, so there is no other way to create one.
- The timeout cannot be changed per request.

#### Sending and timeouts

- You can call `request()` from anywhere (also outside a step, and before the node has an address).
- The Request goes out at the next opportunity (as with `trigger()`), once the node can send (`can_send_now()`; not during the wait).
- The timeout (`timeout`, default 1250 ms) counts from the time of the step that sent the Request (because the Request goes out in `flush()`).

| Destination | How the request ends |
|---|---|
| One address | With the requested PG from that address (`RequestOutcome::Response`), or with an Acknowledgement from that address that names this node and the PGN (`Acknowledged`). |
| Global | Each response that arrives within `timeout` is reported (`last == false`), and finally `Timeout` is reported (`last == true`). |

- For one address, if nothing comes, the Request is sent again up to `retries` (default 2) times, and then the result is `Timeout`. A retry goes out in the step of the timeout.
- Global Requests are not retried.

#### Piggybacking and intervals

- A request made while a request for the same PGN and destination is waiting piggybacks on it (no Request is sent, and it gets the same response; `statistics().joined`).
- `min_interval` (default 0) sets a minimum interval between Requests for the same PGN and destination.
- A request also ends on a response that arrives while it waits (before sending, before a retry). This includes a PG received from periodic broadcasts (it is the latest value all the same).

#### Address changes and failures

| What happened | Handling |
|---|---|
| The node lost or changed its address | Requests already sent are sent again once the node can send (responses would go to the old address; these resends do not count toward `retries`). |
| The node can no longer claim an address (`CannotClaim`) | All requests end with `NotSent` (`NoAddress`). |
| A send failure | `NotSent`. |

#### Callbacks and capacity

- Callbacks are called within a step (from a handler or a timer) and can call `request()` and `cancel()`.
- The callback of a request you `cancel()` is not called.
- `RequestResult::data` is valid only during the call.
- When `capacity` (default 8) requests are waiting, `request()` returns an empty `RequestId`.

### Reception monitoring (`Monitor`)

Create it with `node.attach<Monitor>(pgn, options)`. For one PG, it keeps the latest reception (`data()`, up to `max_length`, default 8 bytes), its time, its source and the number of receptions. It sends nothing. It does not use `set_observer` (it is built with handlers only).

#### Filtering by source

The source filter is one of: any source, one address (`source`), or a NAME (`name`). With a NAME, the monitor looks up the current address in the address table and the nodes of the same `Network` on each reception, so it follows the source when the source moves.

#### Filtering with your own function (`accept`)

With the optional `accept`, a function of yours filters the messages to accept (it is called after the source condition). Use it to watch only one type of a PGN that carries several types told apart by a selector, or to check a sequence number or check value.

- A message that is not accepted is not kept and not counted as a reception (it neither ends `Lost` nor extends the deadline). It is counted in `rejected()`.
- Data that has not passed the check never appears in `data()`.
- `accept` is called within a step. It may destroy the `Monitor`; the message is then not taken (see [Part ownership](#part-ownership-nodeattach)).

#### State and message loss

The states are `Waiting` (nothing received yet), `Receiving` and `Lost` (nothing for `timeout` since the last reception).

- The loss time counts from the first reception (a slow start-up is not reported as loss).
- The deadline counts from the message time, and a reception exactly at the deadline counts as in time, so the result does not depend on the step size (verified by tests).
- State changes are reported with `on_state`, receptions with `on_message`.

### Sending Commanded Address (`AddressCommander`)

`commander.command(target_name, address, done, destination)` sends Commanded Address (the 9 bytes of NAME and new address) with BAM to global, or with RTS/CTS to one address (it waits until the previous transfer of the node ends). Like `request()`, you can call it from anywhere, and it goes out once the node can send.

The wait counts from the end of the transfer (`on_transfer_end`, matched by `TransferEnd::id`). A transfer that did not complete (cancelled by a change of this node's address, aborted by the receiver, timed out) is sent again once.

| Result | When |
|---|---|
| `Moved` | The target sent Address Claimed with that NAME for the new address |
| `Timeout` | That did not happen within `timeout` (default 1250 ms) after the transfer completed |
| `NotSent` | `send()` did not accept the command (`send_status`) |
| `NotSent` | The second transfer, sent again, did not complete either (`CommandResult::transfer` and `reason`) |

A target that is not arbitrary address capable does not comply, so the result is `Timeout`.

### Custom protocol commands and responses (`Exchange`)

`Exchange` is a part for writing the requesting side of procedures that are not in the standard (Proprietary A/B, manufacturer-specific procedures). It handles one "send a command and wait for the response". The procedure (the order of several commands, sessions) belongs to your own part. The responding side has no dedicated part; write it with `on_message` and `send` (see [j1939-guide.md](../j1939-guide.md)).

#### Start (`start()`)

Create it with `Exchange(node, options)` or `node.attach<Exchange>(options)`.

- You can call `start(pgn, command, peer, match, done, command_options)` from anywhere.
- A command is up to `max_length` (default 8 bytes). The part keeps a copy.
- The command is sent at the next opportunity once the node can send: in the same step if `start()` is called from a handler, in the next step if it is called from the application processing or outside a step.
- When `capacity` (default 4) exchanges are running, `start()` returns an empty `ExchangeId`.

#### Peer (`peer`)

- The peer is an address (0–253) or a NAME.
- A PDU1 command goes to the peer's address. A PDU2 command goes to global.
- A NAME is looked up with `Network::address_of()` for each send.
- If no control function has claimed the NAME yet at the first send (right after start-up), the part waits up to `timeout` for its Address Claimed and then sends. If none comes, the result is `PeerLost`.

#### Matching responses (`match`)

Messages from the peer's address (to this node or to global, of any PGN) are passed to the `match` of each exchange that has sent its command, oldest first.

Late responses to earlier commands (the original of a retry, a command you `cancel()`ed) are passed too, so `match` decides whether a message belongs to its exchange. `cancel()` does not cancel a command already sent. For a typed read that also checks the PGN, use `codec::decode<M>(message)`.

`match` returns `Ignore`, `Pending` or `Final`.

| `match` returns | Meaning |
|---|---|
| `Pending` | An intermediate response. `timeout` restarts from the time of that message, and no more retries are sent |
| `Final` | The response. The exchange ends with `Reply` |

A message is used only by the oldest exchange that did not return `Ignore` (identical commands to the same peer receive their responses in order).

#### Per-command options (`CommandOptions`)

| Option | Meaning |
|---|---|
| `priority` | The priority of the command |
| `timeout` | If empty, `ExchangeOptions::timeout`, default 1250 ms |
| `retries` | If empty, `ExchangeOptions::retries`, default 0 |
| `long_answer` | The PGN of a long response |
| `on_address_change` | The policy when this node's address changes |

#### Where the timeout starts

| Case | Starts from |
|---|---|
| Other than the 2 below | The time of the step that sent the command (for a retry, the step that sent the retry) |
| A command of 9 bytes or more | The completion of the transfer (matched by `TransferEnd::id`) |
| A `Pending` response was received | Restarts from its time |

A command of 9 bytes or more is sent with the transport protocol (`WhenBusy::Queue`).

#### Long responses (`long_answer`)

- After the command is sent, when an incoming transfer of that PGN from the peer starts (`Node::on_incoming_transfer`: an RTS/CTS to this node, or a BAM), the wait stops.
- When that transfer ends (completed, aborted, timed out, BAM packet missing), `timeout` restarts from the end time (on completion, the reassembled message is passed to `match` right afterwards).
- Transfers of other PGNs, from other sources or to other nodes do not stop the wait.
- Without `long_answer`, the wait continues during incoming transfers (the time of a long response counts toward `timeout`).

Per attempt, the wait can stay stopped only until `ExchangeOptions::answer_transfer_limit` (default 60 s; not a value from the standard) after the first such transfer started. After that, neither the start nor the end of a transfer changes the deadline (the wait ends at the latest `timeout` after the limit).

#### Retries on timeout (`retries`)

- After a timeout, the command is sent again. A retry goes out in the step of the timeout.
- A failed transfer of a long command (aborted by the receiver, timed out by this node) also counts as one attempt.
- After `Pending`, no retries are sent.
- By default there are no retries, because a command is not necessarily idempotent.

#### When your own address changes (`on_address_change`)

If the node loses or changes its address after sending, the response goes to the old address, and this node cannot receive it.

| Policy or case | Handling |
|---|---|
| `AddressChangePolicy::Stop` (default) | Ends with `Interrupted`. |
| `SendAgain` | Sends again from the new address once the node can send (does not count toward `retries`, and also happens after `Pending`). |
| The transfer of a long command was cancelled after its last packet (`Cancelled`) | Handled as in the 2 rows above. |
| A transfer cancelled before its last packet, or a command not yet sent | It has not reached the peer, so regardless of the policy, the part waits and sends from the new address. |

If the cancellation happened because the peer's address was taken, the Address Claimed that follows ends the exchange with `PeerLost`.

#### Exchange outcome (`ExchangeOutcome`)

`NotSent` means "did not reach the peer". `Interrupted` means "sent, but whether the peer executed it is unknown". The two are separate so that your procedure can handle non-idempotent operations. Whether all packets up to the last one went out is given by `TransferEnd::all_packets_sent`.

| Result | When |
|---|---|
| `Reply` | `match` returned `Final` |
| `Timeout` | No response after all attempts (after `Pending`, `timeout` after the last `Pending`) |
| `NotSent` | `send()` did not accept the command before it was ever sent (its `SendStatus`), or the node can no longer claim an address (`NoAddress`). The transfer of a long command in the last attempt ended before its last packet, or the receiver aborted it (`transfer`, `reason`) |
| `Interrupted` | This node's address changed after sending (`Stop`), or the node can no longer claim an address (`NoAddress`). The transfer was cancelled after its last packet (`transfer` is `Cancelled`), or this node aborted it on timeout (`Aborted`). `send()` did not accept a retry (`QueueFull` and so on) |
| `PeerLost` | The peer's address went away (see "Peer loss" below) |

#### Peer loss (`PeerLost`)

The result is `PeerLost` when, for the peer's NAME (the NAME you gave, or the NAME at that address at the first send), the node receives a sign that the NAME:

- Claims another address
- Sends Cannot Claim
- Has its address taken by another NAME

The part checks with `address_of()` on each received Address Claimed and Cannot Claim, and ends the exchange even if retries remain.

- The deadline for waiting for the NAME to resolve does not extend, even if this node's address changes in the meantime.
- If the peer is an address with no known NAME (such as a test node without a NAME), the exchange ends only by timeout.
- If the peer is a node of the same `Network` and another node takes its address, this becomes known through the peer's Cannot Claim or its Address Claimed for the new address.

#### Callback (`done`) and destruction

- The callback (`done`) is called once per exchange, within a step. It is not called for exchanges you `cancel()`.
- The data of `ExchangeResult::reply` is valid only during the call.
- `match` and `done` can call `start()`, `cancel()` and `cancel_all()`, and can destroy the `Exchange` (nothing more is called after that).
- The notification loop covers only the exchanges present at its start, and settles the state before each call.
- On destruction, the remaining exchanges end without callbacks.
- The `Exchange` may be destroyed after the `Network`. `start()` after the `Network` is destroyed is a `std::logic_error`.

### Not verified against the standard (parts for ECU applications)

The defaults of `Requester` for the timeout and the number of retries (1250 ms, 2) follow the requester values of J1939-21 and J1939-82. The following points are not verified:

- Ending without a retry when an ACK with a reason such as Busy (`AckCode::CannotRespond` and so on) is received
- Not retrying global Requests
- The handling of piggybacking and `min_interval`
- Ending a request not yet sent when the same PG is received
- Whether DM13 also stops periodic transmissions to one address (`PeriodicSender` does not stop them by default; `suppressible` selects)
- The default timeout of `AddressCommander`, and judging a move by Address Claimed

### Not verified against the standard (diagnostics)

| Topic | Not verified |
|---|---|
| DM13 | Handling of exactly 6 seconds, which DM13 restart the 6-second count, handling when no DM13 ever comes after Stop, handling when the same DM13 gives Stop and Start for different networks |
| DM3/DM11 | The deadline for an ACK sent later (if the application does not call `complete_clear()`, no answer is sent) |
| DM22 | The negative reasons that are not used, ignoring DM22 to global |
| DM2 | Building the lamp bytes from previously active DTCs |
| DTC occurrence count | The upper limit |
| Identification | The responses when nothing is set (0xFF for the software ID, empty fields) |
| `parse_dtc_list()` | The meaning of the most significant bit of DTC byte 4 (not interpreted; passed as `ReadDtc::byte4_high_bit` and `raw`) |
| `parse_dtc_list()` | Whether other ECUs send a list with no DTC in a form other than 4 bytes of 0 |
| `parse_dtc_list()` | The meaning of lamp status and flash values that `Diagnostics` does not send |

## Typed messages (`vehicle_sil::j1939_codec`)

You define the signals of a PG in YAML, and the build generates C++ types. For the format and the API, see [j1939-codec.md](../j1939-codec.md).

### Responsibilities

- The types only convert between signal values and bytes. They do not handle sending, receiving, periods, destinations or time.
- `codec.hpp` includes only `vehicle_sil/j1939/types.hpp` (`Pgn`, `Priority`) and does not know `Network` or `Node`.
- The connection to nodes and parts is through the functions in `codec_node.hpp` (`attach_sender`, `encoder`, `on_message`, `send`), all thin functions on top of the public API of the node and `PeriodicSender`.
- The engine does not know typed messages.
- Typed messages have nothing to do with time. Periods and send times follow the rules of `PeriodicSender`.
- The SAE J1939 PG and SPN definition data (J1939DA) is not bundled. Examples and tests use only proprietary PGs and fictitious layouts.

CTest checks the boundary.

| Test | What it checks |
|---|---|
| `j1939_codec.independent_of_the_engine` | `codec.hpp` includes only `types.hpp` |
| `j1939_codec.boundary` | `libs/j1939/codec` does not use engine internals |

### Generation

- `vehicle_sil_add_j1939_codec()` (`cmake/VehicleSilJ1939Codec.cmake`) calls `tools/j1939_codegen/j1939_codegen.py` at build time. The generated files are not committed.
- The generator uses Python 3.11 or later and PyYAML. They are needed only when you call this function (also when you build the vehicle-sil tests and examples).
- The generator resolves the selection and inheritance of special-value profiles (file, message, signal) and generates only an array of special values per signal.
- The same definition always generates the same header.
- Only the constants and members of the signal layout are generated. The bit manipulation is in one place, in a runtime template.

The generator stops at generation time on these definition errors (details in "What the generator checks" in [j1939-codec.md](../j1939-codec.md#what-the-generator-checks)):

- Overlaps
- Out-of-range values
- Names (not a C++ identifier, a keyword or reserved name, a clash with a member of the generated type, a clash with another name)
- Unknown keys
- Special values inside the valid range
- Direct selection of a profile that has no rules
- A custom profile selected for a file or a message that matches no signal
- Several messages with the same PGN (one has no selector, the selectors are in different places, or two selector values are equal)

### Values

- A signal keeps the raw bits as received. It returns a state (`Valid`, `Error`, `NotAvailable`, `Special`, `OutOfRange`, `Undefined`) and, only when `Valid`, the physical value.
- Special values are not reserved codec-wide. Only the signal definition decides them (in a signal without such a definition, every bit pattern is a value).
- A special value never converts to a number implicitly, and setting a physical value never produces a special value (special values are excluded from the valid range).
- Conversion between physical and raw values uses only `double` arithmetic and `std::round`, with no random numbers or clocks.
- raw × scale is rounded to `double` before offset is added. The product is stored once so that the compiler cannot fuse the multiply and add into a single rounding. Tests verify that an optimized clang build gives the same values.

### Resources

- The types are stateless values. `encode`, `decode`, and the handlers and `Encoder` of `codec_node.hpp` allocate no memory in steady state (verified by tests).
- `codec::encoder` builds a new message on the stack for every send.

### Not verified against the standard (typed messages)

The values of the built-in `j1939` profile and the lengths for which no rule is set are not verified (see "Conformance to the standard" in [j1939-codec.md](../j1939-codec.md#conformance-to-the-standard)). You can redefine `j1939` in a file.

## Observation (`Observer`)

`Network::set_observer(&observer)` receives the events of the network, read-only (header `vehicle_sil/j1939/observer.hpp`). It is an API for tests and recording and does not take part in communication.

### Events (`Event`)

An event (`Event`, kind `EventKind`) is a single value type. The meaning of its fields depends on the kind (documented in the header). `node` is the number of the local node (`Network::node()`), or -1 if there is none. `data` is valid only during the call.

| Kind | When | Time |
|---|---|---|
| `AddressChanged` | The address or state of a node changed. Emitted before the `on_address_change` handlers of that node | `AddressChange::time` |
| `SendRequested` | `send()`, `request()` or a response to a Request (`respond()`; a response to a request for an address the node no longer has gets `NoAddress`) returned its value. `held` means the message was held for the wait after a claim. `acknowledge()` is not included (ACKs are visible as `FrameSent`) | The step time |
| `MessageDropped` | A message that should have been sent was not sent (`DropReason`): the node of a held message or ACK lost its address; the data queue (the control queue for an ACK) was full when the held messages were released; a frame was put in the transmit queue before the node lost its address | The cause time (held messages) or the step time (transmit queue) |
| `FrameSent` | A frame was passed to the port (`send_result` is the port's return value; a frame kept after `QueueFull` appears again on the next attempt) | The step time |
| `MessageReceived` | Just before a received message (single-frame, or reassembled by the transport protocol) is delivered to a node. `local` means it came from another node of the same `Network` (`node` is the sending node). Not emitted for TP.CM and TP.DT | The message time |
| `TransferStarted` | A transfer started. On the sending side, when `send()` or `respond()` accepted it (including transfers that go into the response queue or the wait after a claim); on the receiving side, when an RTS or BAM was accepted (`node` is -1 for BAM) | The step time on the sending side; the time of the RTS or BAM on the receiving side |
| `TransferEnded` | A transfer ended (`result`, `reason`). A started transfer ends exactly once (as long as the `Network` does not fail and is not destroyed first). On the sending side, `source` is the address at the time of sending (if the node moves before a held transfer starts, it differs from the `source` at the start) | The cause time |
| `PortEvent` | A port event (`on_port_event()`) | The event time |

### End of a received transfer

| `result` | When |
|---|---|
| `Completed` | A `MessageReceived` for the message follows |
| `AbortedByPeer` | The sender sent a Connection Abort |
| `Aborted` | This node sent one (timeout, retransmission limit and so on) |
| `Lost` | A missing BAM packet (`reason` is `BadSequence`) or a timeout (`Timeout`). Nothing is sent |
| `Cancelled` | One of the 5 cases below |

The result is `Cancelled` when:

- Another NAME claimed the sender's address, or the sender gave it up
- The local node lost its address
- A new RTS or BAM from the same sender replaced the transfer
- The CTS could not be put in the transmit queue
- The transfer carried a single-frame PGN (Address Claimed, Request)

`TransferResult::Lost` is used only on the receiving side and never reaches `on_transfer_end`.

### Read-only rules

Calls from inside `on_event()` are handled as follows.

| Called from inside `on_event()` | What happens |
|---|---|
| Sending on that `Network` (`send`, `request`, `respond`, `acknowledge`), registering handlers, adding nodes or parts, creating and starting a `Timer`, the step functions, `set_observer()` | `std::logic_error`, and the `Network` enters the failed state. |
| Unregistering handlers, cancelling or destroying a `Timer` | These are called from destructors, so they do not throw; they put the `Network` in the failed state (unregistration returns `false`). |
| An exception thrown from `on_event()` | Fails the `Network`. |

### When it is called, and its effects

- `on_event()` is called synchronously within the step, at the points in the table above.
- Having an Observer or not changes neither the frames sent, nor their times, nor how handlers are called (verified by tests).
- When no Observer is set, each event costs one pointer comparison, and the engine allocates no memory.

### Setting, clearing and destruction

- Set and clear the Observer only outside a step (anywhere once the `Network` is in the failed state).
- An Observer watches only one network. Setting it on another network removes it from the previous one (a `std::logic_error` if the previous network is within a step).
- Destroying an Observer removes it automatically. Destroying the `Network` first is safe.
- Do not destroy an Observer inside `on_event()`.

## Step size and resource limits

### Step size

| Step size | What happens |
|---|---|
| Over 50 ms | A warning (`NetworkOptions::warning`, default stderr). |
| Over 200 ms | `start()` throws `std::invalid_argument`, and the host enters the failed state (the 200 ms for Request responses and packet intervals cannot be kept). |

10 ms or less is recommended. When `RealTimeDriver` runs the network, the same check applies to its `max_idle`.

In real time, the driver wakes at timer deadlines (`next_deadline()`). Packets that a CTS asks for go out in the step that received the CTS, but frames kept after the port's `QueueFull` and frames carried over by the per-step limit go out in the step after `max_idle`.

### Buffer and timer reservation

All buffers are allocated at construction. `NetworkOptions` sets:

- Receptions per step
- Nodes
- The data queue
- Sends per step
- Timers
- The hold area per node
- Transport protocol sessions (each a 1785-byte buffer and one timer; the timer is allocated separately from `timer_capacity`)
- The response queue

`timer_capacity` works by reservation. Because of the reservation, starting a timer never fails for lack of a slot.

| What reserves | Number | If there are not enough |
|---|---|---|
| Adding a node with a NAME | 2 (the wait after a claim, and Cannot Claim) | `add_node()` throws `std::invalid_argument`. |
| Creating a `Timer` | 1 | Creating the `Timer` throws `std::length_error`. |

### Memory allocation

The following do not allocate memory (verified by tests that count `operator new`):

- Receiving and delivering frames
- Responding to Requests
- Sending (including the port's `QueueFull` and `Failed`, and carry-over by the send limit)
- Local loopback
- Timers
- Address Claim (including arbitrary address selection, the address table, address violations, Commanded Address and state notifications)
- Transport protocol (including retransmission requests, timeouts, Aborts and the response queue)

The following also allocate no memory in steady state:

- The toolbox and the parts (starting and cancelling a `Timer`, periodic DM1 and its BAM, DM13, DM1/DM2/identification responses, DM22, ACKs sent later, `PeriodicSender`, responses, timeouts and retries of `Requester`, `Monitor`, `AddressCommander`, and responses, intermediate responses, timeouts, retries and long commands of `Exchange`)
- Notifications to the `Observer`
- Sending and receiving typed messages (`codec::attach_sender`, `codec::on_message`)

Memory is allocated only:

- When a node is added
- When handlers and responders are registered and unregistered
- When a part is created
- When identification data is set
- When `Requester::request()`, `AddressCommander::command()` and `Exchange::start()` copy the callback (large captures)

### When a limit is reached

| Limit | What happens |
|---|---|
| Reception | The rest of that step is dropped and counted. |
| Data queue | `send()` returns `QueueFull`. |
| Control queue | What overflows is dropped and counted. |
| Nodes | `add_node()` throws `std::length_error`. |
| Transport protocol | As described in "Transport protocol (J1939-21 TP)" above. |

The capacity of the control queue is derived from the reception limit, the number of nodes, the size of the hold area, the number of sessions and the size of the response queue. Normally it does not fill up.

### Failed state

The `Network` enters the failed state on either of:

- An exception from a handler, responder, timer or the port
- A usage error (`start`/`begin`/`receive`/`process`/`flush`/`add_node` from a handler, responder or timer of that `Network`, a time that does not increase, an error in the order of phases)

Every later step call is a `std::logic_error`. The `Network` stays in the failed state even if a handler catches and ignores the exception.

## J1939 exchanges verified by integration tests

The Sender runs a `Peer` in real time and creates one node of the J1939 stack. Its NAME is industry group 2, function 130, manufacturer 0x7F0, identity 0x1234. After the Receiver is running, the Sender adds the node and has it claim address 0x80. Once the address is its own, the node broadcasts PGN 0xFF10 5 times. All frames go out through the SIL Kit CAN port of the Peer.

The Receiver does not use the J1939 stack. It receives directly with the SIL Kit CAN API and checks the order and content, byte for byte, against expected values computed from the J1939 definitions.

| Order | Content | CAN ID | DLC | Data |
|---|---|---|---|---|
| 1 | Address Claim | `0x18EEFF80` | 8 | `34 12 00 FE 00 82 00 20` (NAME `0x20008200FE001234`, little-endian) |
| 2–6 | PGN 0xFF10 | `0x18FF1080` | 8 | Test data derived from the send number |

The stack starts with its own Address Claim. It does not send a Request for Address Claim at start-up.

| Exit code | When |
|---|---|
| 1 | Verification failed (one of the 5 cases below) |
| 2 | Timeout (the expected frames did not all arrive in time) |
| 3 | Connection or start-up failed |

Verification fails when:

- A frame is not an extended frame
- The order is wrong (a PGN before the Address Claim, a second Address Claim)
- An unknown ID appears
- An extra frame arrives before all the expected frames are complete
- A payload does not match

## Known J1939 limitations

The limitations of the J1939 stack and the points not verified against the standard are described in the sections of this page. The main ones that matter when you connect to real ECUs or tools:

- There is no ETP (messages over 1785 bytes).
- Transfers running when the network stops are dropped without an Abort being sent.
- The receiver does not send holds (CTS for 0 packets).
- DM13 stops only the broadcasts of parts that read the suppression state (DM1). Messages that the application sends directly with `Node::send()` do not stop.
- When the node ends its own suspension, it does not announce the resumption (see "DM13 (`BroadcastSuppression`)").
- Running the J1939 stack directly on an XL channel (`ExternalPortAdapter`) and operation with the Vector Network Simulator are not verified (see "Test coverage" in [bridges.md](../bridges.md#test-coverage) and "Simple CAN Network Simulator" in [can.md](can.md#simple-can-network-simulator-vehicle_silcan_netsim-vehicle_sil_can_bus_simulator)).
