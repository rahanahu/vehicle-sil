# 共通仮想時間

[English](../../internals/virtual-time.md)

仮想時間の進み方、時間ゲート（一時停止、ステップ実行、速度）、受信の順序について、実装が守る保証と制限を書きます。

SIL Kit の `ITimeSyncService` で、すべてのピアが 1 つの仮想時間を共有します。ピアごとにステップ幅を決められます（例: 物理モデル 1 ms、LIN Slave 2 ms、LIN Master 5 ms、J1939 ECU 10 ms）。ピアはそれぞれ独立したプロセスで、同じ PC でも別の PC でも動きます。

## 時間の型

- シミュレーション時間は `vehicle_sil::SimTime`（`std::chrono::time_point<SimClock, nanoseconds>`）と `SimDuration` で表します。
- `SimClock` は壁時計ではなく、`now()` を持ちません。
- `SimTime` は `steady_clock` や `system_clock` の時刻とは型が違うので、混ぜるとコンパイルエラーになります。
- `SimTime{}` はシミュレーションの開始時刻（T = 0）です。

## 参加と進み方

### 時刻同期への参加とステップハンドラー

`ParticipantRuntimeOptions::virtual_time` を指定すると、participant は時刻同期に参加します。ハンドラーは非同期版（`SetSimulationStepHandlerAsync`）で、利用者のハンドラーが戻るとすぐに `CompleteSimulationStep()` を呼びます。利用者から見ると、ハンドラーが戻ったときにステップが終わる点はブロッキング版と同じです。

SIL Kit はステップハンドラーと受信ハンドラーを同じ I/O スレッドで呼ぶので、ステップの実行中、その participant のほかのハンドラーは呼ばれません。

`CompleteSimulationStep()` は完了の処理を I/O スレッドのタスクとして積みます。そのため、ステップで送信したメッセージだけでなく、SIL Kit がそれを自分に配送するときに送信するメッセージ（LIN の Master が送信するフレーム。2 段目の送信）も、次のステップの時刻を通知する前に送信されます。ブロッキング版では、この 2 段目の送信が通知より後になり、受信側のステップに間に合う保証がありません（[dependencies.md](../dependencies.md)）。

利用者は `set_step_handler()` でステップごとの処理を渡します。`start()` より前に渡さないと、`start()` が `std::logic_error` を投げます。

### 開始と進む順序

開始と停止は `LifecycleMode::Coordinated` でそろえます。`SimulationController`（または `vehicle_sil_sim_controller`）が、必要な参加者がそろってから workflow configuration を配布します。その結果、全員が T = 0 から同時に始まります。

SIL Kit は、participant がステップ T を実行するのを、ほかの全員が T より前のステップを終えるまで待たせます。全体の進み方は最も遅いピアで決まります。

- ステップハンドラーが壁時計で長くかかると（重い `tick()` など）、ほかのピアはそれを待ちます。ステップは飛ばしません。
- そのため、実行速度に関係なく、各ピアのステップの並びと受信するデータは同じになります。

### 終わりの時刻（`stop_at` と `VirtualTimeOptions::end`）

`SimulationController` の `stop_at` を指定すると、controller は stop_at だけのステップで時刻同期に参加し、時刻 stop_at で全体を停止します。このとき、ほかの全ピアは stop_at より前のステップをすべて終えています。stop_at と同時刻のステップを実行するかどうかは決まっていません。

そのため、各ピアの作業範囲は `VirtualTimeOptions::end` で決めます。end ≤ stop_at にすれば、最後に処理するステップは停止のタイミングに左右されません。

| ステップ | ステップハンドラー | `steps_completed()` | 時刻同期と実時間との結合 |
|---|---|---|---|
| end より前に始まる | 呼ばれる | 数える | 参加する |
| end 以降 | 呼ばれない | 数えない | 参加する |

end 以降はハンドラーが受信バッファ（`StepInbox`、`SilKitCanPort` の受信キュー）を空にしないので、ほかのピアが送信し続けるとあふれます。あふれの判定は、処理したステップの範囲で行います。

### 実行の上限と中断（`vehicle_sil_sim_controller`）

`vehicle_sil_sim_controller` の `--timeout-ms` は、起動待ちの上限です。`--stop-at-ms` を指定したときは、起動後の実行にも同じ値を上限として別に適用します。`--stop-at-ms` がなければ、シミュレーションは Ctrl+C / SIGTERM まで続きます。起動待ちの間の Ctrl+C は、プロセスをそのまま終了させます。

実行中に必要な参加者が抜けると、controller は次の条件でシミュレーションを中断し、終了コード 1 で終わります。

| 参加者の抜け方 | 中断するとき |
|---|---|
| Error で抜けた（ステップの失敗、接続断） | すぐ |
| ほかの状態で抜けた | 5 秒たってもシミュレーションが終わらないとき |

5 秒は、参加者が自分で止めたシミュレーションを、誤って失敗にしないための猶予です。

この判定は `vehicle_sil::FailureCheck`（`vehicle_sil/core/failure_check.hpp`）で、`vehicle_sil::Simulation`、`vehicle_sil_launch run`、Control Server の `SimulationMonitor` と共通です。controller を持つツール（`Simulation`、`vehicle_sil_sim_controller`、`vehicle_sil_launch run`）は、終わりを待って中断や停止をするループも `vehicle_sil::watch_simulation()`（`vehicle_sil/core/simulation_watch.hpp`）で共有します。どのツールも、ログに参加者の名前、状態、理由を出力します。SIL Kit は失敗した参加者がいても全体を止めず、仮想時間が進まなくなるだけだからです。

### ステップハンドラーの例外と停止

ステップハンドラーが例外を投げると、`ParticipantRuntime` はそれを捕まえて SIL Kit にエラーを報告します。その participant は Error になり、`step_error()` がメッセージを返します。`wait_until_finished()` は Error も終了として返します。SIL Kit は Error の participant を停止するまでそのままにするので、`stop()` かデストラクターで Shutdown にします。

例のピア（`examples/virtual_time`）は、シミュレーションが `--end-ms` より前の最後のステップに達せずに終わった場合（中断）、Shutdown でも終了コード 1 で終わります。

停止の保証とルールは次のとおりです。

- `stop()` が戻った時点で、ステップハンドラーは実行中でなく、以後も呼ばれません。
- 実行中のハンドラーがあれば、`stop()` は終わるまで待ちます。
- ハンドラーが使うオブジェクトは、`stop()`（またはデストラクター）のあとに破棄します。
- ステップハンドラーの中からは `stop()` ではなく `request_stop()` を呼びます。
- coordinated では、どの participant が停止しても全体が止まります。

## 実時間との結合

- 何も指定しなければ、仮想時間はできるだけ速く進みます（実時間より速くなりえます）。
- `VirtualTimeOptions::real_time_factor` を指定すると、そのピアは各ステップを壁時計に合わせて保持します。1.0 で実時間、4.0 で 4 倍速、0.5 で半分の速度です。
  - 最初のステップで壁時計と仮想時間を対応づけ、ステップ [T, T+Δ) は「対応づけた時刻 + (T + Δ − 開始時刻) / factor」まで終わりません（`RealTimePacer`）。
  - 1 つのピアを結合すれば、ほかのピアもそれを待つので全体が同じ速度になります。
  - 待つことしかしないので、目標より遅いピアを速くはできません。
- SIL Kit の `AnimationFactor`（experimental）は使いません。

## 一時停止、ステップ実行、速度（時間ゲート）

`SimulationControllerOptions::time_control` を指定すると、`SimulationController` は `TimeControlOptions::step`（既定 10 ms）のステップで時刻同期に参加します。そのステップの完了を保留して、シミュレーション全体を止めます（時間ゲート）。

### 止まる位置

controller がステップ P を保留すると、時刻同期に参加しているほかの全ピアは「開始時刻が P 以下のステップ」をすべて実行し、P より後に始まるステップを実行しません。ステップ幅が違っても同じです（P = 50 ms なら、1 ms のピアは 50 ms、3 ms のピアは 48 ms のステップまで）。これを「P で止まっている」と呼びます。止まる位置は controller のステップの倍数です。

### 操作

どの操作もスレッド安全で、待ちません。

| 操作 | すること |
|---|---|
| `pause()` | ペース調整で保留しているステップがあればそこで、なければ次のステップで止める。 |
| `pause_at(T)` | T 以上で最初の controller のステップで止める（T を過ぎていれば次のステップ）。 |
| `resume()` | 再開する（止める予定も消す）。 |
| `run_until(T)` | T 以上で最初の controller のステップまで進めて止める。すでに T 以降で止まっていれば何もしない。 |
| `step(d)` | `run_until(time_state().now + d)` と同じ。 |
| `set_speed(f)` | 速度を、仮想時間の秒 / 壁時計の秒で指定する（空ならできるだけ速く）。 |
| `time_state()` | 現在の位置（止まっているか、P、止める予定、速度）と、遅れと止まっていた時間（下の「遅れの測り方」）を読む。 |
| `wait_until_paused(timeout)` | 止まるのを待つ（ライフサイクルが終わったら空を返す）。 |
| `TimeControlOptions::start_paused` | T = 0 で止めて始める（全ピアは時刻 0 のステップだけを実行して止まる）。 |

`set_speed(f)` では、controller が各ステップの完了を壁時計の期限まで遅らせます。速度を変えたときは待ち終えた分を保ち、再開のときは壁時計との対応づけをやり直します。いちばん遅いピアより速くはできません。遅れたときは追いつきません（下の「遅れの測り方」）。

### ステップの保留

保留はステップハンドラーの外で行います（`ParticipantRuntime::set_step_hold()` と `release_step()`）。controller の SIL Kit のスレッドは空いたままなので、止まっている間も状態の通知と停止を受信します。SIL Kit の HealthCheck は保留しているステップを時間切れにしません。止まっている間の `stop()` と `abort()` は、そのまま全体を終わらせます。

### 決定論性

時間ゲートは止める位置と速度を決めるだけです。途中で止めた実行、1 ステップずつ進めた実行、速度を変えた実行のどれでも、各ピアが実行するステップと受信するデータは、止めずに実行したときと同じです。

### `stop_at` との併用

`stop_at` と併用すると、controller は stop_at 以上で最初の自分のステップで停止します。`wall_time_to_stop_at()` には、止まっていた時間と速度の調整で待った時間も入ります（止まっていた時間を除いた値は `TimeState::running_for`）。stop_at のステップは保留しませんが、遅れは測ります。

### 速度を変える時点と期限

`set_speed()` で同じ値を設定し直しても、何も変わりません。値を変えたときの扱いは、変える時点で決まります。

| 速度を変える時点 | 起きること |
|---|---|
| ペース調整でステップを保留している間 | 待ち終えた分はそのままで、残りを新しい速度で待つ。 |
| ステップの間 | 次のステップの期限はそのままで（そのステップがすでに遅れていれば、その遅れも保って）、そこから新しい速度で数える。 |
| ステップの間（速度の指定がない状態から速度を付ける） | 次のステップの期限はその時点になる。 |
| 止まっている状態から再開するとき | そこから壁時計との対応づけをやり直す。 |
| 最初のステップより前（`start()` の前） | 最初のステップで対応づける（始まるまでの時間を遅れに数えず、取り戻そうと速く進めることもない）。 |

### 遅れの測り方

定義は `TimeControlOptions` のコメントを正とします。遅れは、速度があり、壁時計との対応づけ（基準）がある間だけ数えます。

| 言葉 | 定義 |
|---|---|
| 期限 | controller のステップ P を始めてよい壁時計の時刻（基準の壁時計 +（P − 基準の仮想時刻）÷ 速度）。 |
| 遅れ | ステップ P が始まった壁時計の時刻 − 期限（負なら 0）。 |
| 遅れたステップ（`late_steps`） | 遅れが `TimeControlOptions::late_tolerance`（既定 10 ms。壁時計の時間で、ステップと速度によらない）を超えたステップ。 |
| `max_lateness` | 許容の内のものも含む、遅れの最大。 |
| ずれ（`slipped`） | 遅れたステップの遅れの合計。 |
| `paused_for` | 止まっていた壁時計の時間の合計（止まっている間も増える）。 |
| `running_for` | 最初のステップが始まってから最後のステップが始まるまでの、止まっていた時間を除いた壁時計の時間。 |

**期限**。どのステップも期限より前には始まりません。

**遅れ**。ステップ P が始まるのは、ゲートが前のステップを放し、P より前に始まるピアのステップが全部終わったと controller が知ったときです。ゲートのスレッドの起床の遅れも入ります（`TimeState::max_gate_lateness` に、その分だけを別に持ちます）。ピアがステップを終えてすぐ次のステップに入ると、SIL Kit は終わったことを次のステップの後で伝えるので、遅れは最大でピアの 1 ステップの時間だけ大きく出ます（小さくは出ません）。

**ずれ**。遅れたステップでは追いつかず、そのステップを新しい基準にします。以後のステップは、そこから指定の速度で進みます。許容の内の遅れでは基準を変えず、期限を過ぎたステップは保留しないので、自然に取り戻します。

**数える範囲**。基準をとった次のステップから、最後のステップ（stop_at のステップを含む）までです。期限を過ぎてもまだ始まっていないステップは、`time_state()` を呼んだ時点までの遅れ（`current_lateness`）で数えます。`time_state()` の数は「いま終わったとしたら」の値で、同じステップを 2 回は数えません。数は、次のどれか早い時点で固定します（`ParticipantRuntime::set_stop_observer()`）。

- 止める要求（`stop()`、`request_stop()`、stop_at）
- `abort()`
- controller のライフサイクルが Running を離れたとき（ほかのピアが止めたときも）

止まったままの実行が終わっても、その遅れは残ります。

**止まっていた時間**。止まっていた時間は数えません（再開で基準をとり直します）。`running_for` は、次のステップが期限を過ぎている間と、速度の指定がなくゲートが何も保留していない間は、いままでの時間です。起動と終了の処理は入りません。

**ステップの細かさ**。ゲートが壁時計に合わせるのは controller のステップの境目だけです。時刻 T に始まるピアのステップは、T 以上で最初の controller のステップの期限に動きます。T にあたる壁時計の時刻より、最大で「controller のステップ −（controller のステップとピアのステップの最大公約数）」遅く、早くはなりません。実時間で動く機器と接続するときは、controller のステップを、ピアのステップの最大公約数にします（`vehicle_sil_launch` は、速度の指定があるとき、既定でそうします）。

### ゲートの待ち

ゲートのスレッドは、期限まで `steady_clock` の時刻で待ちます（`libs/core/src/deadline_waiter.cpp`）。Windows では、条件変数の時間つきの待ちがシステムのタイマーの分解能（既定で約 15.6 ms）で丸められるので、高分解能の待機タイマー（`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`）で待ちます。それがない Windows では、普通の待機タイマーと `timeBeginPeriod(1)`（ゲートがある間だけ）を使います。

### 実装の場所

状態と計算は `libs/core/src/time_gate.{hpp,cpp}`（`detail::TimeGate`）にあり、スレッド、ロック、時計を持ちません（どの関数も壁時計の時刻を引数で受け取ります）。`SimulationController` が mutex の下で呼び、保留したステップを放すスレッドを持ちます。遅れの数は、時刻を決めた例で `tests/core/test_time_gate_model.cpp` が確認します。

### 制限

- 止まるのは時刻同期に参加しているピアだけです。仮想時間を使わないピア（実時間のピア、Vector XL のブリッジなど）は動き続けます。
- controller のステップを小さくすると、ステップごとの同期の往復が増え、全体が遅くなります。
- ピア自身の `real_time_factor` と `set_speed()` は両方かかります（遅いほうで決まります）。速度を controller で決めるときは、ピアの `real_time_factor` を使いません。
- 巻き戻しと、終わったシミュレーションのやり直し（リセット）はできません。やり直すにはプロセスを起動し直します。
- 速度の調整は controller のステップごとです。ピアの (P, P + controller のステップ] のステップは、controller が保留を解いてからまとめて進みます。
- `wait_until_paused()` は、同じプロセスのピアのステップの中から呼びません（そのステップが終わらないと止まる位置に達しないので、必ず時間切れになります）。ほかの操作はステップの中からも呼べます。
- time_control があるとき、controller の `runtime()` の `set_step_hold()` と `release_step()` は時間ゲートが使っているので、呼びません。
- `ParticipantRuntime::set_step_hold()` の保留の判断は、`stop()` が戻った後と、停止の要求の後には呼ばれません。`VirtualTimeOptions::end` 以降のステップでは呼ばれます。
- 保留の判断の中から `release_step()` と `stop()` は呼びません（`request_stop()` は呼べます）。

## 受信の扱い（決定論性）

SIL Kit が保証するのは、ステップ T の時点で T より前のタイムスタンプのメッセージをすべて受信していることだけです。タイムスタンプがちょうど T のメッセージをステップ T の前に受信するかどうかは決まっていません。そこで、次のようにしています。

- ステップの外で受信したメッセージは `StepInbox` にためます。
- ステップ T では、タイムスタンプが T より前のものだけを、(タイムスタンプ, タイブレーク, 到着順) の順に渡します。T ちょうどのものは次のステップで渡します。
- 別のピアがステップ T で送信したデータは、受信側では T より後の最初のステップで処理されます。たとえば 1 ms の物理モデルが T で出した値を、10 ms の ECU はステップ T+1 ms 以降（実際には次の 10 ms 境界）で受信します。
- `StepInbox` の容量は固定です。満杯になると捨てて数えます。

CAN のフレームも同じルールです。`SilKitCanPort` は、タイムスタンプが T より前のフレームだけをステップ T で渡します。同じ時刻に別の送信者が送信したフレームの到着順は SIL Kit では決まらないので、J1939 の `Network` は、送信者ごとの列を CAN の調停の順に取り出して並べます（[j1939.md](j1939.md) の「1 ステップの処理」）。結果はステップ幅と到着順によりません。

## J1939 を仮想時間で動かす

J1939 の `Network` は SIL Kit の `SilKitCanPort` の上で、ホストのステップとして動きます。`Peer` を使うか、`bind_host(runtime, host)` でホストを `ParticipantRuntime` のステップハンドラーに結び付けます。スタックはスレッドを作らず、時計を読みません。タイマー（Address Claim の後の 250 ms など）は仮想時間で進みます。

1 ステップの中では、受信と処理、アプリの処理、送信の順です（[j1939.md](j1939.md) の「1 ステップの処理」、`Peer` は [execution.md](execution.md) の「Peer」）。アプリがステップの中で送信したメッセージは、そのステップの終わりに、ステップの時刻で送信されます。送信を起点とするタイマー（T3 など）も、この時刻から数えます。

## 固定周期 tick() の統合

既存の ECU モデル（固定周期の `tick()` を持つ DLL など）は、ステップハンドラーから `TickScheduler` で呼びます。vehicle-sil は、DLL から使える共通ライブラリです。DLL そのものは取り込みません。

| 呼び方 | 周期とステップ幅の関係 |
|---|---|
| `TickScheduler` | タスクの周期とオフセットは、participant のステップ幅の倍数でなければならない。そうでなければ `add()` が例外を投げる。 |
| `Ecu` の `every(period, fn)` | 検査しない（周期の時刻以後の最初のステップで、1 ステップに 1 回まで呼ぶ）。 |

`TickScheduler` では、周期がずれたまま黙って動くことはありません。例の ECU は、周期がステップ幅の倍数であることを起動時に `on_step_grid()` で確認してから `every` を使います。

1 つの participant に、周期の違う複数のタスクを載せられます（例: ステップ 5 ms で、10 ms の `tick()` と 20 ms の診断タスク）。

`tick()` はステップハンドラーの中で動くので、次のことが言えます。

- `tick()` の実行中、その participant のほかの SIL Kit ハンドラーは呼ばれません。受信コールバックとの排他は不要です。
- 長い `tick()` は全体を待たせます。

### DLL を統合する前に確認すること

`tick()` の中で、同じステップのうちに別のピアの応答を待つことはできません（デッドロックする）。ステップはハンドラーが戻ると完了するので（「参加と進み方」）、応答を待ってから `CompleteSimulationStep()` を呼ぶ形はありません。統合する DLL にこの処理がないかを、統合の前に確認します。

DLL の内部で実時間に依存している箇所（スリープ、`GetTickCount` などでの時刻の取得、XL ドライバのタイムスタンプ）は、vehicle-sil では置き換えられません。統合する DLL ごとに確認が必要です。

## 検証の範囲

単体テストは、プロセス内のレジストリか偽の CAN コントローラーを使い、仮想時間で動きます。速度を変えて結果を比べるテストを除き、壁時計の速度によりません。確認していることは次のとおりです。

- 共通仮想時間
  - ステップ幅の違う参加者が SIL Kit の進行条件を守ること（ステップ T を始めた時点で、ほかの全員が T より前のステップを終えている）
  - 遅い参加者を全体が待つこと
  - `real_time_factor` で指定した速度で進むこと
  - 例外が報告されること
  - `TickScheduler` の周期
  - `StepInbox` の順序と容量

- 上流へのパッチ（[dependencies.md](../dependencies.md)）には、どれも、パッチを外すと失敗する vehicle-sil のテストがあります。

プロセスを分けた統合テストでは、次のことを確認しています。

- 統合テスト（`virtual_time.*`）では、registry、`vehicle_sil_sim_controller`、物理モデル（1 ms）、ECU（10 ms、共有ライブラリの `tick()` と J1939）、LIN センサー（2 ms）、ボディコントローラー（5 ms、LIN Master と J1939 の受信）を別プロセスで動かします。どのピアも `Peer` の上で動きます。
  - 各ピアのトレースを照合し、データがピアの間を予測どおりの仮想時刻で渡ることを確認します。
  - ECU は最初のステップで Address Claimed を送信し、その 250 ms 後に自分のアドレスを持ちます。CCVS はそれ以後だけ送信します。ボディコントローラーが受信した Address Claimed と CCVS の時刻と内容を、ECU のトレースと照合します。
  - 全速、遅い `tick()`、4 倍速への結合、1 つのピアだけ 0.5 倍速への結合の各条件で、トレースがバイト単位で一致することを確認します。
  - 壁時計の所要時間が、実時間より速い（全速、4 倍速）または遅い（遅い `tick()`、0.5 倍速）ことを確認します。
