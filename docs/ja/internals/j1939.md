## 実装している機能と前提

外部の J1939 ライブラリを使いません。API はまだ変わることがあります。今あるのは次の機能です。

- 識別子と PGN
- 単一フレームの送受信
- Request（PGN 59904）への応答
- Acknowledgement（PGN 59392）
- タイマーの仕組み
- NAME と Address Claim（任意アドレスの選択、アドレス表、Commanded Address の処理、アドレス違反を含む）
- トランスポートプロトコル（BAM と RTS/CTS。9〜1785 バイト）
- コンポーネントを作るためのツールキット（`Subscription`、`Timer`、`Node::attach`）
- 読み取り専用で観測する API（`Observer`）
- プロトコルのコンポーネントの DM13（ブロードキャストの抑制）、診断（DM1、DM2、DM3、DM11、DM22）、識別情報
- ECU アプリ向けの周期送信（`PeriodicSender`）、Request の送信と応答待ち（`Requester`）、受信の監視（`Monitor`）、Commanded Address の送信（`AddressCommander`）、独自プロトコルのコマンドと応答（`Exchange`）

ETP はありません。NAME を指定しないノードは、生成時に指定した固定のアドレスで動きます（テスト用）。

前提は次の 2 つです。

- `vehicle_sil::can` だけに依存します（SIL Kit なし）。スレッドを持たず、時計を読みません。`Network` が `Steppable` で、ホストがステップごとに実行します。
- 時刻は `SimTime` です。受信したメッセージの時刻はフレームの時刻（仮想時間では送信側のステップ時刻）、送信の時刻は送信したステップの時刻です。

## 責務の境界（エンジン、ツールキット、コンポーネント）

機能を追加するときは、次の 3 つのどこに置くかを先に決めます。規格に含まれるという理由だけでエンジンに入れません。

| 置く場所 | 置くもの |
|---|---|
| エンジン（`Network` と `Node`） | J1939 の通信を成り立たせるもの、ノード全体の状態と通信上の正しさ、複数のコンポーネントが共有する通信資源、コンポーネントごとに持つと競合や不整合が起きるもの |
| ツールキット | コンポーネントを安全かつ簡潔に書くための小さな共通機能（イベントの登録の RAII、仮想時間のタイマー、ノードがコンポーネントを所有する仕組み） |
| プロトコルのコンポーネント | 固有の手順や状態機械を持ち、ノード全体の状態や共有資源を直接変えず、他のコンポーネントと独立に追加し削除できるもの（周期送信、Request を送信して応答を待つ処理、診断、機能安全通信、Memory Access、独自プロトコルなど） |

今ある次の機能は、すべてエンジンです。

- 識別子と PGN
- 送受信と配送
- NAME とアドレスと Address Claim
- Commanded Address の受信
- Request の配送と NACK
- Acknowledgement の送信
- トランスポートプロトコルのセッション・タイムアウト・中断・送信キュー
- 統計とポートのイベントの集計

ツールキットに追加するのは、複数のコンポーネントが共通に必要とし、既存の API では安全さや簡潔さが足りず、特定のプロトコルの処理を含まないものだけです。

コンポーネントは次のルールを守ります。

- ノードの公開 API とツールキットだけで作ります。
- スレッドやイベントループを持たず、ステップの中だけで動きます。
- エンジンの内部を操作するためだけの公開 API は追加しません。
- 同じ機能をエンジンとコンポーネントの両方に作りません。
- `on_any_request` を使いません（応答者のない PGN への既定の NACK を奪うため）。
- 1 つの PGN の応答者は 1 つです（同じ PGN に複数あると、先に登録したものだけが呼ばれます）。

境界をまたぐ機能は、通信の整合を保証する部分をエンジンに、プロトコルの手順をコンポーネントに分けます。

| 機能 | エンジン | コンポーネント |
|---|---|---|
| Request | 配送 | 発行、応答待ち、時間切れ |
| Commanded Address | 受信したときのアドレスの変更と、トランスポートプロトコルのセッションとの整合 | 送信 |

エンジンにもコンポーネントにも入れないものと、エンジンでしないことは次のとおりです。

- PG と SPN の定義（信号の配置、スケーリング、特別な値）は、エンジンにもコンポーネントにも入れません。型付きメッセージ（`vehicle_sil::j1939_codec`）がバイト列との変換だけを受け持ち、エンジンとコンポーネントはバイト列を扱います。
- DM13 によるブロードキャストの停止は、エンジンでは行いません。エンジンはどの送信が「ブロードキャスト」かを区別できないためです。抑制の状態はコンポーネント（`BroadcastSuppression`）がノードに 1 つ持ち、自分で周期的にブロードキャストするコンポーネント（DM1 など）がそれを読みます。アプリが `Node::send()` で直接送信するメッセージは抑制されません。

## 値の型

- `Pgn` は 18 ビット（拡張データページ、データページ、PF、PS）です。PF が 240 未満（PDU1）の PGN は宛先を持ち、PGN の PS は 0 です。PS が 0 でない PDU1 の値と 18 ビットを超える値は不正です。予約ビット（拡張データページ）は PGN の一部として扱い、フレームを捨てません。
- `Identifier` は 29 ビットの識別子の各フィールドです。PDU1 では PS が宛先、PDU2 では宛先は常にグローバル（255）です。不正な PGN、優先度 8 以上、PDU2 で宛先がグローバル以外のものは `encode()` が `std::invalid_argument` を投げます。
- アドレス 254 は未取得のアドレス、255 はグローバル宛てです。ノードのアドレスは 0〜253 です。

## Network と Node

`Network` は 1 つの CAN チャネルにある、このプロセスのノード（`Node`）の集まりです。ノードは `add_node()` で作り、`Network` が所有します（`Network` の寿命まで有効）。

### ノードの追加

| `add_node()` を呼ぶ場所 | 扱い |
|---|---|
| ステップの外 | 追加できます。 |
| ホストのアプリの処理の中 | 追加できます。その `Network` の次の `begin()` から加わります。 |
| 同じホストの別の `Network` のハンドラーの中 | 追加できます。その `Network` の次の `begin()` から加わります。 |
| 別のホスト | その `Network` から見てステップの外なので、次のステップから加わります（ホストを実行する順で決まります）。 |
| 自分の `Network` のハンドラー、応答者、タイマー | 使い方のエラーです。 |

ステップの中で追加したノードは、その `Network` の次の `begin()` まで受信せず、Address Claim も始めません。これはホストへの登録順によらず同じです。

`Node::address()` は今のアドレス（Address Claim で変わります）、`Node::requested_address()` は追加したときのアドレス（`NodeOptions::address`）です。

### 受信の振り分け

- 次のフレームは、無視して数えます: 11 ビットのフレーム、送信元 255 のフレーム、送信元 254（アドレスを持たないノード）からの Address Claimed と Request 以外のフレーム。
- 各ノードには、宛先が自分のアドレスかグローバルのフレームだけを渡します（他のアドレス宛ての PDU1 は渡しません）。

### ローカル折り返し

- 同じ `Network` のノードが送信したフレームは、ポートが受け付けた（`Accepted`）ものだけが、次のステップで他のノードに渡ります。
- 送信したノード自身には渡りません。
- 同じアドレスのノード同士も互いのフレームを受信します。

### ハンドラー（`on_message`、`on_any_message`）

- ハンドラーに渡す `Message` のデータは、呼び出しの間だけ有効です。
- ハンドラーの登録は、配送中のフレームが終わった時点で反映します（そのフレームでは呼ばれません）。
- 解除は、配送中でもその時点から反映され、そのフレームの残りでも呼ばれません（ハンドラーの関数オブジェクト自体は配送の終わりに破棄します）。
- 関数オブジェクトの破棄（キャプチャのデストラクター）の中から、ほかのハンドラーを解除・登録してもかまいません。

## 1 ステップの処理

### 受信フレームの処理順

`process()` は、ポートから受信したフレームと前のステップのローカル折り返しを、時刻順に処理します。同じ時刻のフレームは、次の順に取り出します（CAN の調停の近似）。

1. 送信元アドレスごとの列を作ります。列の中は到着順で、同じ時刻・同じアドレスでは外部のフレームが折り返しより先です。
2. 列の先頭の CAN ID が小さいものから 1 つずつ取ります。

そのため、同じ送信者の順序は保たれ、結果はポートの到着順とステップ幅によりません。ただし、同じアドレスを使う別の送信者（アドレスの衝突中）が同じ時刻に送信したフレームは 1 つの列に入り、その中は到着順です。

### タイマーの発火

タイマーは 2 種類です。

| 種類 | 発火するとき |
|---|---|
| タイムアウト | 期限より後の時刻のフレームを処理する直前か、ステップの最後で期限 < now のとき（期限と同じ時刻のフレームが先） |
| 予定（scheduled） | 期限 ≤ now の最初のステップ |

- どちらも、期限がフレームの時刻より前ならそのフレームの前に発火します。
- 同時に発火できるタイマー同士は（期限、開始の順）です。
- 期限がちょうど now のときは予定だけが発火し、同じ期限のタイムアウトは次のステップになります。
- タイムアウトの判定はステップ幅によりません。
- `next_deadline()` は最も早い期限を返します（タイムアウトは期限より後の最初のステップで発火します）。

タイマーの中で開始したタイマーの扱いは、期限で決まります。

| 開始したタイマーの期限 | 発火するとき |
|---|---|
| それを開始したタイマーの期限より後 | 同じ発火の機会に（期限、開始の順に）発火します。 |
| その期限と同じか前（同じ期限での始め直しなど） | 次の発火の機会（次のフレームの前か、ステップの最後。ステップの最後なら次のステップ）まで発火しません。 |

そのため、期限から始め直す周期は、周期がステップ幅より短くても、ステップの中ですべての期限の分だけ発火し、遅れがたまりません。実時間で長く止まった後は、遅れた分を 1 ステップで取り戻します。

### 送信の順序（`flush()`）

ハンドラー、Request の応答者、タイマーから送信したフレームは、そのステップの `flush()` でポートに渡します。`flush()` は次の順に渡します。

1. 制御フレーム（Address Claimed、Acknowledgement、トランスポートプロトコルの TP.CM）
2. データキュー
3. トランスポートプロトコルのデータパケット（TP.DT）

データキューと TP.DT は、合わせて 1 ステップの上限 `max_frames_per_step` までです。残りは次のステップで渡します。

| ポートの戻り値 | 扱い |
|---|---|
| `QueueFull` | そのフレームと後続を残して、次のステップで渡し直します（順序を保つ）。 |
| `Failed` | そのフレームを捨てて数え、後続は続けます。 |

## 送信

- `Node::send()` は 8 バイトまでなら単一フレーム、9〜1785 バイトならトランスポートプロトコル（下）です。
- 送信はステップの中（ハンドラー、応答者、タイマー、ホストのアプリの処理）だけです。ステップの外では `std::logic_error` です。
- `Node::request(pgn, destination)` は Request（3 バイト、優先度 6）を送信します。応答を待つ、時間切れで送信し直す、といった要求側の手順はエンジンではなくコンポーネント（`Requester`）にあります。

`Node::send()` は結果を戻り値で返します。戻り値は `Ok`、`QueueFull` と、次の 4 つです。

| 戻り値 | なるとき |
|---|---|
| `TooLong` | 1786 バイト以上 |
| `InvalidArgument` | 不正な PGN、優先度 8 以上、単一フレームの PDU2 を 1 つの宛先へ、宛先 254 |
| `NoAddress` | アドレスを失ったノード |
| `Busy` | 下の「トランスポートプロトコル」の「送信の種類と同時に送信できる数」 |

`Node::can_send_now()` は、送信したものがすぐ自分のアドレスから出るときに true です。

| ノードの状態 | `can_send_now()` |
|---|---|
| NAME なし、`Claimed`、待たない `Claiming` | true |
| 要求の後の待ちの間、最初の要求の前、アドレスがないとき | false |

値はアドレスか状態の変化（`on_address_change`）でだけ変わるので、自分で送信するコンポーネントはその通知で始めて止めます。

## Request と Acknowledgement

### 受信した Request の扱い

- 宛先が自分かグローバルの Request を処理します。
- 3 バイト未満の Request は無視して数え、3 バイトを超えるものは先頭 3 バイトを要求された PGN とします。
- 送信元 254 の Request には、Address Claimed（PGN 60928）の Request を除いて応答しません。
- Address Claimed の Request は Address Claim の手順で答え（下）、NACK も ACK もしません。NAME のないノードは答えません。
- 応答者がいなければ、宛先指定の Request に NACK を返し、グローバルの Request には何も返しません。要求元のアドレス要求（Address Claim）を見ているかどうかは条件にしません。

### 応答者（`on_request`、`on_any_request`）

応答者（`on_request(pgn, ...)`、`on_any_request(...)`）がいれば呼びます。PGN ごとの応答者が先で、同じ PGN に複数あれば先に登録したものです。応答者は `RequestContext` で、次のどちらかを呼びます。どちらも呼ばなければ何も送信しません。

| 呼ぶもの | すること |
|---|---|
| `respond(data)` | 要求された PG を送信します。PDU1 の PG を宛先指定の Request で求められたら要求元へ、それ以外はグローバルへ送信します。 |
| `acknowledge(code)` | 宛先指定の Request のときだけ Acknowledgement を送信します。グローバルの Request には送信しません。 |

- 9 バイト以上の `respond()` はトランスポートプロトコルで送信します（PDU2 の PGN でも、宛先指定の Request には要求元へ RTS/CTS。下の「トランスポートプロトコル」）。
- `acknowledge()` は、制御キューがあふれて捨てたときにも false を返します。

### 後で答える（`RequestContext::defer()`）

何ステップかかかる処理の後で答えるときは、`RequestContext::defer()` で要求を値（`PendingRequest`）として取っておき、後で `Node::respond(pending, data)` か `Node::acknowledge(pending, code)` で答えます。

- 宛先と送信の方法は `RequestContext` で答えたときと同じです。
- ステップの中だけで呼べます。
- その間にノードがアドレスを失うか変えると、応答は送信せず `NoAddress`（`acknowledge` は false）を返します（要求は前のアドレスへのものだったため）。
- 別のノードの要求を渡すと `std::invalid_argument` です。

### Acknowledgement のフレーム

- 送信するフレーム: 優先度 6、宛先グローバル、データは [制御バイト、0xFF、0xFF、0xFF、要求元のアドレス、要求された PGN（3 バイト、受信した値のまま）]。
- `parse_acknowledgement(message)` は、受信した Acknowledgement（PGN 59392、8 バイト以上）のフィールド（`Acknowledgement`: 制御バイト、グループ機能、指定されたアドレス、PGN）を返します（それ以外は空）。形式を知っているのはエンジンだけにし、コンポーネントは自分で解析しません。

### 規格との一致を確認していない点（Request と Acknowledgement）

- 要求された PGN が不正な値（PS が 0 でない PDU1、18 ビット超）のときの扱い（一致する応答者がないので宛先指定なら NACK）
- 拡張データページのビットが立ったフレームの扱い
- Acknowledgement の 2〜4 バイト目の値

## NAME と Address Claim

### NAME の形式（`Name`）

`Name` は 64 ビットの NAME です。フィールドは、下位ビットから次の順です。

| フィールド | ビット数 |
|---|---|
| Identity Number | 21 |
| Manufacturer Code | 11 |
| ECU Instance | 3 |
| Function Instance | 5 |
| Function | 8 |
| 予約 | 1 |
| Vehicle System | 7 |
| Vehicle System Instance | 4 |
| Industry Group | 3 |
| Arbitrary Address Capable | 1 |

- 値が小さいほど優先されます。最上位の Arbitrary Address Capable のビットが立った NAME は、立っていない NAME より常に低い優先度です。
- バス上では 8 バイトで、下位バイトが先です。
- 例とテストで使う Manufacturer Code `0x7F0` は仮の値です。実際の ECU には、その製造者に割り当てられた値を設定します。

### アドレスの要求と状態

- `NodeOptions::name` を指定したノードは、`address` を要求します。
- 任意アドレス可能（Arbitrary Address Capable）な NAME なら、`address` に 254 を指定でき、そのときは任意アドレスの範囲（下）の最初の空きを要求します。
- 状態は `Node::address_state()` で読めます（`NotStarted`、`Claiming`、`Claimed`、`CannotClaim`。NAME のないノードは `Fixed`）。
- 開始: ノードが加わった最初のステップで、そのステップのフレームを処理した後に、Address Claimed（優先度 6、宛先グローバル、データは NAME）を送信します。事前に Request for Address Claimed は送信しません。

### 要求の後の待ち

Address Claimed を送信したステップの時刻から 250 ms の間（`Claiming`）、そのノードが送信するもの（`send()`、`request()`、Request への応答、ACK/NACK）をノードの保留領域（`NetworkOptions::hold_capacity`、既定 16 件）に持ちます。待ちが明けたステップで、その時点のアドレスで送信します。

| 条件 | 起きること |
|---|---|
| 保留領域があふれた `send()` | `QueueFull` を返します。 |
| Address Claim の手順のフレーム（Address Claimed、Cannot Claim、Request for Address Claimed とその応答） | 待ちません。 |
| 任意アドレス不可で、アドレスが 0〜127 か 248〜253 のノード | 例外として待ちません（`Claiming` の間もすぐに送信します）。 |
| 待ちが明けたときにデータキューがあふれている | `send()` が `Ok` を返したメッセージでも捨てて数えます（`held_dropped`）。 |

待ちの終わりは予定のタイマーです。期限以後の時刻に競合する Address Claimed が届き、それが期限と同じステップで処理される場合は、ステップ幅によって、保留を送信してから負けるか、先に負けて保留を捨てるかが変わります（下の「Address Claim の制限」）。

### 競合

自分のアドレスで、他のノードの Address Claimed（8 バイト以上）を受信したら NAME を比べます。

| 自分の NAME | ノード | 起きること |
|---|---|---|
| 小さい | すべて | Address Claimed を送信し直します。 |
| 大きいか同じ | 任意アドレス可能で、空きがある | アドレスを失い、空いたアドレスを選んで要求し直します。 |
| 大きいか同じ | それ以外のノードと、空きのない任意アドレス可能なノード | アドレスを失い、`CannotClaim`（アドレス 254）になります。 |

勝ったときの Address Claimed は、同じ時刻の原因には 1 回だけ送信します。同じ時刻の要求は互いに届くためです。回数はフレームの時刻だけで決まり、ステップ幅によりません。原因は次のどれかです。

- 競合の Address Claimed
- アドレス違反
- 移った原因のフレームか Commanded Address
- 最初の要求（時刻は、そのステップの時刻）

アドレスを失うと、次のものを捨てて数えます。

- 保留中のメッセージ
- アドレスが変わる前に送信キューに入ったフレーム（元のアドレスに戻った後でも捨てます。Cannot Claim も含み、送信元 254 の Request だけは除きます）

任意アドレス可能なノードは、任意アドレスの範囲（`NetworkOptions::arbitrary_address_first`〜`arbitrary_address_last`、既定 128〜247）のうち、アドレス表にも同じ `Network` の他のノードにもない最小のアドレスを選びます。選んだらすぐに Address Claimed を送信して、待ちをやり直します（`Claiming`）。負けたアドレスは、勝った NAME が表に入るので選びません。

`CannotClaim` になったノードは、`cannot_claim_delay(name)` の後に Cannot Claim（送信元 254 の Address Claimed）を送信します。

- 遅延は 0〜153 ms（0.6 ms 刻み）で、NAME から決まる擬似乱数です（同じ NAME からは常に同じ値）。
- 起点は負けを知ったフレームの時刻です。
- 最初の要求で空きがなかったときは、そのステップの時刻です。

### Request for Address Claimed

宛先がグローバルか自分のアドレスの Request for Address Claimed には、状態ごとに次のように答えます。

| ノードの状態 | 応答 |
|---|---|
| `Claiming`、`Claimed` | Address Claimed（宛先グローバル）を要求の数だけ送信します。 |
| `CannotClaim` | 遅延の後に Cannot Claim を送信します（未送信の Cannot Claim があればまとめて 1 回）。 |

ノード自身が送信する Request for Address Claimed の扱いは次のとおりです。

- ノード自身が送信する Request for Address Claimed（グローバルか自分宛て）には、そのノードも答えます。
- 最初の要求の前のノードが送信する Request for Address Claimed は送信元 254 で出し、そのノード自身は答えません（要求はすぐ後に送信するため。ほかの送信は保留します）。
- アドレスを失ったノードが送信できるのは、Request for Address Claimed（送信元 254）だけです。

アドレスを失ったノードは、宛先指定のフレームを受信せず（グローバル宛てだけ）、Request for Address Claimed 以外の Request に応答しません。

### アドレス違反

`Claiming` か `Claimed` のノードは、他の送信者が自分のアドレスを送信元にしたフレームを受信したら、Address Claimed を送信し直します。

- 対象のフレームは、Address Claimed と Request for Address Claimed を除きます。8 バイト未満の Address Claimed は含みます。
- 送信し直すのは原因の時刻ごとに 1 回です（競合への応答と同じ規則）。
- 状態は変えません。
- そのフレームは普通に配送します。
- 数は `address_violations` です。
- NAME のないノードは検出しません。

### Commanded Address の受信

Commanded Address（PGN 65240。NAME 8 バイトと新しいアドレス 1 バイト）は、宛先がグローバルか自分のアドレスで、NAME が自分のものなら処理します。Commanded Address は 9 バイトなので、トランスポートプロトコル（BAM か RTS/CTS）で届きます。

| 条件 | 起きること |
|---|---|
| 任意アドレス可能なノード | 新しいアドレスへ移ります。 |
| 新しいアドレスが今のアドレスと同じ | Address Claimed を送信し直すだけです。 |
| 新しいアドレスに優先される NAME がいる | 競合で負けて、任意アドレスの範囲の空きへ移ります。 |
| 任意アドレス不可のノード、9 バイトでないもの、新しいアドレスが 254 か 255 のもの、最初の要求の前のノードへのもの | 無視して数えます（`commanded_addresses_ignored`）。 |
| 8 バイト未満のもの | NAME が分からないので数えません。 |

新しいアドレスへ移るときは、保留中のメッセージと元のアドレスのフレームを捨て、Address Claimed を送信して待ちをやり直します。`CannotClaim` のノードも移ります。予定の Cannot Claim は送信しません。

### アドレス表（`Network::address_table()`）

同じ `Network` のノード以外の制御機能について、アドレスと NAME の対応を持ちます（`name_at(address)`、`address_of(name)`、254 件固定）。受信した Address Claimed（8 バイト以上）で更新します。

| 受信したもの、起きたこと | 表の更新 |
|---|---|
| 同じ NAME が新しいアドレスを要求した | 古いアドレスの対応を外します。 |
| 自分のノードがアドレスを要求した | そのアドレスにいた優先度の低い NAME を外します。 |
| Cannot Claim を受信した | その NAME の対応を外します。 |
| 同じアドレスを複数の NAME が要求した | 優先される（小さい）NAME を残し、要求の届いた順によりません。 |
| 自分のノード（`Claiming` か `Claimed`）が持つアドレスへの要求で、その NAME が自分のノードの NAME より大きい（優先度が低く、負ける） | 入れません。 |
| ローカルのノードの Address Claimed（折り返し） | 更新しません。 |
| 8 バイト未満の Address Claimed | 要求として扱わず、数えます（`address_claims_malformed`）。 |

自分のノードの要求で優先度の低い NAME を外すのは、Address Claimed を送信キューに入れた時点です。そのため、それが送信できなかった場合も外れたままです。相手が要求し直せば入ります。

### 今の対応を調べる（`Network::address_of(name)`、`Network::name_at(address)`）

- 同じ `Network` のノード（`Claiming` か `Claimed`）とアドレス表の両方から調べます。
- 相手が同じプロセスのノードでも、ほかの participant でも同じに使えます。
- 受信した Address Claimed と Cannot Claim は、ノードのハンドラーが呼ばれる前に表へ入るので、そのハンドラーの中では新しい対応が見えます。
- 同じ `Network` のノードが相手のときは、そのノードの状態が変わった時点で変わります。

同じ `Network` の別のノードがそのアドレスを要求したときは、対応が変わるのが、相手のノードがその要求を処理した後、つまり自分のノードのハンドラーより後のことがあります。そのときは、相手のノードの Cannot Claim か新しいアドレスの Address Claimed（折り返し）で見えます。

### 状態の通知（`Node::on_address_change`）

`Node::on_address_change(handler)` は、アドレスか状態が変わるたびに `AddressChange`（新旧の状態とアドレス、原因の時刻）で呼ばれます。ハンドラーと同じく、ステップの中で呼ばれ、送信できます。登録と解除の規則もハンドラーと同じです。

### 規格との一致を確認していない点（Address Claim）

- 同じ NAME の別の送信者からの Address Claimed を負けとして扱うこと
- Cannot Claim の遅延の起点と擬似乱数の作り方
- 待ちの間の ACK/NACK を保留すること
- 任意アドレスの範囲と最小の空きを選ぶこと
- アドレス違反への応答の頻度（原因の時刻ごとに 1 回）と 8 バイト未満の Address Claimed を違反に含めること
- 任意アドレス不可のノードが Commanded Address を無視すること
- 同じアドレスの要求が重なったときにアドレス表に小さい NAME を残すこと（その NAME の制御機能がいなくなっていても、要求し直すまで残ります）

### Address Claim の制限

- 待ちの終わりは予定のタイマーなので、期限と同じステップの中で期限以後の時刻に届いた競合でも、保留を送信してから負けることがあります。このとき `on_address_change` の時刻は、Claimed の後に、それより前の時刻の CannotClaim になります。
- 同じアドレスの別の送信者が同じ時刻に送信したフレームの処理順（SIL Kit では決まらない）で、バスに出るフレームと結果は変わりませんが、`held_dropped` と `address_violations` の数は変わることがあります。
- Address Claimed は送信キューから出た時刻ではなく、入れたステップの時刻から待ちを数えます。
- 制御キューがあふれて Address Claimed を捨てた場合も、状態は進みます（`control_frames_dropped` で数えます）。
- `timer_capacity` は、要求するノード 1 つにつき 2 つ必要です（足りなければ `add_node()` が `std::invalid_argument`）。
- `CannotClaim` になった任意アドレス可能なノードは、後でアドレスが空いても自分からは要求し直しません（Commanded Address で移れます）。

### Address Claim にまだないもの

- ノードの削除
- バスオフの後の扱い
- 応答しない制御機能を表から外すこと

表から外れるのは、その NAME が別のアドレスを要求したとき、Cannot Claim を送信したとき、自分のノードがそのアドレスを要求して勝つときだけです。Commanded Address の送信はコンポーネント（`AddressCommander`）です。

## トランスポートプロトコル（J1939-21 の TP）

9〜1785 バイトのメッセージを、TP.CM（PGN 60416、`kPgnTransportControl`）と TP.DT（PGN 60160、`kPgnTransportData`）のフレームに分けて送信し、受信したものを組み立てます。

- 2 つの定数は `types.hpp` にあり、フレームを見る側（故障注入でパケットを欠落させる、記録するフレームを絞る）で使います。
- どちらのフレームも優先度 7 です。
- TP.CM と TP.DT のフレームはハンドラーに渡しません。組み立てたメッセージを、単一フレームと同じ経路（`on_message`、`on_any_message`、Request と Commanded Address の処理）で渡します。
- 組み立てたメッセージの `Message::time` は、転送が終わった時刻（最後のパケットの時刻）です。送信側が送信し始めた時刻ではないので、受信側が時刻から送信側の周期を測るときは、単一フレームのメッセージを使います。

### 送信の種類と同時に送信できる数

- 宛先がグローバルなら BAM、1 つのアドレスなら RTS/CTS です。
- PDU2 の PGN も、宛先を指定すれば RTS/CTS で送信します（単一フレームでは不正です）。
- `priority` は検査だけして使いません。
- 1 つのノードが同時に送信できるのは、BAM 1 本と、宛先ごとに RTS/CTS 1 本です。

| 条件 | `send()` の戻り値 |
|---|---|
| 実行中の転送と同じ種類の送信 | `Busy` |
| 送信セッションの空きがない（`bam_transmit_sessions`、`rts_transmit_sessions`、既定は各 4） | `QueueFull` |

`send()` の 9 バイト以上の送信は、既定では同じノードの転送が実行中だと `Busy` です。`WhenBusy::Queue` を指定すると、`respond()` と同じ応答待ち行列（容量を共有）で待ち、前の転送が終わってから始まります。複数のコンポーネントが同じノードから長いメッセージを送信するとき（DM1 の BAM と、識別情報の応答の BAM など）に、コンポーネントごとに再試行を書かないためです。

### 送信した転送の結果（`Node::on_transfer_end`）

結果は `Node::on_transfer_end(handler)` に `TransferEnd` で通知します。`TransferEnd` の内容は、PGN、宛先、長さ、結果、Abort の理由、原因の時刻、転送の識別子 `id`、データのパケットをすべて出したか `all_packets_sent` です。

`send()` と `RequestContext::respond()` が `Ok` を返した転送には、必ず 1 回だけ通知します（`Network` を止めたときに実行中だったものを除く）。

結果は `Completed`、`AbortedByPeer`、`Aborted`、`Cancelled` のどれかです。

| 結果 | なるとき |
|---|---|
| `Completed` | RTS/CTS は EndOfMsgACK を受信した、BAM は最後のパケットを出した |
| `AbortedByPeer` | 受信側が Connection Abort を送信した（理由は `TransferEnd` の `reason`） |
| `Aborted` | このノードが Abort を送信した |
| `Cancelled` | フレームを出さずに終えた |

- `Cancelled` になるのは、下のアドレスの変化と、まれに、Claim の後の待ちで保留した転送が、待ちが明けたときに制御キューに入らなかった場合です。
- BAM の `Completed` は、最後のパケットを出した次のステップで通知します。時刻は最後のパケットを出したステップの時刻です。その間にアドレスが変わっても `Completed` です。

転送の識別子の規則は次のとおりです。

- `send()`、`respond()`（`RequestContext` と `Node`）が転送を受け付けると、その直後の `Node::last_transfer_id()` がその転送の `TransferId` を返します（1 フレームの送信と、受け付けなかった呼び出しでは空）。
- ID は `Network` の中で一意です。
- 応答待ち行列で待った転送も、Claim の後の待ちで保留した転送も、受け付けたときの ID で終わります。
- 同じノードが同じ PGN と宛先の転送を重ねても、終わりを取り違えません。

`all_packets_sent` からは、次のことが分かります。

| `all_packets_sent` | 結果 | 分かること |
|---|---|---|
| false | どれでも | 受信側はメッセージを組み立てられていません（最後のパケットの前に終わった、始まらなかった）。 |
| true | 完了でない（EndOfMsgACK が来ない、その間にアドレスが変わった） | 受信側が受け取ったかは分かりません。 |

### 受信する転送の通知（`Node::on_incoming_transfer`）

受信する転送は `Node::on_incoming_transfer(handler)` に `IncomingTransfer` で通知します。`IncomingTransfer` の内容は、開始か終わり、ID、PGN、送信元、宛先、長さ、終わりの結果と理由、原因の時刻です。

| 転送 | 通知するノード |
|---|---|
| RTS/CTS | 受け入れた宛先のノードだけ |
| BAM | 送信側を除く、開始のときに参加していたすべてのノード（その後で追加したノードには、開始も終わりも通知しません） |

- 開始を通知した転送には、終わりを必ず 1 回通知します（`Network` が失敗するか破棄される前に限ります）。
- CTS を制御キューに入れられずに受け入れなかった RTS は、開始も終わりも通知しません。
- ID は送信する転送と同じ番号の列から振ります。
- ハンドラーの規則は `on_transfer_end` と同じで、ステップの中で呼ばれます。

終わりの結果は `Completed`、`AbortedByPeer`、`Aborted`、`Lost`、`Cancelled` のどれかです。

| 終わりの結果 | なるとき、起きること |
|---|---|
| `Completed` | 組み立てたメッセージを、この通知の直後に配送します。 |
| `Aborted` | このノードが Abort を送信した（時間切れなど） |
| `Lost` | BAM のパケットの欠落か時間切れ |
| `Cancelled` | アドレスの変化、同じ送信元の同じ転送のやり直し、CTS が送信できなかった |

### BAM の送信

- 告知を出したステップから `bam_packet_interval`（既定 50 ms、10〜200 ms）ごとに 1 パケットを出します。
- 間隔は前のフレームを出したステップの時刻から数えるので、ステップ幅で割り切れなければ切り上がります（短くはなりません）。
- BAM への Abort は受信しても無視します。

### RTS/CTS の送信

- RTS のバイト 5（1 回の CTS で送信できる最大のパケット数）は `rts_max_packets_per_cts`（既定 255 = 制限なし）です。
- CTS で求められたパケットを、CTS を受信したステップでまとめて出します。
- CTS の許可数が残りより多ければ最後のパケットまで出します。
- 0 個の CTS は保留（Hold）です。
- 全パケットを出す前の EndOfMsgACK、別の PGN の CTS・EndOfMsgACK・Abort は無視します。

送信側は、次のときに Abort を送信します。

| 条件 | Abort の理由 |
|---|---|
| CTS の次のパケット番号が 0、総数より大きい、最後に求められたウィンドウの先頭より前、出した最大の番号 + 1 より後 | 7 |
| 許可数が RTS のバイト 5 を超えた | 250 |
| 前のウィンドウのパケットを出し終える前に次の CTS が来た | 4 |
| T3 と T4 | 3 |

### Request への長い応答

`RequestContext::respond()` の 9 バイト以上の応答は、宛先指定の Request には要求元へ RTS/CTS、グローバルの Request には BAM で送信します。

- 同じノードの同じ種類の転送が実行中か、セッションの空きがなければ、ネットワークの応答待ち行列（`response_queue_capacity`、既定 8）に入れ、`flush()` の始めに入れた順に始めます。
- 待ち行列があふれたら `QueueFull` です。
- 順序は待ち行列の中だけで保ちます。同じノードの `send()` は、セッションが空いていれば待ち行列より先に始まります。

### BAM の受信

送信元ごとに 1 本です。

| 条件 | 起きること |
|---|---|
| 告知の宛先がグローバルで、9〜1785 バイト、パケット数がサイズと合い、PGN が正しい | 受信します。 |
| それ以外の告知 | 無視して数え、実行中の BAM には影響しません。 |
| 同じ送信元の新しい正しい告知 | 実行中の BAM を捨てて置き換えます。 |
| パケットの番号が期待と違う（欠落、重複、順序違い、0） | メッセージを捨てます（BAM は再送を求められないため。Abort は送信しません）。 |
| 受信のセッションが満杯（`bam_receive_sessions`、既定 8） | 新しい告知を無視して数えます。 |

- パケットの間隔の下限は検査しません。
- 送信元の Address Claim を見ていなくても受信します。

### RTS/CTS の受信

送信元と宛先の組ごとに 1 本です。宛先は、アドレスを持つ（`Claiming`、`Claimed`、NAME なしの固定）ローカルのノードです。グローバル宛ての RTS と、ローカルのノードがいない宛先の RTS は無視します。

RTS は、次のときに Abort で拒否します。

| 条件 | Abort の理由 |
|---|---|
| 1785 バイト超 | 9 |
| 9 バイト未満・パケット数の不一致・バイト 5 が 0・不正な PGN | 250 |
| 受信のセッションが満杯（`rts_receive_sessions`、既定 8） | 1 |
| 同じ送信元から別の PGN の RTS（実行中の転送は続けます） | 1 |

同じ PGN の RTS は、実行中の転送をフレームを出さずに捨てて、新しく始めます。

CTS の許可数は min(RTS のバイト 5, `cts_window`（既定 16）, 残り) です。ウィンドウを受信し終えたら次の CTS、全部受信したら EndOfMsgACK を送信してメッセージを渡します。

パケットは、番号とデータで次のように扱います。

| パケット | 扱い |
|---|---|
| 期待どおりの番号 | 受信します。 |
| 直前のパケットの重複、今のウィンドウの先頭より前の番号（前のウィンドウの遅れたパケット） | 無視します。 |
| それ以外（先の番号、0、ウィンドウの中の古い番号）、データが足りない（DLC が短い）パケット | 欠落として扱います。 |

- 欠落があると、ウィンドウの最後の番号のパケットが来たら、欠けた先頭から CTS で再送を求めます。欠落の後、再送の CTS までのパケットは捨てます。
- 再送の要求は、ウィンドウを受信し終えるまでに 2 回までで、3 回目が必要なときは Abort（理由 5）です。
- ウィンドウの最後のパケットが欠けたときは T1 で終わります。
- 受信側は保留（0 個の CTS）を送信しません。
- 送信元からの CTS と EndOfMsgACK は無視します。
- 送信元の Abort でフレームを出さずに終えます。

### 組み立てたメッセージ

- パケットの優先度は問いません。組み立てたメッセージの優先度は、RTS か BAM の告知の優先度です。時刻は最後のパケットの時刻です。
- 組み立てた Address Claimed（PGN 60928）と Request（PGN 59904）は、単一フレームの PG なので配送せずに数えて捨てます。Commanded Address など、ほかの PGN は単一フレームと同じ経路で渡します。

### トランスポートプロトコルのタイマー

タイムアウトはすべて Abort（理由 3）です。BAM の受信だけはフレームを出さずに捨てます。

| タイマー | 値 | 起点 |
|---|---|---|
| BAM の受信の T1 | 750 ms | 告知かパケットのフレームの時刻 |
| 受信側の T1（パケットの間） | 750 ms | そのセッションに届いた最後のパケット（無視したものも含む）のフレームの時刻 |
| 受信側の T2（CTS の後の最初のパケット） | 1250 ms | CTS を出したステップの時刻 |
| 送信側の T3（RTS かウィンドウの最後のパケットの後） | 1250 ms | それを出したステップの時刻 |
| 送信側の T4（保留の後） | 1050 ms | 保留の CTS のフレームの時刻（保留が続けば数え直す） |

- タイムアウトは期限より後の時刻で判定します（期限ちょうどのフレームは受け付けます）。判定はステップ幅によりません。
- 送信を起点とするタイマーは、フレームをポートに渡したステップの時刻から数えます（ポートが `Failed` を返した場合も同じ）。
- ポートの `QueueFull` で渡し直しが続けば、そのぶん遅れて数え始めます。

### アドレスの変化と転送

Claim の後の待ちの間に送信した転送は、セッションを確保して待ち、待ちが明けたとき保留したほかのメッセージと一緒に、保留した順に始めます。待ちの間に受信した RTS への CTS も、待ちが明けてから出します。

ノードがアドレスを失うか変えると、そのノードの送受信の転送と応答待ち行列の応答を、フレームを出さずに終えます（送信は `Cancelled`）。古いアドレスから Abort は出せないためです。

- キューに残っていた TP.CM も出しません。
- 最初の Claim では終えません。
- この通知（Claim の後の待ちで保留していた転送を含む）の時点で、ノードの `address()` と `address_state()` は変化の後のもので、`on_address_change` はその後に呼ばれます。
- `on_transfer_end` のハンドラーがその通知の中で送信し直した転送は、同じアドレスの変化では終えません（新しいアドレスと状態で扱います）。

アドレス表で、あるアドレスの NAME が外れるか別の NAME に替わると、次のものをフレームを出さずに終えます（時刻は原因の Address Claimed のフレームの時刻）。

- そのアドレスとの RTS/CTS の転送
- その送信元の BAM の受信
- そのアドレスへの応答待ち行列の応答

アドレス表にない相手（Address Claim を見ていない相手）と、同じ Network のノード（アドレス表に入らない）は対象外です。同じ Network のノード同士の転送では、相手のノードのアドレスが変わっても、こちらのセッションはタイムアウトで終わります。

終わったか置き換わったセッションの TP.CM がキューに残っていれば、出さずに捨てて数えます（`transport_stale_dropped`）。

### 規格との一致を確認していない点（トランスポートプロトコル）

- 送信側が T3・T4 で Abort（理由 3）を送信すること
- 再送の要求の回数（ウィンドウごとに 2 回）と、欠落の後のパケットを捨ててウィンドウの最後で再送を求めること
- 直前のパケットの重複を無視して古い番号を欠落とすること
- DLC が短いパケットの扱い
- RTS を拒否する理由の選び方（9 バイト未満・バイト 5 が 0・不正な PGN に 250、セッションの満杯に 1）
- CTS の次のパケット番号の有効範囲
- 許可数が RTS のバイト 5 を超えたときの理由 250
- 同じ送信元の新しい BAM で置き換えること
- BAM の告知の検査（8 バイト以下を無視）
- Abort のバイト 3〜5 を 0xFF にすること
- 組み立てたメッセージの優先度と時刻

### トランスポートプロトコルの制限

- 停止したときに実行中の転送は、フレームを出さずに捨てます（Abort を送信してから止める仕組みはありません）。
- 受信側は保留を送信しません。
- 対応する PGN を登録して RTS や BAM を拒否する仕組みはありません。
- ETP（1785 バイト超）はありません。
- 送信を起点とするタイマーと BAM の間隔は、ポートに渡したステップの時刻から数えます。バスの混雑で実際の送信が遅れると、そのぶん早く数え始め、BAM のバス上の間隔は縮むことがあります。
- 同じ Network のノードどうしの転送も、ローカル折り返し（次のステップに渡る）で同じ手順で進みます（アドレスが変わったときの違いは上）。
- `next_deadline()` は、CTS で求められたパケットなど、タイマーを持たない次の flush の仕事を含みません。
- 再送を求めた後に、前のウィンドウの遅れたパケットのうち、再送のウィンドウの中の番号のもの（例: 5 が欠けて 5〜16 を求めた後に届いた元の 10）は欠落として扱うので、再送の要求をもう 1 回使うことがあります（回復はします。ウィンドウの先頭より前の番号は無視します）。

## ほかの ECU の転送を追う（`TransferSniffer`）

`TransferSniffer`（ヘッダー `vehicle_sil/j1939/transfer_sniffer.hpp`）は、バスのフレームを順に受け取り、ほかの ECU どうしの転送（RTS/CTS、設定で BAM も）がどう終わったかを知らせます。完了した転送は、組み上がったメッセージも渡します。聞くだけで、フレームを送信しません。タイマーを持たず、時計も読みません。時刻は、渡されたフレームの時刻と `advance(now)` だけで進みます。

- `Network` に依りません（使うのは `types.hpp` の値の型だけ）。生の CAN のフレーム（`can::RawChannel` の `can::TimedFrame`）をそのまま `feed()` に渡せます。29 ビットのフレームだけを読みます。
- フレームは時刻の小さい順に渡します（並べ直しません）。`advance(now)` をステップごとに呼ぶと、バスが静かなときも、止まった転送が時刻どおりに片づきます。結果（どの転送がどう終わるか、`time`）はフレームとその時刻だけで決まり、`advance()` を呼ぶ時点によりません。変わるのは `noticed` だけです。
- 生成のときに `sessions` × 1785 バイトを確保し、その後は確保しません。スレッド安全ではありません。1 つのスレッド（ステップ）から使います。
- `on_transfer` のハンドラーは、転送が終わるたびに `feed()` か `advance()` の中から呼ばれます。ハンドラーの中から、その `TransferSniffer` の `feed()`、`advance()`、`on_transfer()` を呼ぶと `std::logic_error` です。`data` は呼び出しの間だけ有効です。
- `end_transfers_of(address, time)` は、送り手か宛先が `address` の転送を全部 `Lost`（`time` は渡した時刻）で終えて知らせ、終えた数を返します。覚えていた別の PGN の告知も捨てます。そのアドレスのフレームをもう渡さないと決めたときに呼びます（`Listener` は、同じ `Network` のノードがそのアドレスを取ったときに呼びます。生の CAN から使う人は、Address Claimed を自分で見て、持ち主が代わったときに呼べます）。先に時刻を `time` まで進めるので、それより前に時間切れになっていた転送は `TimedOut` です。ハンドラーの中からは `std::logic_error` です。統計の `lost` は、BAM の乱れとこの関数で終えた転送の合計です。
- ハンドラーが例外を投げても、`feed()`、`advance()`、`end_transfers_of()` は仕事を最後まで済ませてから（渡したフレームの処理、その時刻までに終わる転送の通知）、その例外を投げ直します。複数の呼び出しが投げたら、最初の 1 つです。次の呼び出しに持ち越すものはないので、同じフレームをもう一度渡しません。

**規格と照らしていません。** 下の決まりは、このリポジトリのエンジンの受信側に合わせたものです。ほかのスタックで違いうる所は、`SnifferOptions` で変えられます。

### 転送の終わり方（`SniffEnd`）

終わり方（`SniffEnd`）と時刻（`SniffedTransfer::time`。条件に使うのはこの時刻です）:

| 終わり方 | いつ | `time` |
|---|---|---|
| `Completed` | 全部のパケットを見て、受け手が EndOfMsgACK を返した（`delivery` が `WhenAllPacketsSeen` なら、全部のパケットを見た時点）。BAM は最後のパケット | 受け手がメッセージを持った時点のパケットの時刻 |
| `Refused` | 完了したが、TP で運ばない PGN（Request、Address Claimed）だった。メッセージは渡さない | `Completed` と同じ |
| `Incomplete` | 受け手は EndOfMsgACK を返したが、盗み聞きの側がパケットを見逃していた | EndOfMsgACK の時刻 |
| `AbortedBySender`、`AbortedByReceiver` | Connection Abort（`reason` は理由のバイト） | Abort の時刻 |
| `Replaced` | 送り手が、終わる前に次を告知した（別の PGN の告知は、受け手がそれに CTS を返したとき） | 告知の時刻 |
| `Lost` | BAM のパケットが欠けた、重なった、順が違った。または、`end_transfers_of()` で終えた | そのパケットの時刻（`end_transfers_of()` は渡した時刻） |
| `TimedOut` | 転送のフレームが来なくなった | 最後のフレームの時刻 + `timeout`（BAM は `broadcast_timeout`）。猶予は含まない |

`started` は告知（RTS、BAM）の時刻、`noticed` は盗み聞きが知らせた時点の時刻（聞き手のステップ幅と、ほかのフレームに左右されます）です。

### エンジンの受け手と同じメッセージ

**`conflicting_packets` が 0 で完了したメッセージは、エンジンの受信側のノードが受け取るメッセージと同じです**（公開の約束）。同じフレームの列に対して、`SniffedTransfer::message()` の PGN、優先度（告知のフレームのもの）、送信元、宛先、時刻、バイト列が、受け手のノードのハンドラーに渡る `Message` と一致します。ノードのハンドラー用に書いた読み手を、そのまま使えます。`SniffedTransfer::conflicting_packets` は、その転送で、同じ番号なのに中身の違うパケットを見た数です。0 でなければ、受け手がどちらを取ったかはバスからは分からず、渡すバイト列（先に見たほう）は受け手のものと違うことがあります。

- 時刻は、受け手が求めた最後のパケットの時刻です。再送があると、欠けを埋めたパケットより後になります（受け手は、欠けた番号からウィンドウの終わりまでを求め直すため）。CTS は、この時刻を決めるためだけに読みます（CTS と同じ時刻のパケットは、その CTS への答えとして数えます）。
- `WhenAllPacketsSeen` では、時刻は最後の欠けを埋めたパケットの時刻で、受け手のメッセージの時刻より早いことがあります。その転送の後続のフレーム（EndOfMsgACK、重なったパケット）は `orphan_control`、`orphan_data` に数えます。

### 決まり

- 転送は、送り手と受け手の組で見分けます（BAM は送り手）。RTS の形の検査、TP で運ばない PGN の判定、制御バイト、時間切れの既定値は、エンジンと同じもの（内部ヘッダー `src/transport_wire.hpp`）を使います。形の合わない告知は `announcements_malformed` に数えて追いません。
- TP.DT は番号の位置に入れます。順は問いません。同じ番号をもう一度見たら、先に入れたものを残します（`repeated_packets`。中身が違えば `conflicting_packets` にも）。番号 0、最後より大きい番号、短すぎるパケットは `bad_packets` です。BAM は順番どおりだけを受け、そうでなければ `Lost` です。
- 同じ組の新しい RTS:
  - 同じ PGN なら置き換えます（前のものは `Replaced`。形の合わない RTS でも前のものは終わります）。
  - 別の PGN なら、既定（`other_group = KeepRunning`）では無視して `announcements_ignored` に数え、走っている転送を続けます（エンジンの受信側が、新しいほうを断るため）。
  - 無視した告知は、受け手が断る（その PGN の Abort）まで覚えておき、受け手が断らずに答えたら、その転送に乗り換えます。
  - 受け手がその PGN に CTS を返したら、走っていた転送を `Replaced`（時刻は告知の時刻。受け手が EndOfMsgACK を返した後なら `Incomplete`）で終え、告知の転送を始めます。受け手にとって前の転送がフレームなしに終わっていた場面です（送り手のアドレスの持ち主が変わり、新しい持ち主が告知した、など）。
  - 受け手が走っている転送を EndOfMsgACK か Abort で終えたときも、断られていない告知が残っていれば、そこから告知の転送を始めます（告知が `timeout + grace` より古ければ始めません）。送り手が最後のパケットの直後に別の PGN を告知した場面です。
  - 走っている転送が `TimedOut` で終わったときも、受け手が断っていない告知が残っていれば、告知の転送を始めます。受け手が前の転送をフレームなしに終えていて、告知への答えが時間切れの直後に来ることがあるためです。告知にだれも答えなければ、その転送も `TimedOut` で終わります（だれも答えない RTS と同じです）。
  - 覚えておいた告知から始めた転送の時間は、その告知の時刻から数えます。始める時点で告知が `timeout + grace` より古ければ、その転送はすぐ `TimedOut` で終わります。
  - 告知を無視した転送は、その PGN の EndOfMsgACK でしか完了しません（`WhenAllPacketsSeen` でも。無視した告知のパケットで欠けが埋まり、別のメッセージの中身を渡すことを防ぐため）。
  - `Replace` にすると、別の PGN の RTS でも置き換えます。
- 時間切れは「経過が値より大きい」で判定します（ちょうどの時刻のフレームは、まだその転送のものです）。接続（RTS/CTS）を `TimedOut` にするのは、経過が `timeout + grace` を超えてからです。あきらめた ECU は自分の時間切れの後に Abort を送信するので、その Abort で `AbortedBySender` か `AbortedByReceiver` として終えるためです。猶予（既定 250 ms）は、Abort が遅れる幅（送り手のステップ幅、送信確認の遅れ）を覆う値にします。ステップ幅が数十 ms を超える構成では伸ばします。猶予より後に届いた Abort は、相手のいないフレームです（`orphan_control`）。BAM に猶予はありません。
- どのフレームでも（TP 以外でも）時刻が進み、止まった転送は、新しい告知が空きを探す前に片づきます。空きがなければ `no_session` に数えて追いません。
- パケットが欠けたまま EndOfMsgACK を見たときは、すぐには決めません。時刻が進んだ時点（後の時刻のフレームか `advance()`）で、そろっていれば `Completed`、欠けていれば `Incomplete` です。同じ時刻のフレームは、どちらの順でも届きうるためです。
- Abort は、PGN の合う転送を、Abort の送り元が受け手である転送から先に探します。
- 相手のいない TP.DT と制御フレーム（CTS、EndOfMsgACK、Abort）は `orphan_data`、`orphan_control` に数えて捨てます。増えるのは、転送の途中から聞き始めたとき、終わった転送の残りが届いたとき（猶予より後に届いた Abort を含む）、追わなかった告知の転送のフレームが届いたとき（空きがなく `no_session` に数えた告知、形の合わない告知を受け手が断る Abort）です。`broadcasts` が切のときの BAM と、宛先がグローバルの TP.DT は、読まず、数えません。

### 設定（`SnifferOptions`）

既定はエンジンの値で、規格とは照らしていません。

| 項目 | 既定 | 意味 |
|---|---|---|
| `sessions` | 32 | 同時に追う転送の数（接続と BAM の合計） |
| `timeout` | 1250 ms | 接続のフレームが来ない時間の上限 |
| `grace` | 250 ms | 接続を `TimedOut` にする前に、Abort を待つ時間 |
| `broadcast_timeout` | 750 ms | BAM のパケットが来ない時間の上限 |
| `delivery` | `WhenAcknowledged` | 接続を完了とする時点 |
| `other_group` | `KeepRunning` | 走っている転送と別の PGN の RTS の扱い |
| `broadcasts` | false | BAM も追う。`Network` は BAM を自分で組み立ててハンドラーに渡すので、生の CAN から使うときに入れる。切の間、BAM のフレームは統計にも数えない |

### 統計（`SnifferStatistics`）

項目名は変えません（道具の表示や、シナリオの変数の名前に使うため）: `started`、終わり方ごとの `completed`、`incomplete`、`aborted_by_sender`、`aborted_by_receiver`、`replaced`、`lost`、`timed_out`、`refused`、追わなかった告知の `announcements_malformed`、`announcements_ignored`、`no_session`、相手のいないフレームの `orphan_data`、`orphan_control`、パケットの `bad_packets`、`repeated_packets`、`conflicting_packets`、再送の要求の `retransmit_requests`。

### バスの上からは見分けられないこと

- `WhenAcknowledged` では、受け手がメッセージを持ってから EndOfMsgACK がバスに出るまでの間、盗み聞きはまだ「途中」と見ています。この間に送り手が同じ PGN を告知し直すか Abort を送信すると、受け手とは違う結果になります（告知は前を `Replaced` にし、その後の EndOfMsgACK は次の転送のものと読みます。Abort は `AbortedBySender` ですが、受け手はメッセージを受け取っています）。別の PGN の告知は、上の決まりで追えます。ふつうの送り手は EndOfMsgACK を待つので、起きるのは壊れた送り手か、順の崩れるブリッジ越しです。
- 受け手がフレームを出さずに転送を終えたこと（アドレスの持ち主が変わったとき）は、バスに出ません。その転送は、次の告知に受け手が答えた時点で `Replaced`、答えがないか、告知が時間切れの後なら `TimedOut` です（エンジンの受け手は Address Claimed の時刻に終えています）。Address Claimed は読みません。
- 前の転送の遅れたパケットが、同じ送り手の次の転送の間に届くと、次の転送のパケットとして入ります。後から正しいパケットが届いても先のものを残すので、`Completed` で渡すバイト列が、受け手の組み立てたものと違うことがあります（エンジンの受け手は、CTS を出す前のパケットを捨てます）。その転送は `conflicting_packets` が 0 でないので見分けられます。遅れたパケットの中身がたまたま同じ場合と、正しいパケットが届かなかった番号を埋めた場合は見分けられません。
- 両方が同時に Abort を送信すると、バスで先のものを終わりとし、後のものは `orphan_control` です。
- 生の CAN から使うときは、同じ時刻のフレームの順は届いた順です。

### 規格との一致を確認していない点（`TransferSniffer`）

- 上の決まり全部と時間切れの値
- とくに、同じ 2 つの ECU が同じ PGN を互いに同時に送信しているときに Abort がどちらを終えるか（ここでは片方だけ）
- EndOfMsgACK の大きさとパケット数が告知と違うときの扱い（ここでは見ません）
- 別の PGN の RTS を受け手がどう扱うか

エンジンの時間切れ（T1〜T4）は定数で、変えられるのは盗み聞きの値だけです。

## ほかの participant が言ったことを聞く（`Listener`）

`Listener`（ヘッダー `vehicle_sil/j1939/listener.hpp`）は、1 つの `Network` に付けて、ほかの participant が送信したメッセージとフレームをハンドラーに渡します。宛先が誰でも渡します。聞くだけで、送信もアドレスの主張も応答もしません。使い方は [../j1939-guide.md](../j1939-guide.md) の「受信だけをする participant」にあります。

### 渡すもの

| 口 | 渡すもの | 出どころ |
|---|---|---|
| `on_message(pgn, …)`、`on_any_message(…)` | 単一フレームのメッセージ、BAM のメッセージ、その `Network` のノード宛ての接続のメッセージ | `Network` が受けて組み立てたもの（聞き役の席の `on_message`） |
| 同上 | ほかの ECU どうしの接続（RTS/CTS）のメッセージ | `Listener` が持つ `TransferSniffer` が、フレームから組み立てたもの |
| `on_transfer(…)` | ほかの ECU どうしの接続の終わり（`SniffedTransfer`）。メッセージを渡さなかったものも | `TransferSniffer` |
| `on_frame(…)` | `Network` が受け取ったフレーム（`ReceivedFrame`。TP.CM、TP.DT、ほかのアドレス宛てを含む） | 聞き役の席の `on_frame` |

- **同じメッセージは 1 回だけ渡します。** BAM は `Network` が組み立てるので、盗み聞きには追わせません（`ListenerOptions::sniffer.broadcasts` は読まずに切ります）。ノード宛ての接続は `Network` が組み立てるので、「同じ `Network` のノード」の判定で盗み聞きに回しません。
- **盗み聞きした接続のメッセージは、`conflicting_packets` が 0 なら、エンジンの受信側のノードが受け取る `Message` と同じです**（「ほかの ECU の転送を追う（`TransferSniffer`）」の約束）。ハンドラーの型はノードと同じ `Message` です。0 でないメッセージも渡します。`Message` には印がないので、見分けるのは、同じ転送について直後に呼ばれる `on_transfer` の `SniffedTransfer::conflicting_packets` か、統計の `conflicting_packets`（0 のままなら全部同じ）です。
- 制限: `delivery` が `WhenAllPacketsSeen` のとき、受け手が捨てた転送のメッセージを渡すことがあります。エンジンの受け手は、送り手のアドレスを別の NAME が主張すると（Address Claimed）その転送を取り消しますが、盗み聞きは Address Claimed を読まないので、パケットがそろえば完了にします。既定の `WhenAcknowledged` では、受け手の EndOfMsgACK が来ないので渡りません。

### 同じ `Network` のノード

- **同じ `Network` のノードが送信したものは渡しません**（メッセージもフレームも）。折り返し（席の `local`）はノードが 2 つ以上のときにしか起きないので、渡すと、ノードを 1 つ追加しただけで聞こえるものが変わるためです。`ListenerOptions::hear_local` を入れると、折り返したフレーム（`ReceivedFrame::local` が立ちます）とメッセージも渡します。ノードが 1 つの `Network` では、入れても何も増えません。自分のノードの送信は、送信した側の口（`Node::on_transfer_end`、`Requester` の結果）で数えます。折り返したフレームは、`hear_local` によらず盗み聞きには渡しません（時刻も進めません）。そのため、`hear_local` を入れても、ノードからほかの participant 宛ての接続（RTS/CTS）はフレームだけが渡り、メッセージはどこからも渡りません（`Network` は宛先が自分のノードのものしか組み立てません）。
- **ローカルのアドレスの判定はフレームごと**: フレームの送り元か宛先が、その `Network` のノードが使っているアドレス（NAME のないノードのアドレス、主張の途中か主張を終えたノードのアドレス。エンジンが RTS を受け入れる条件と同じ）なら、そのフレームは盗み聞きに渡しません。その会話は `Network` のものです。まだ主張を始めていないノードと、アドレスを失ったノードのアドレスは、ほかの ECU のものとして追います。判定はフレームを `Network` が扱う前の状態でします（Address Claimed で負けるフレームそのものは、負ける前のアドレスで判定します）。
- 盗み聞きに渡さなかったフレームのアドレスに、追っている転送が残っていれば（ほかの ECU どうしの転送の途中で、ノードがそのアドレスを取った）、その場で `Lost` で終えます（`time` はそのフレームの時刻。`TransferSniffer::end_transfers_of()`）。ほかの participant の Address Claimed では終えません（持ち主が代わった後の転送は、盗み聞きの決まりで追えます）。

### 順と時刻

- **1 つのフレームについての順**: まず `on_frame` のハンドラー。次に、そのフレームの時刻かアドレスで終わりが決まった**ほかの転送**（`TimedOut`、`Incomplete`、`Lost`）の `on_transfer`。その後に、そのフレーム自身がもたらすもの: 盗み聞きした接続がそのフレームで `Completed` になるなら、そのメッセージ、続けてその `on_transfer`（Abort などほかの終わり方は `on_transfer` だけ）。単一フレームと、`Network` がそのフレームで組み立てたメッセージは、メッセージのハンドラーへ。つまり、ほかの転送の終わりが、それに気づくきっかけになったフレームのメッセージより先に知らされることがあります（前後は `time` で比べます）。同じメッセージについては、`Observer`、`Listener`、ノードのハンドラーの順です。同じ種類のハンドラーは登録の順で、`on_message` と `on_any_message` は 1 本の列です（`Node` と同じ）。
- **時刻**: 盗み聞きした接続のメッセージは、既定（`SniffDelivery::WhenAcknowledged`）では EndOfMsgACK のフレームで渡しますが、`Message::time` は受け手がメッセージを持った時点のパケットの時刻です。そのため、後の時刻のメッセージの後に渡ることがあります。フレームから決めたこと（メッセージ、Abort）は、聞く participant のステップ幅によりません。時間の経過から決めたこと（`TimedOut`、欠けのある EndOfMsgACK の `Incomplete`）は、ステップの受信を扱い終えた時点（席の `on_step_end`。`Listener` がここで盗み聞きの `advance(now)` を呼びます）で、その時刻のタイマーより先に渡します。その `time` はステップ幅によりませんが、渡るステップは変わります。前後は `time` で比べます。

### ハンドラーと寿命

- **読み取り専用**: ハンドラーは聞き役の席の中で動くので、席の決まりがそのまま当たります（「聞き役の席（内部の口）」）。ハンドラーからの送信などは `std::logic_error` で `Network` を失敗させ、例外を握りつぶしてもステップは止まります。盗み聞き経由で呼ばれるハンドラー（接続のメッセージ、`on_transfer`）の例外は、盗み聞きがそのフレームの処理を終えてから外に出るので、転送が中途半端な状態で残ることはありません。`Listener` 自身のハンドラーの中からのハンドラーの登録は `std::logic_error`（「… was called from a handler of this Listener. Register the handlers before the simulation starts (outside a step); a handler only reads what it is given」）で、これも握りつぶしてもステップが止まります。
- **1 つの `Network` に 1 つ**: 2 つ目は `std::logic_error`（「this Network already has a Listener (a Network has one); add the handlers to that Listener」）。見張りのコードは `Listener&` を受け取ってハンドラーを追加します。生成と破棄はステップの外でします。破棄はノードのハンドラーの中からもできますが、`Listener` 自身のハンドラーの中からはできません。`Network` より先でも後でも破棄できます。
- **ハンドラーの解除**: 登録の関数は `Listener::HandlerId` を返します。`Listener::remove_handler(id)` か、それを持つ `ListenerSubscription`（破棄か `reset()` で外す。`Node` のハンドラーの `Subscription` と同じ形）で外します。
  - 外したハンドラーは以後呼ばれません。ステップの中でも、`Listener` のハンドラーの中（そのハンドラー自身でも、ほかのハンドラーでも）からでも外せ、そのフレームの残りでも呼ばれません。
  - ハンドラーのオブジェクトは、`Listener` がそのフレーム、メッセージ、ステップの終わりの処理を終えた所で破棄します（走っているハンドラーは最後まで動けます）。そのため、`Listener` のハンドラーの中から外したハンドラーは聞き役の席の中で壊れ、そこで `Node` の `Subscription` や `Timer` を壊すと `Network` が失敗します。そうしたハンドラーには（捕まえたものを通じても）それらを持たせず、ハンドラーの外で壊します。
  - `ListenerSubscription` は、`Listener` が先に壊れた後は何もしません（`Network` の有無によりません）。戻り値を捨てた登録は、`Listener` が壊れるまで残ります。
  - 追加したハンドラーと、それが捕まえたものは、外すか `Listener` を壊すまで生きていなければなりません。
  - `Node` の `Subscription` との違い: `Listener` のハンドラーの中で `Node` の `Subscription` を外すと `Network` が失敗します（席の決まり）が、`ListenerSubscription` は `Network` に触らないので外せます。ハンドラーの中からの**登録**は、どちらも誤りです。
- 生成のときに `sniffer.sessions` × 1785 バイトを確保し、ステップの中では確保しません（解除も確保しません）。スレッド安全ではありません（`Network` を回すスレッドから使います）。

### 聞こえないもの

- `Network` が無視するフレーム（`frames_ignored`。11 ビットのフレーム、送り元が 255 のフレーム、送り元が 254 で Address Claimed と Request 以外のフレーム、形の正しくないフレーム）と、`Network` が受け取らなかったフレーム（`receive_capacity` を超えた分は `receive_overflows`）、`Network` に空きのセッションがなくて組み立てなかった BAM と、同じ理由でノードが断った RTS（どちらも `transport_rejected`）、盗み聞きが追えなかった接続（`sniffer_statistics()` の `no_session`、`incomplete`、`replaced`、`lost`）。
- `vehicle_sil::spy::Spy` は、このうち `frames_ignored` 以外の数と、`conflicting_packets`、組み立ての途中で捨てた BAM（`transport_bam_dropped`）を変数に書きます（[../j1939-guide.md](../j1939-guide.md) の「受信だけをする participant」）。
- 前のステップの時刻より古い時刻のフレーム: `Network::receive()` は「ステップの時刻より前」だけを確認するので、席には来えます。盗み聞きは、そのフレームをその時刻のものとして扱い、進めた時刻は戻しません（時間切れの判定は、前より後の時刻でだけ動きます）。SIL Kit のポートは、時刻のないフレーム（時刻同期なしの participant のもの）に届いたステップの時刻を付けるので、これは前のステップの時刻より古くなりません。

### 規格との一致を確認していない点（`Listener`）

接続を追う決まりと値（`TransferSniffer` の節）。エンジンどうしの転送を横から聞いた結果が受け手と一致することはテストしていますが、ほかのスタックの受け手、ブリッジ越しの並びでは確認していません。

## ツールキット（`Subscription`、`Timer`、`Node::attach`）

コンポーネントとアプリが安全に書けるようにするための、プロトコルに依らない 3 つの仕組みです（ヘッダー `vehicle_sil/j1939/toolbox.hpp` と `network.hpp`）。

### 登録の解除（`Subscription`）

`Subscription{node, node.on_message(...)}` は、ハンドラーや応答者の登録（`HandlerId`）を持ち、破棄か `reset()` で解除します。

- 解除の後は、配送の途中でも（自分のハンドラーの中でも、別のハンドラーの中でも）呼ばれません。
- ムーブできます。
- `Network` の破棄の後に破棄しても安全です（何もしません）。

### 仮想時間のタイマー（`Timer`）

`Timer(node_or_network, kind, callback)` は、仮想時間のタイマーです。OS の時計やスレッドは使いません。実時間で動かすときは、ドライバーが `next_deadline()` まで眠ってからステップを実行します。

枠の予約は次のとおりです。

- 生成時に `timer_capacity` の枠を 1 つ予約し、破棄で返します。
- 残りの枠は `Network::timers_free()` で分かります。
- 残りの枠は、`timer_capacity` から、NAME を持つノードの 2 つずつと、今ある `Timer` の 1 つずつを引いた数です。トランスポートプロトコルのセッションのタイマーは別枠で、数えません。

開始と発火は次のとおりです。

- `start_at(t)` と `start_after(d)` は動いているタイマーを始め直します。
- ハンドラー、応答者、タイマーの中、アプリの処理、ステップの外のどこからでも呼べます。
- 過ぎた期限も受け付け、次の機会（次のフレームの前かステップの最後、なければ次のステップ）に発火します。
- 発火の中で始めたタイマーは、それを始めたタイマーの期限より後の期限のときだけ、同じ回で発火します（「1 ステップの処理」）。
- コールバックの中で、自分自身を含むタイマーを始め直し、取り消し、破棄できます。
- `Network` の破棄の後の破棄は安全で、`start_at()` は `std::logic_error` です。

`start_after(d)` の起点は、処理中のイベントの時刻（`Network::event_time()`）です。

| 呼ぶ場所 | 起点の時刻 |
|---|---|
| ハンドラー（応答者を含む） | 受信したメッセージの時刻 |
| アドレスの変化と転送の終わりの通知 | その原因の時刻（`AddressChange::time`、`TransferEnd::time`） |
| `Timer` のコールバック | その期限 |
| それ以外 | ステップの時刻（最初のステップの前は 0） |

- コンポーネントが時間の間隔を数えるときもこの時刻を使うと、結果がステップ幅によりません。
- コールバックの中で `start_after()` で始め直す周期は、ステップ幅によらず期限がずれず、発火の回数も変わりません。発火はステップ幅の分だけ遅れることがあります。周期がステップ幅より短いと、1 ステップに何回も発火します。
- メッセージを送信した時刻から数える間隔（応答の待ち時間など）は、送信がそのステップの `flush()` で出るので、`start_at(*network.now() + d)` で数えます。

### コンポーネントの所有（`Node::attach`）

`node.attach<T>(args...)` は、コンポーネント `T(node, args...)` を作り、`Network` に所有させます。

- `node.find<T>()` は、そのノードに最初に付けた `T` を返します（なければ nullptr）。
- どこからでも呼べます（ハンドラーの中で付けたコンポーネントのハンドラーは、次の配送から呼ばれます）。
- コンポーネントは `attach` を使わず、アプリが所有してもかまいません（`Network` より先に破棄します）。

アプリが所有するコンポーネントは、ネットワークのスレッドのどこで破棄してもかまいません。対象は、ライブラリのコンポーネントと、`Subscription` と `Timer` で作ったコンポーネントです。

| 破棄する場所 | 扱い |
|---|---|
| ハンドラー、応答者、タイマーのコールバックの中（同じノードのものでも、ほかのノードのものでも） | 破棄できます。その後は、同じ配送の残りでも、そのコンポーネントの `Subscription` のハンドラーは呼ばれず、そのコンポーネントの `Timer` は発火しません。 |
| コンポーネントが呼ぶ利用者の関数の中（`PeriodicSender` の Encoder、`Monitor` の `accept`、`on_state`、`on_message`、`Exchange` の照合とコールバック） | 破棄できます。 |
| `AddressCommander` のコールバックと `Diagnostics` の `on_clear` の中 | 例外で、破棄できません（呼んだ後も同じコンポーネントの処理が続くため）。 |
| `Observer` の中 | 破棄できません。 |

利用者の関数の中で破棄できるコンポーネントは、呼ぶ関数オブジェクト（と Encoder に渡すバッファ）を呼び出しの間だけ手元に移し、破棄されたことをフラグで知り、その後は自分自身にアクセスしません。仕組みは内部のヘッダー `vehicle_sil/j1939/detail/user_call.hpp` にまとめてあります。

### 破棄の順序

1. `Network` の破棄では、まず全ノードの付けたコンポーネントを、最後に付けたものから順に破棄します（ハンドラーは呼びません）。その間ノードとタイマーはまだ使えます。
2. その後でエンジンを破棄します。

- コンポーネント A がコンポーネント B を使うなら、B を先に付けます。
- コンポーネントのデストラクターからは送信できません（ステップの外のため）。

### 利用者に通知するループ

コンポーネントが自分の利用者に通知するループも、エンジンと同じ規則を守ります。ループは開始時の範囲だけを扱い、通知の後に要素への参照を使わず、通知の前に自分の状態を確定します。

## プロトコルのコンポーネント（`libs/j1939/parts`）

コンポーネントは 1 つずつ別の CMake ターゲットで、エンジン（`vehicle_sil::j1939`）の公開ヘッダーとツールキットだけを使います。コンポーネントのターゲットの include パスにはエンジンの `src/` が入らず、エンジンの内部は private です。

| ターゲット | コンポーネント | 内容 |
|---|---|---|
| `vehicle_sil::j1939_broadcast_suppression` | `BroadcastSuppression` | DM13 によるブロードキャストの抑制の状態（ノードに 1 つ） |
| `vehicle_sil::j1939_diagnostics` | `Diagnostics`、`Identification`、`parse_dtc_list` | DTC と DM1/DM2/DM3/DM11/DM22、識別情報、受信した DTC の一覧の読み取り。`BroadcastSuppression` を使う |
| `vehicle_sil::j1939_periodic_sender` | `PeriodicSender` | 1 つの PG の周期送信。ノードのアドレスと DM13 に従う。`BroadcastSuppression` を使う |
| `vehicle_sil::j1939_requester` | `Requester` | Request の送信と、応答・ACK・時間切れの報告、再送、同じ要求の相乗りと間隔の抑制 |
| `vehicle_sil::j1939_monitor` | `Monitor` | 1 つの PG の最新の受信と途絶（送信元はアドレスか NAME） |
| `vehicle_sil::j1939_address_commander` | `AddressCommander` | Commanded Address の送信と、相手が移ったことの確認 |
| `vehicle_sil::j1939_exchange` | `Exchange` | 独自プロトコルのコマンドを 1 つの相手へ送信し、応答を待つ（時間切れ、送信し直し、途中の応答、取り消し、自分と相手のアドレスの変化、長いコマンドと長い応答の転送） |

### 境界の検査（`j1939_parts.boundary`）

CTest の `j1939_parts.boundary` が、次のことを確認します。

| 対象 | 確認すること |
|---|---|
| コンポーネントのソース | 内部ヘッダーの include、テスト用の API（`detail::NetworkTestAccess`）、クラスを friend にする宣言（隠れた friend の関数は可）や `#define private` などがない |
| コンポーネントの CMakeLists.txt | コンパイルの定義・オプションを追加しない |
| コンポーネントの CMakeLists.txt | include パスに自分の `include/` しか追加しない |
| コンポーネントの CMakeLists.txt | `vehicle_sil::j1939` と他のコンポーネントのターゲットだけをリンクしている |

コンポーネントは `Observer` を設定しません。`set_observer` も禁止語です。`Network` の `Observer` は 1 つで、テストと記録のためのものです。コンポーネントはハンドラーで加わります。

### 呼べる場所とスレッド

コンポーネントの API の「どこからでも呼べる」は、ステップを実行するスレッドの上でのこと（ハンドラー、タイマー、アプリの処理、ステップの外）です。コンポーネントはロックを持たないので、ほかのスレッドからはホストの `post()` で渡します（[core.md](core.md) の「スレッドとキュー」）。

### コンポーネントが予約するタイマーの数

コンポーネントは、`timer_capacity` から次の数のタイマーを予約します。数は各コンポーネントの定数 `kTimers` にあります（`Monitor::kTimers` は `timeout` があるとき。タイマーを使わない `Identification` にはありません）。

| コンポーネント | タイマーの数 |
|---|---|
| `BroadcastSuppression` | 3 |
| `Diagnostics` | 3 |
| `Identification` | 0 |
| `PeriodicSender` | 1（送信する PG ごと） |
| `Requester` | 2 |
| `Monitor` | 1（`timeout` があるとき） |
| `AddressCommander` | 2 |
| `Exchange` | 2 |

- `PeriodicSender` は、生成時に DM13 に従う送信（`suppressible` が true か、指定なしでグローバル宛て）なら、ノードにまだなければ `BroadcastSuppression` も付けるので、その 3 も予約します。
- NAME を持ち診断を付けたノードは、Address Claim の 2 と合わせて 8 です（既定の 64 で 8 ノード）。
- 周期送信の多いノードでは `timer_capacity` を上げます。足りなければコンポーネントの生成が `std::length_error` で、メッセージに `timer_capacity` と出ます。
- 周期送信ごとにタイマーを 1 つ使うのは、期限の並べ替えと発火の回の規則をエンジンの `Timer` にだけ持たせるためです（コンポーネントの中で同じ仕組みを作り直しません）。

ハンドラーの中でコンポーネントを作るときは（要求ごとに周期送信を始めるなど）、作る前に `Network::timers_free()` をその数と比べ、足りなければ要求を拒否します。ハンドラーの中の `std::length_error` は `Network` を失敗させるので、確認しないと、多数のアドレスから要求を送信するだけでその ECU の通信を止められます。確認してから作るまでの間に、同じスレッドのほかの処理は割り込みません。

### DM13（`BroadcastSuppression`）

ノードに 1 つです。自分でブロードキャストするコンポーネントはこれを参照し、`suspended()` の間はブロードキャストしません。

- `BroadcastSuppression::of(node)`（なければ既定の設定で付ける）か `BroadcastSuppression::attach(node, options)` で作ります。
- 同じノードに 2 つ目を付けると `std::logic_error` です。
- コンストラクターは非公開のキーの型を引数に取るので、それ以外の方法では作れません。自分で生成したものは `of()` とコンポーネントから見えず、別の状態になるためです。コンパイル時に検出します。

他のノードの DM13 は、次のように扱います。

| 受信した DM13 | 起きること |
|---|---|
| 自分のネットワーク（`BroadcastSuppressionOptions::network`、既定は J1939 Network #1）のコマンドが Stop | 止めます。 |
| 自分のネットワークのコマンドが Start | 再開します。 |
| 自分のネットワークのコマンドが Stop でも Start でもない | Current Data Link のコマンドを使います。 |
| 8 バイト未満 | 無視します。 |

- 止めている間は DM13 を受信するたびに 6 秒を数え直します。Start でなければ、ほかのネットワークへのものや Hold Signal だけのものでも数え直します。
- 6 秒間 DM13 が来なければ再開します。
- 最後の DM13 からちょうど 6 秒の時刻に届いた DM13 は、まだ止めている間に届いたものとして扱います。
- 受信した DM13 の Suspend Signal と Suspend Duration は、送信元自身の一時停止の告知として扱い、停止の指示には使いません。

自分の一時停止は次のとおりです。

- `suspend(duration, scope)` でブロードキャストを止め、次の機会に DM13 をグローバルへ送信して告げます。
- 告げる DM13 は、全ネットワークのコマンドと Hold Signal が「指定なし」、Suspend Signal が全部の停止か一部の停止、バイト 5〜6 が秒数で、期間なしは 0xFFFF です。
- 期間が過ぎるか `resume()` で再開します。再開は告げません。まだ送信していない告知は取り消します。

抑制が反映されるのは、その状態を読むコンポーネントのブロードキャストだけです。Request への応答、Address Claim、Acknowledgement、トランスポートプロトコルの制御フレーム、アプリが `Node::send()` で直接送信するメッセージは止まりません。

### 診断（`Diagnostics`）

#### DTC

- DTC は SPN（19 ビット）と FMI で区別し、点灯するランプと点滅の速度を持ちます。
- `set_active(dtc, active)` で有効・無効にします（どこからでも呼べ、DM1 は次の機会に出ます）。
- 数は `DiagnosticsOptions::dtc_capacity`（1〜445。445 件の DM1 が 1 回の BAM に収まる）までで、超えると `std::length_error` です。
- 有効にするたびに発生回数（1〜126）が増えます。
- 無効にした DTC は「以前に有効」として残ります。

#### DM1 の周期送信

DM1（有効な DTC）は、ノードがアドレスを持っている間（Claimed か NAME なし）、1 秒ごとにグローバルへ送信します。アドレスを得たときに始め、失うと止めます。

- DTC の状態が変わったときは次の機会にすぐ送信します。
- ただし同じ DTC の変化による送信は 1 秒に 1 回までで、それ以内の変化は次の DM1 に載ります。
- この送信の後の周期は、変化の時刻から数えます。過ぎた期限で始めた `Timer` の中の変化のように、その時刻から 1 秒がもう過ぎているときは、ステップの時刻から数えます。
- `BroadcastSuppression` が抑制している間は送信しません（周期は進み、後から埋め合わせません）。
- 9 バイト以上の DM1 は、同じノードの前の転送が終わるのを待つ BAM（`WhenBusy::Queue`）です。
- 前の DM1 の BAM が終わるまで、次の DM1 の BAM は始めません。

#### DM1 と DM2 の Request への応答

DM1 と DM2（以前に有効な DTC）の Request には、抑制中も答えます。

| 応答の長さ | Request | 送信の方法 |
|---|---|---|
| 8 バイト以下 | どちらでも | グローバルへ 1 フレーム |
| 9 バイト以上 | 宛先指定 | 要求元へ RTS/CTS |
| 9 バイト以上 | グローバル | BAM |

- グローバルへ送信する応答は、同じ時刻に届いた複数の要求に 1 回だけ送信し、同じ PGN の BAM が送信中なら新たに送信しません。
- 1 秒の制限と応答の重複の判定はイベントの時刻で数えるので、結果はステップ幅によりません。
- DM1 と DM2 の BAM が送信中かどうかは、そのノードの転送の終わり（PGN と宛先グローバル）で数えます。
- 同じノードからアプリが DM1 や DM2 を BAM で送信すると、その数え方がずれます（診断を付けたノードでは、アプリはこの 2 つを送信しない前提です）。

データの形式は次のとおりです。

- ランプの状態とランプの点滅の 2 バイト（載せる DTC から合成。点滅は速い > 遅い > 点灯）
- DTC ごとに 4 バイト（SPN、FMI、発生回数）
- DTC がなければ 4 バイトの 0
- 8 バイト未満は 0xFF で埋めます。

#### DM3 と DM11

DM3 は以前に有効な DTC を消し、DM11 は有効な DTC を以前に有効にします。

- 宛先指定の Request には消し終えたときに肯定の ACK（消すものがなくても）を返し、グローバルの Request には返しません。
- `DiagnosticsOptions::on_clear` で、アプリが消すか、拒否する（NACK）か、後で消すかを決められます。

後で消すときは、次のように進みます。

1. 宛先指定の要求を `deferred_capacity` まで取っておきます（あふれた分には「応答できない」の ACK）。
2. アプリが `complete_clear(kind, cleared)` を呼びます（`on_clear` の中からでもよい）。
3. 次の機会に肯定か否定の ACK を返します。

その間にノードがアドレスを変えると、取っておいた要求には答えません。

#### DM22

- DM22 は自分宛てのもの（8 バイト以上）だけを処理し、DTC を 1 つ消して（有効なものは以前に有効へ、以前に有効なものは削除）要求元に DM22 で答えます。
- 否定の理由は、DTC がない、または有効と以前に有効の取り違えです。
- 同じステップの複数の DM22 には処理の順に答えます。

#### 受信した DM1、DM2 を読む（`parse_dtc_list()`）

受信した DM1、DM2 は `parse_dtc_list()` で読みます（`DtcListView`。データの形式の逆として読み、確保せず、渡したバイト列を指すだけ）。ルールは [j1939-guide.md](../j1939-guide.md) の「ほかのノードの故障コード（DM1、DM2）を読む」にあります。コンポーネントのハンドラーは使わないので、`Diagnostics` を付けていないノードでも使えます。

### 識別情報（`Identification`）

次の Request に答えます。

| Request | 内容 |
|---|---|
| ソフトウェア ID | フィールド数と、`*` で終わる各フィールド。未設定は 8 バイトの 0xFF |
| ECU ID | 部品番号、製造番号、場所、種類、製造者 |
| 製品 ID | コード、ブランド、モデル |
| 診断プロトコル ID | J1939-73 だけ |

- 8 バイト未満は 0xFF で埋め、9 バイト以上は宛先指定の Request なら要求元へ RTS/CTS、グローバルなら BAM です。
- 同じ要求元への 2 つ目の応答は、1 つ目の転送が終わってから始まります。

### 周期送信（`PeriodicSender`）

`node.attach<PeriodicSender>(pgn, period, data_or_encoder, options)` で作ります。`PeriodicSenderOptions` で宛先（PDU1 なら 1 つのアドレス）、優先度、遅れた期限の扱い、DM13 に従うか、`max_length` を選びます。9 バイト以上はトランスポートプロトコルです。

#### データの渡し方

| 渡すもの | 動作 |
|---|---|
| バイト列 | コンポーネントが持ち、`set_data()` で入れ替えます。 |
| `Encoder` | 送信するたびに呼び、コンポーネントのバッファに書いて長さを返します。バッファは生成時に `max_length` バイト、既定 8 です。 |
| `VectorEncoder` | 送信するたびに呼び、`std::vector<std::uint8_t>&` に追記します。空で渡し、大きさが長さです。 |

- `VectorEncoder` のベクターはコンポーネントが持ち、生成時に `max_length` バイトの容量を確保するので、追記だけなら送信するたびの確保はありません。
- `VectorEncoder` が何も追記しなければ、データのないフレームを送信します。
- 長さが送信するたびに変わるメッセージは `VectorEncoder` で作ります。
- span で呼べず、`std::vector<std::uint8_t>&`（値や const& ではない）を取って何も返さない関数を `VectorEncoder` として受け取ります。
- span で呼べる関数は `Encoder` として受け取り、長さを返さなければコンパイルエラーです。

#### 送信を始めるとき、止めるとき

- 送信するのは `Node::can_send_now()` の間だけです。要求の後の待ちの間は送信しません。エンジンが保留して 250 ms 後にまとめて出すのを避けるためです。
- 送信できるようになった通知の中ですぐ 1 回送信し（そのステップに出ます）、そこから周期を数えます。
- 生成時にすでに送信できるノードは、次の機会に始めます。
- アドレスを失うか変えると止め、送信できるようになったらまた始めます。

#### 期限とステップ幅

期限は `Timer` の期限（イベントの時刻）で数えるので、ステップ幅によらず格子（始めた時刻 + k × 周期）からずれません。送信するのは期限以後の最初のステップで、フレームの時刻はそのステップの時刻です。

ステップ幅が周期以下なら、1 ステップに入る期限は高々 1 つなので、送信の回数と期限はステップ幅によりません（テストで確認しています）。この主張は、送信できるようになった通知から始まった周期についてのものです。

`trigger()`、`resume()`、途中での生成で始め直したときは、最初の発火でもう周期が過ぎていれば、そのステップから周期を数え直します（まとめも追いつきもしません）。これは、アプリの処理やステップの外から始め直したときと、ステップ幅が周期以上のときに起こります。そのため始め直しを含む送信の時刻と回数は、ステップ幅によることがあります。

遅れた期限とは、ステップ幅が周期より長く、1 ステップに期限が複数入るときのことです。扱いは `MissedDeadlines` で選びます。

| `MissedDeadlines` | 動作 |
|---|---|
| `MissedDeadlines::Coalesce`（既定） | まとめて 1 回送信し（まとめた数は `statistics().coalesced`）、次の期限はそのステップより後の最初の格子点です。 |
| `CatchUp` | 期限ごとに送信し、同じ時刻のフレームが並びます（9 バイト以上は前の転送が終わるまで `Busy` で、失敗として数えます）。 |

#### DM13 に従うか（`suppressible`）

| `suppressible` | 動作 |
|---|---|
| true | `BroadcastSuppression::of(node).suspended()` の間は送信しません。 |
| false | `BroadcastSuppression` を使いません。 |
| 指定なし（既定） | そのときの宛先がグローバル宛て（`kGlobalAddress`）なら従い、1 つのアドレスなら従いません。宛先を変えると決め直します。 |

- 抑制中に送信しないのは、送信できるようになったときの最初の送信も含みます。期限は進み、埋め合わせません。数は `statistics().suppressed` です。
- 宛先指定の周期送信を DM13 で止めるかは確認していないので、利用者が選びます（下の「規格との一致を確認していない点（ECU アプリ向けのコンポーネント）」）。

1 つのアドレス宛てで作った（DM13 に従わない）送信を `set_destination(kGlobalAddress)` でグローバル宛てにするときは、ノードの `BroadcastSuppression`（`node.find()`）を使います。その場では付けません。ハンドラーの中でタイマーを取ることになり、それより前の DM13 も知らないためです。ノードになければ `std::logic_error` で、何も変わりません。このときは、組み立てで `BroadcastSuppression::of(node)` を付けるか、`suppressible` を指定します。

#### `trigger()`、`pause()`、`resume()`

`trigger()` は次の機会に送信し、周期をそこから数え直します。次の機会は、呼ぶ場所で決まります。

| `trigger()` を呼ぶ場所 | 送信するステップ |
|---|---|
| ハンドラーの中 | そのステップ |
| `Timer` のコールバックの中 | そのステップか次のステップ（発火中のタイマーと同じ期限で始めたタイマーは次の回になるため） |
| アプリの処理とステップの外 | 次のステップ（アプリの処理ですぐ送信するなら `Node::send()` を使います） |

`pause()` と `resume()` で止めて再開します。

#### 後からの変更

| 関数 | 反映されるとき |
|---|---|
| `set_period(period)` | 呼んだ時点（処理中のイベントの時刻。`Timer::start_after()` と同じ起点）から新しい周期を数え直します。 |
| `set_destination(address)`、`set_priority(priority)` | 次の送信から反映され、期限の格子は変えません。 |

- `set_period()` の後の次の送信は 1 周期後です（すぐ送信するなら `trigger()` も呼びます）。
- まだ来ていない「次の機会」の送信（`trigger()`、`resume()`）は残し、新しい周期はそこから数えます。
- どれも一時停止の間とノードが送信できない間にも呼べ、再開したときに新しい値で動きます。
- 不正な値（周期 0 以下、コンストラクターと同じ宛先の検査、優先度 8 以上）は `std::invalid_argument` で、状態は変わりません。
- `destination()` と `priority()` で今の値を読めます。

`set_period()` は `Observer` の中から呼びません。`PeriodicSender` のタイマーが動いている間は `std::logic_error` で `Network` が失敗し、周期は変わりません。動いていない間は周期を覚えるだけです。

#### 送信の失敗

- 送信の失敗（`SendStatus`）は数えて（`statistics().failures`、`last_failure`）、次の期限でまた送信します。例外にしません。
- Encoder の例外と、`max_length` を超える長さは `Network` を失敗させます（メッセージに PGN、長さ、`max_length`）。
- Encoder の中でその `PeriodicSender`（アプリが持つもの）を破棄してかまいません。そのメッセージは送信しません（`out` は Encoder が戻るまで有効です）。

### Request の送信（`Requester`）

`Requester::of(node).request(pgn, destination, callback)` で要求します。

#### 生成と設定

- `Requester` はノードに 1 つで、ノードに付けてコンポーネントとアプリが共有します（相乗りと間隔の抑制はノード単位です）。
- `of()` はなければ既定の設定で付けます。
- 設定を選ぶときは、何かが `of()` を使う前に `Requester::attach(node, options)` で付けます。2 つ目は `std::logic_error` です。
- コンストラクターは非公開のキーの型を引数に取るので、それ以外の方法では作れません。
- 要求ごとに待ち時間を変えることはできません。

#### 送信と待ち時間

- `request()` はどこからでも呼べます（ステップの外、アドレスを得る前も）。
- Request は次の機会（`trigger()` と同じ）に、ノードが送信できるようになってから出ます（`can_send_now()`。待ちの間は出しません）。
- 待ち時間（`timeout`、既定 1250 ms）は Request を出したステップの時刻から数えます（`flush()` で出るため）。

| 宛先 | 終わり方 |
|---|---|
| 1 つのアドレス | そのアドレスからの要求した PG（`RequestOutcome::Response`）か、そのアドレスからの、このノードと PGN を指定した Acknowledgement（`Acknowledged`）で終わります。 |
| グローバル | `timeout` の間に来た応答をそのたびに報告し（`last == false`）、最後に `Timeout`（`last == true`）を報告します。 |

- 1 つのアドレス宛てでは、来なければ `retries`（既定 2）回まで送信し直し、その後は `Timeout` です。送信し直しは時間切れのステップで出ます。
- グローバル宛てでは送信し直しません。

#### 相乗りと間隔

- 同じ PGN と宛先の要求が待っている間に来た要求は、その要求に相乗りします（Request を送信せず、同じ応答を受け取ります。`statistics().joined`）。
- `min_interval`（既定 0）で、同じ PGN と宛先の Request の間隔の下限を持てます。
- 待っている間（送信する前、送信し直す前）に来た応答でも終わります。周期的にブロードキャストされている PG を受信した場合も含みます（最新の値であることは同じです）。

#### アドレスの変化と失敗

| 起きたこと | 扱い |
|---|---|
| ノードがアドレスを失うか変えた | 送信した要求を、送信できるようになってから送信し直します（応答は古いアドレスへ来るため。この送信し直しは `retries` に数えません）。 |
| アドレスを要求できなくなった（`CannotClaim`） | すべて `NotSent`（`NoAddress`）で終えます。 |
| 送信の失敗 | `NotSent` です。 |

#### コールバックと容量

- コールバックはステップの中（ハンドラーかタイマー）で呼ばれ、`request()` と `cancel()` を呼べます。
- `cancel()` した要求のコールバックは呼びません。
- `RequestResult::data` は呼び出しの間だけ有効です。
- `capacity`（既定 8）の要求が待っていると、`request()` は空の `RequestId` を返します。

### 受信の監視（`Monitor`）

`node.attach<Monitor>(pgn, options)` で作ります。1 つの PG について、最新の受信（`data()`。`max_length`、既定 8 バイトまで）、時刻、送信元、受信数を持ちます。何も送信しません。`set_observer` は使いません（ハンドラーだけで作ります）。

#### 送信元で絞る

送信元は、どれでも、1 つのアドレス（`source`）、NAME（`name`）のどれかで絞ります。NAME で絞るときは、受信するたびにアドレス表と同じ `Network` のノードから今のアドレスを調べるので、送信元が移っても追います。

#### 利用者の関数で絞る（`accept`）

`accept`（任意）で、受け入れるメッセージを利用者の関数で絞れます（送信元の条件の後に呼びます）。セレクターで複数の型を載せた PGN の 1 つの型だけを見るときや、通し番号や検査値を確認するときに使います。

- 受け入れなかったメッセージは保持せず、受信として数えず（`Lost` を終えず、期限も延ばしません）、`rejected()` に数えます。
- 確認する前のデータが `data()` に出ることはありません。
- `accept` はステップの中で呼ばれます。その中で `Monitor` を破棄してもかまいません（そのメッセージは受け入れません。[コンポーネントの所有](#コンポーネントの所有nodeattach)）。

#### 状態と途絶

状態は `Waiting`（まだ受信していない）、`Receiving`、`Lost`（最後の受信から `timeout` の間来ない）です。

- 途絶の時間は最初の受信から数えます（起動の遅れを途絶にしません）。
- 期限はメッセージの時刻から数え、期限ちょうどの受信は間に合ったとします。そのため結果はステップ幅によりません（テストで確認しています）。
- 変化は `on_state`、受信は `on_message` で通知します。

### Commanded Address の送信（`AddressCommander`）

`commander.command(target_name, address, done, destination)` は、Commanded Address（NAME と新しいアドレスの 9 バイト）を、グローバルなら BAM、1 つのアドレスなら RTS/CTS で送信します（ノードの前の転送が終わるまで待ちます）。`request()` と同じく、どこからでも呼べ、ノードが送信できるようになってから出ます。

転送の終わり（`on_transfer_end`、`TransferEnd::id` で照合します）から待ちを数えます。完了しなかった転送（自分のアドレスの変化による取り消し、受信側の Abort、時間切れ）は 1 回だけ送信し直します。

| 結果 | なるとき |
|---|---|
| `Moved` | 相手がその NAME で新しいアドレスの Address Claimed を送信した |
| `Timeout` | 転送の完了から `timeout`（既定 1250 ms）までに来なかった |
| `NotSent` | `send()` が受け付けなかった（`send_status`） |
| `NotSent` | 送信し直した 2 回目の転送も完了しなかった（`CommandResult::transfer` と `reason`） |

任意アドレス不可の相手は従わないので `Timeout` になります。

### 独自プロトコルのコマンドと応答（`Exchange`）

規格にない通信手順（Proprietary A/B、メーカー独自の手順）の要求側を書くためのコンポーネントです。1 回の「コマンドを送信し、応答を待つ」を扱い、手順（複数のコマンドの順序、セッション）は利用者のコンポーネントが持ちます。応答側には専用のコンポーネントがなく、`on_message` と `send` で書きます（[j1939-guide.md](../j1939-guide.md)）。

#### 開始（`start()`）

`Exchange(node, options)` か `node.attach<Exchange>(options)` で作ります。

- `start(pgn, command, peer, match, done, command_options)` はどこからでも呼べます。
- コマンドは `max_length`（既定 8 バイト）までで、コピーして持ちます。
- コマンドは、ノードが送信できるようになってから次の機会に送信します。ハンドラーの中からならそのステップ、アプリの処理とステップの外からなら次のステップです。
- `capacity`（既定 4）のやり取りが動いていると空の `ExchangeId` を返します。

#### 相手（`peer`）

- 相手はアドレス（0〜253）か NAME です。
- PDU1 のコマンドは相手のアドレスへ、PDU2 のコマンドはグローバルへ送信します。
- NAME は送信するたびに `Network::address_of()` で調べます。
- 最初に送信するときにまだどの制御機能もその NAME を要求していなければ（起動の直後）、その Address Claimed を `timeout` まで待ってから送信し、来なければ `PeerLost` です。

#### 応答の照合（`match`）

相手のアドレスからのメッセージ（このノード宛てかグローバル、PGN によらない）を、送信した後のやり取りの `match` に、古いものから順に渡します。

前のコマンド（送信し直した元、`cancel()` したもの）への遅れた応答も渡るので、取り違えないかは `match` が決めます。`cancel()` は送信したコマンドを取り消しません。PGN も確認する型付きの読み出しは `codec::decode<M>(message)` です。

`match` は `Ignore`、`Pending`、`Final` のどれかを返します。

| `match` の戻り値 | 意味 |
|---|---|
| `Pending` | 途中の応答。そのメッセージの時刻から `timeout` を数え直し、以後は送信し直さない |
| `Final` | 応答。`Reply` で終わる |

1 つのメッセージは、`Ignore` を返さなかった最も古いやり取りだけが使います（同じ相手への同じコマンドは、応答を順に受け取ります）。

#### コマンドごとの設定（`CommandOptions`）

| 設定 | 内容 |
|---|---|
| `priority` | コマンドの優先度 |
| `timeout` | 空なら `ExchangeOptions::timeout`、既定 1250 ms |
| `retries` | 空なら `ExchangeOptions::retries`、既定 0 |
| `long_answer` | 長い応答の PGN |
| `on_address_change` | 自分のアドレスが変わったときの方針 |

#### 待ち時間の起点

| 場合 | 起点 |
|---|---|
| 下の 2 つ以外 | コマンドを送信したステップの時刻（送信し直しも、その送信し直しを送信したステップから） |
| 9 バイト以上のコマンド | 転送の完了（`TransferEnd::id` で照合） |
| `Pending` の応答を受信した | その時刻から数え直す |

9 バイト以上のコマンドはトランスポートプロトコルで送信します（`WhenBusy::Queue`）。

#### 長い応答（`long_answer`）

- 送信した後、相手からその PGN の受信の転送が始まると（`Node::on_incoming_transfer`。このノードへの RTS/CTS か BAM）、待ちを止めます。
- その転送が終わると（完了、中断、時間切れ、BAM の欠落）、終わりの時刻から `timeout` を数え直します（完了なら組み立てたメッセージがすぐ後に `match` に渡ります）。
- ほかの PGN、ほかの送信元、ほかのノード宛ての転送では止めません。
- 指定しなければ、受信の転送があっても待ちは進みます（長い応答の時間を `timeout` に含めます）。

止めておけるのは、1 回の試行につき、最初にその転送が始まってから `ExchangeOptions::answer_transfer_limit`（既定 60 秒。規格の値ではありません）までです。それを過ぎると、転送の開始も終わりも待ちの期限を変えません（待ちは遅くとも上限の `timeout` 後に終わります）。

#### 時間切れの送信し直し（`retries`）

- 時間切れの後に送信し直し、送信し直しは時間切れのステップで出ます。
- 長いコマンドの転送の失敗（受信側の Abort、このノードの時間切れ）も 1 回の試行です。
- `Pending` の後は送信し直しません。
- 既定で送信し直さないのは、コマンドが冪等とは限らないためです。

#### 自分のアドレスが変わったとき（`on_address_change`）

送信した後にノードがアドレスを失うか変えると、応答は古いアドレスへ送信されるので、このノードは受信できません。

| 方針、場合 | 扱い |
|---|---|
| `AddressChangePolicy::Stop`（既定） | `Interrupted` で終えます。 |
| `SendAgain` | 送信できるようになってから新しいアドレスで送信し直します（`retries` に数えず、`Pending` の後でも送信し直します）。 |
| 長いコマンドの転送が最後のパケットの後に取り消された（`Cancelled`） | 上の 2 つと同じ扱いです。 |
| 最後のパケットの前に取り消された転送、まだ送信していないコマンド | 相手に届いていないので、方針によらず待って新しいアドレスから送信します。 |

相手のアドレスが取られたための取り消しなら、続く Address Claimed で `PeerLost` になります。

#### やり取りの結果（`ExchangeOutcome`）

`NotSent` は「相手に届いていない」、`Interrupted` は「送信したが、相手が実行したかは分からない」で、非冪等な操作を手順の側で扱えるように分けています。最後のパケットまで出したかは `TransferEnd::all_packets_sent` で判断します。

| 結果 | なるとき |
|---|---|
| `Reply` | `match` が `Final` を返した |
| `Timeout` | 試行が尽きても応答がなかった（`Pending` の後は、最後の `Pending` から `timeout`） |
| `NotSent` | 一度も送信しないうちに `send()` が受け付けなかった（その `SendStatus`）か、アドレスを要求できなくなった（`NoAddress`）。最後の試行の長いコマンドの転送が、最後のパケットの前に終わったか、受信側に中断された（`transfer`、`reason`） |
| `Interrupted` | 送信した後に自分のアドレスが変わった（`Stop`）か、アドレスを要求できなくなった（`NoAddress`）。最後のパケットの後に転送が取り消された（`transfer` が `Cancelled`）か、このノードが時間切れで中断した（`Aborted`）。送信し直しを `send()` が受け付けなかった（`QueueFull` など） |
| `PeerLost` | 相手のアドレスがなくなった（下の「相手の消失」） |

#### 相手の消失（`PeerLost`）

相手の NAME（指定した NAME か、最初に送信したときにそのアドレスにあった NAME）について、次のどれかを受信したときです。

- 別のアドレスを要求する
- Cannot Claim を送信する
- 別の NAME にアドレスを取られる

Address Claimed と Cannot Claim を受信するたびに `address_of()` で確認し、送信し直しが残っていても終えます。

- NAME の解決を待つ期限は、その間に自分のアドレスが変わっても延びません。
- NAME の分からないアドレス（NAME のないテスト用のノードなど）が相手なら、時間切れだけで終わります。
- 相手が同じ `Network` のノードで、別のノードにアドレスを取られたときは、相手の Cannot Claim か新しいアドレスの Address Claimed で分かります。

#### コールバック（`done`）と破棄

- コールバック（`done`）はやり取りごとに 1 回、ステップの中で呼ばれ、`cancel()` したものには呼ばれません。
- `ExchangeResult::reply` のデータは呼び出しの間だけ有効です。
- `match` と `done` の中から `start()`、`cancel()`、`cancel_all()` を呼べ、`Exchange` を破棄できます（その後は何も呼びません）。
- 通知のループは開始時のやり取りだけを扱い、状態を確定してから呼びます。
- 破棄すると、残りのやり取りはコールバックなしで終わります。
- `Network` より後に破棄してもかまいません。`Network` の破棄の後の `start()` は `std::logic_error` です。

### 規格との一致を確認していない点（ECU アプリ向けのコンポーネント）

`Requester` の待ち時間と送信し直しの回数の既定値（1250 ms、2 回）は、J1939-21 と J1939-82 の要求側の値に合わせています。確認していないのは次の点です。

- Busy などの理由の ACK（`AckCode::CannotRespond` など）を受信したら送信し直さずに終えること
- グローバルの Request を送信し直さないこと
- 相乗りと `min_interval` の扱い
- まだ送信していない要求を同じ PG の受信で終えること
- DM13 が 1 つのアドレス宛ての周期送信も止めるか（`PeriodicSender` は既定では止めず、`suppressible` で選べます）
- `AddressCommander` の待ち時間の既定値と、Address Claimed で移ったと判断すること

### 規格との一致を確認していない点（診断）

| 対象 | 確認していない点 |
|---|---|
| DM13 | 6 秒ちょうどの扱い、6 秒を数え直す DM13 の範囲、Stop の後に DM13 が一度も来ない場合の扱い、Stop と Start が同じ DM13 で別々のネットワークに指定されたときの扱い |
| DM3/DM11 | 後から返す ACK の期限（アプリが `complete_clear()` を呼ばなければ答えません） |
| DM22 | 否定の理由のうち使っていないもの、グローバル宛ての DM22 を無視すること |
| DM2 | ランプのバイトを以前に有効な DTC から作ること |
| DTC の発生回数 | 上限 |
| 識別情報 | 未設定のときの応答（ソフトウェア ID の 0xFF、空のフィールド） |
| `parse_dtc_list()` | DTC の 4 バイト目の最上位ビットの意味（解釈せず `ReadDtc::byte4_high_bit` と `raw` で渡します） |
| `parse_dtc_list()` | ほかの ECU が DTC のない一覧を 4 バイトの 0 以外の形で送信するか |
| `parse_dtc_list()` | ランプの状態と点滅の、`Diagnostics` が送信しない値の意味 |

## 型付きメッセージ（`vehicle_sil::j1939_codec`）

PG の信号を YAML で定義し、ビルドのときに C++ の型を生成します。書式と API は [j1939-codec.md](../j1939-codec.md) にあります。

### 責務

- 型は信号の値とバイト列の変換だけを持ちます。送受信、周期、宛先、時間は持ちません。
- `codec.hpp` は `vehicle_sil/j1939/types.hpp`（`Pgn`、`Priority`）だけを include し、`Network` と `Node` を知りません。
- ノードとコンポーネントへの接続は `codec_node.hpp` の関数（`attach_sender`、`encoder`、`on_message`、`send`）で、どれもノードの公開 API と `PeriodicSender` の上の薄い関数です。
- エンジンは型付きメッセージを知りません。
- 型付きメッセージは時間に関わりません。周期と送信の時刻は `PeriodicSender` の規則のとおりです。
- SAE J1939 の PG と SPN の定義データ（J1939DA）は同梱しません。例とテストは、独自（Proprietary）の PG と架空の配置だけを使います。

境界は CTest で検査します。

| テスト | 確認すること |
|---|---|
| `j1939_codec.independent_of_the_engine` | `codec.hpp` の include が `types.hpp` だけである |
| `j1939_codec.boundary` | `libs/j1939/codec` がエンジンの内部を使わない |

### 生成

- `vehicle_sil_add_j1939_codec()`（`cmake/VehicleSilJ1939Codec.cmake`）がビルドのときに `tools/j1939_codegen/j1939_codegen.py` を呼び、生成物はコミットしません。
- 生成器は Python 3.11 以上と PyYAML を使い、この関数を呼んだときだけ必要です（vehicle-sil のテストと例をビルドするときも必要です）。
- 特別な値のプロファイルの選択と継承（ファイル、メッセージ、信号）は生成器が解決し、信号ごとの特別な値の配列だけを生成します。
- 生成したヘッダーは同じ定義から同じ内容になります。
- 生成するのは信号の配置の定数とメンバーだけで、ビット操作はランタイムのテンプレートの 1 か所にあります。

生成器は、次の定義のエラーを生成の時点で止めます（詳しくは [j1939-codec.md](../j1939-codec.md#生成器が確認すること) の「生成器が確認すること」）。

- 重なり
- 範囲外
- 名前（C++ の識別子でない、キーワードか予約された名前、生成する型のメンバーと重なる、互いに重なる）
- 知らないキー
- 有効範囲の内側の特別な値
- 規則のないプロファイルの直接の指定
- ファイルやメッセージで選んだ自前のプロファイルがどの信号にも合わないこと
- 同じ PGN の複数のメッセージ（どれかにセレクターがない、セレクターの位置が違う、セレクターの値が重なる）

### 値

- 信号は受信した raw のビットをそのまま持ち、状態（`Valid`、`Error`、`NotAvailable`、`Special`、`OutOfRange`、`Undefined`）と、`Valid` のときだけの物理値を返します。
- 特別な値は Codec 全体では予約せず、信号の定義だけで決まります（定義のない信号ではすべてのビットパターンが値）。
- 特別な値が数値に暗黙に変わることはなく、物理値を設定して特別な値になることもありません（有効範囲から外すため）。
- 物理値と raw 値の変換は `double` の四則演算と `std::round` だけで、乱数や時計を使いません。
- raw × scale は `double` に丸めてから offset を加えます。積を一度格納し、コンパイラーが積和を 1 回の丸めにまとめないようにしています。clang の最適化ビルドでも同じ値になることをテストで確認しています。

### 資源

- 型は状態を持たない値で、`encode`、`decode`、`codec_node.hpp` のハンドラーと `Encoder` は定常状態でメモリを確保しません（テストで確認しています）。
- `codec::encoder` は送信するたびに新しいメッセージをスタックに作ります。

### 規格との一致を確認していない点（型付きメッセージ）

組み込みの `j1939` プロファイルの値と、規則を設けていない長さは確認していません（[j1939-codec.md](../j1939-codec.md) の「規格との一致」）。利用者はファイルで `j1939` を定義し直せます。

## 観測（`Observer`）

`Network::set_observer(&observer)` で、ネットワークのイベントを読み取り専用で受け取ります（ヘッダー `vehicle_sil/j1939/observer.hpp`）。テストと記録のための API で、通信には加わりません。ほかの participant のメッセージを聞いて使う製品のコードは、`Listener` に書きます。

### イベント（`Event`）

イベント（`Event`、種類は `EventKind`）は 1 つの値の型です。フィールドの意味は種類ごとに決まっています（ヘッダーに記載）。`node` はローカルのノードの番号（`Network::node()`）で、なければ -1 です。`data` は呼び出しの間だけ有効です。

| 種類 | いつ | 時刻 |
|---|---|---|
| `AddressChanged` | ノードのアドレスか状態が変わったとき。そのノードの `on_address_change` のハンドラーより先 | `AddressChange::time` |
| `SendRequested` | `send()`、`request()`、Request への応答（`respond()`。ノードがもう持たないアドレスへの要求への応答は `NoAddress`）が戻り値を返したとき。`held` は、Claim の後の待ちのために保留したこと。`acknowledge()` は含めません（ACK は `FrameSent` で見えます） | ステップの時刻 |
| `MessageDropped` | 送信するはずのメッセージを送信しなかったとき（`DropReason`）: 保留中のメッセージか ACK のノードがアドレスを失った、保留を出すときにデータキュー（ACK は制御キュー）が満杯だった、アドレスを失う前に送信キューに入れたフレーム | 原因の時刻（保留）かステップの時刻（送信キュー） |
| `FrameSent` | ポートにフレームを渡したとき（`send_result` はポートの戻り値。`QueueFull` で残したフレームは次の試みでも出ます） | ステップの時刻 |
| `MessageReceived` | 受信したメッセージ（単一フレームと、トランスポートプロトコルで組み立てたもの）をノードに配送する直前。`local` は同じ `Network` の他のノードから（`node` が送信したノード）。TP.CM と TP.DT は出ません | メッセージの時刻 |
| `TransferStarted` | 転送の開始。送信側は `send()` か `respond()` が受け付けたとき（応答待ち行列や Claim の後の待ちに入るものを含む）、受信側は RTS か BAM を受け付けたとき（BAM は `node` が -1） | 送信側はステップの時刻、受信側は RTS か BAM の時刻 |
| `TransferEnded` | 転送の終わり（`result`、`reason`）。開始した転送は 1 回だけ終わります（`Network` が失敗するか破棄される前に限ります）。送信側の `source` は送信した時のアドレスです（保留した転送が始まる前にノードが移ると、開始の `source` と違います） | 原因の時刻 |
| `PortEvent` | ポートのイベント（`on_port_event()`） | イベントの時刻 |

### 受信側の転送の終わり

| `result` | なるとき |
|---|---|
| `Completed` | 続いてそのメッセージの `MessageReceived` が出ます |
| `AbortedByPeer` | 送信側が Connection Abort を送信した |
| `Aborted` | このノードが送信した（タイムアウト、再送の上限など） |
| `Lost` | BAM のパケットの欠落（`reason` が `BadSequence`）か時間切れ（`Timeout`）。何も送信しません |
| `Cancelled` | 下の 5 つのどれか |

`Cancelled` になるのは次のときです。

- 送信側のアドレスを別の NAME が要求したか手放した
- ローカルのノードがアドレスを失った
- 同じ送信者の新しい RTS か BAM が置き換えた
- CTS を送信キューに入れられなかった
- 単一フレームの PGN（Address Claimed、Request）を運んでいた

`TransferResult::Lost` は受信側にだけ使い、`on_transfer_end` には渡りません。

### 読み取り専用のルール

`on_event()` の中から呼んだときの扱いは次のとおりです。

| `on_event()` の中から呼ぶもの | 起きること |
|---|---|
| その `Network` の送信（`send`、`request`、`respond`、`acknowledge`）、ハンドラーの登録、ノードやコンポーネントの追加、`Timer` の生成と開始、ステップの関数、`set_observer()` | `std::logic_error` で、`Network` は失敗状態になります。 |
| ハンドラーの解除、`Timer` の取り消し・破棄 | デストラクターから呼ばれるので例外を投げず、`Network` を失敗状態にします（解除は `false` を返します）。 |
| `on_event()` からの例外 | `Network` を失敗させます。 |

`on_event()` が例外を外に出さずに `Network` を失敗させた場合（`std::logic_error` を自分で捕まえた、解除や取り消しをした）は、その場ではステップを止めません。そのフレームやメッセージの残りの処理は動き、`Network` が次に失敗を確認する所で止まります（聞き役の席は、関数が戻った所で止めます）。

### 呼ばれるときと影響

- `on_event()` はステップの中で同期的に、上の表の時点で呼ばれます。
- Observer の有無で、送信するフレームと時刻、ハンドラーの呼ばれ方は変わりません（テストで確認しています）。
- 未設定ならイベントごとにポインターの比較 1 回で、エンジンはメモリを確保しません。

### 設定、解除、破棄

- 設定と解除はステップの外だけです（失敗状態の後はどこでも）。
- Observer は 1 つのネットワークだけを見ます。別のネットワークに設定すると前のネットワークから外れます（前のネットワークがステップの中なら `std::logic_error`）。
- Observer の破棄で自動で外れ、`Network` を先に破棄しても安全です。
- `on_event()` の中で Observer を破棄してはいけません。

## 聞き役の席（内部の口）

`Network` の受信の道には、聞き役（ほかのノードどうしのやり取りを横から聞くコンポーネント）が座る席が 1 つあります（`detail::FrameSeat`、`libs/j1939/src/frame_seat.hpp`）。エンジンの内部の口です。ヘッダーはインストールせず、利用者の拡張点ではありません。席の設定（`Network::set_seat()`）は非公開で、テストは `tests/j1939/network_test_access.hpp` から使います。座るのは `Listener` の実装（`src/listener.cpp` の中のクラス）だけです。エラーの文は、席に座るものを「Listener」と呼びます。

`Observer` とは別の口です。`Observer` はテストと記録のためのもので、席と同時に付けられます。

| 呼び出し | いつ | 渡すもの |
|---|---|---|
| `on_frame(time, frame, local)` | ステップの受信フレームを並べ直した後、そのフレームをネットワークが扱う直前。TP.CM、TP.DT、ほかのアドレス宛てのフレームも来ます | フレームとその時刻。`local` は同じ `Network` のノードが送信したもの（折り返し。ノードが 2 つ以上のときだけあります） |
| `on_message(message, local)` | メッセージ（単一フレームと、トランスポートプロトコルで組み立てたもの）をノードに配る直前。`Observer` の `MessageReceived` と同じ時点、同じ中身で、`Observer` の後 | `Message` と `local` |
| `on_step_end(now)` | ステップの受信フレームを扱い終えた後、ステップの時刻までのタイマーを発火させる前。フレームがないステップでも、ステップごとに 1 回 | ステップの時刻 |

- 席に来ないフレーム: `Network` が受け取らないもの（11 ビットのフレーム、無効なフレーム、受け付けない送り元のフレーム、`receive_capacity` を超えた分）。
- 順: フレームの時刻より前のタイマー、`on_frame`、（メッセージなら）`Observer` の `MessageReceived`、`on_message`、ノードのハンドラー。ステップの最後は、`on_step_end`、残りのタイマーの順です。
- 聞き役がステップのフレームから決めたこと（転送の完了、Abort）は、残りのタイマーが動く時点でそろっています。聞き役が `on_step_end(now)` で時刻の経過から決めたこと（時間切れ）は、ステップの時刻まで進んでいるので、締め切りがそれより前のタイマーにも見えます。どちらが先に起きたかは、順ではなくそれぞれの `time` で比べます。
- 席は読み取り専用です。席の関数の中から、その `Network` の送信、ハンドラーの登録、ノードやコンポーネントの追加、`Timer` の生成と開始、ステップの関数、`set_observer()`、席の設定を呼ぶと `std::logic_error` で、`Network` は失敗状態になります。文は「… called from a Listener handler (handlers only read: update variables there and send from on_step)」です。
- ハンドラーの解除と `Timer` の取り消し・破棄は例外を投げず、`Network` を失敗状態にします。席の関数からの例外も `Network` を失敗させます（「a Listener handler threw: …」）。
- 席の関数が例外を外に出さずに `Network` を失敗させた場合（`std::logic_error` を自分で捕まえた、ハンドラーの解除や `Timer` の取り消しをした）も、関数が戻った所で `std::logic_error` になります。そのフレーム、メッセージ、ステップの残り（ノードのハンドラー、トランスポートプロトコルの処理、タイマー）は動きません。
- 席の関数はステップの中で同期的に呼ばれます。席の有無で、送信するフレームと時刻、ハンドラーの呼ばれ方、`Observer` のイベントは変わりません（テストで確認しています）。席が空ならイベントごとにポインターの比較 1 回で、席があってもエンジンはメモリを確保しません。
- 設定と解除はステップの外だけです（失敗状態の後はどこでも）。席は 1 つで、もう座っているものがあるとき、座るものが別の `Network` の席にいるときは `std::logic_error` です（文に直し方があります）。
- 座るものの破棄で席は自動で空き、`Network` を先に破棄しても安全です。破棄はステップの中でもできます（ノードのハンドラー、タイマー、アプリケーションの段から。その後は何も呼ばれず、`Network` は失敗しません）。席の関数の中で、座っているもの自身を破棄してはいけません（破棄したオブジェクトの関数が動き続けるので未定義の動作で、`Network` は検出できません）。

## ステップ幅と資源の上限

### ステップ幅

| ステップ幅 | 起きること |
|---|---|
| 50 ms を超える | 警告します（`NetworkOptions::warning`、既定は標準エラー出力）。 |
| 200 ms を超える | `start()` が `std::invalid_argument` を投げ、ホストが失敗状態になります（Request への応答とパケット間隔の 200 ms を守れないため）。 |

推奨は 10 ms 以下です。`RealTimeDriver` で実行するときは、その `max_idle` で同じ検査をします。

実時間では、タイマーの期限（`next_deadline()`）にドライバーが起きます。CTS で求められたパケットは CTS を受信したステップで出ますが、ポートの `QueueFull` で残したフレームと 1 ステップの上限で繰り越したフレームは、`max_idle` の後のステップで出ます。

### バッファとタイマーの予約

バッファはすべて生成時に確保します。`NetworkOptions` で決めるのは次のものです。

- 1 ステップの受信数
- ノード数
- データキュー
- 1 ステップの送信数
- タイマー数
- ノードごとの保留領域
- トランスポートプロトコルのセッション（各 1785 バイトのバッファとタイマー 1 つ。タイマーは `timer_capacity` とは別に確保）
- 応答待ち行列

`timer_capacity` は予約制です。予約があるので、タイマーの開始が枠不足で失敗することはありません。

| 予約するもの | 数 | 足りないとき |
|---|---|---|
| NAME を持つノードの追加 | 2 つ（Claim 後の待ちと Cannot Claim） | `add_node()` が `std::invalid_argument` を投げます。 |
| `Timer` の生成 | 1 つ | `Timer` の生成が `std::length_error` を投げます。 |

### メモリの確保

次の処理では、メモリを確保しません（テストで `operator new` を数えて確認しています）。

- フレームの受信と配送
- Request への応答
- 送信（ポートの `QueueFull` と `Failed`、送信数の上限による繰り越しを含む）
- ローカル折り返し
- タイマー
- Address Claim（任意アドレスの選択、アドレス表、アドレス違反、Commanded Address、状態の通知を含む）
- トランスポートプロトコル（再送の要求、タイムアウト、Abort、応答待ち行列を含む）

次のものも、定常状態ではメモリを確保しません。

- ツールキットとコンポーネント（`Timer` の開始と取り消し、DM1 の周期送信と BAM、DM13、DM1/DM2/識別情報の応答、DM22、後で返す ACK、`PeriodicSender`、`Requester` の応答と時間切れと送信し直し、`Monitor`、`AddressCommander`、`Exchange` の応答と途中の応答と時間切れと送信し直しと長いコマンド）
- `Observer` への通知
- 型付きメッセージの送受信（`codec::attach_sender`、`codec::on_message`）

メモリを確保するのは、次のときだけです。

- ノードの追加
- ハンドラーと応答者の登録と解除
- コンポーネントの生成
- 識別情報の設定
- `Requester::request()`、`AddressCommander::command()`、`Exchange::start()` がコールバックをコピーするとき（大きなキャプチャ）

### 上限に達したとき

| 上限 | 起きること |
|---|---|
| 受信 | そのステップの残りを捨てて数えます。 |
| データキュー | `send()` が `QueueFull` を返します。 |
| 制御キュー | あふれた分を捨てて数えます。 |
| ノード数 | `add_node()` が `std::length_error` を投げます。 |
| トランスポートプロトコル | 上の「トランスポートプロトコル」の節のとおりです。 |

制御キューの容量は、受信の上限、ノード数、保留領域の大きさ、セッション数、応答待ち行列の大きさから決めています。通常は満杯になりません。

### 失敗状態

次のどちらかで、`Network` は失敗状態になります。

- ハンドラー、応答者、タイマー、ポートからの例外
- 使い方のエラー（その `Network` のハンドラー、応答者、タイマーからの `start`/`begin`/`receive`/`process`/`flush`/`add_node`、時刻が増えない、段階の順序のエラー）

以後のステップの呼び出しはすべて `std::logic_error` です。ハンドラーが例外を捕捉して無視しても失敗状態のままです。

## 検証の範囲

規格との一致を確認していない点は、このドキュメントの各節にまとめています。

### J1939（`j1939.*`、`j1939_parts.*`、`tests/j1939/`）

仮想バスの上で、テストが相手ノードのフレームを仮想時間で 1 つずつ送信し、スタックが送信するフレームとその時刻を確認します。

| 対象 | 確認すること |
|---|---|
| Address Claim とアドレスの管理（J1939-81） | 要求の後の待ち、優先度による勝ち負け、Cannot Claim とその遅延、任意アドレスの選択、Request for Address Claimed、Commanded Address、アドレス違反、アドレス表、同じ Network の複数のノード、2 つの Network |
| Request と Acknowledgement（J1939-21） | グローバルと宛先指定、NACK の条件、null アドレスからの要求、不正な長さ、後で答える要求 |
| トランスポートプロトコル（BAM、RTS/CTS） | 最小・最大・境界のサイズ、CTS のウィンドウと再送の要求、hold、各タイムアウト、Abort の理由、同時セッションと上限、応答の待ち行列 |
| 仮想バスの故障注入 | 欠落、遅延、重複、並べ替え、ポートの `QueueFull` と `Failed`、受信キューのあふれ、ECU 単位の通信断 |
| プロトコルのコンポーネント（J1939-73） | DM13 によるブロードキャストの抑制、DM1 の周期と内容、DM2、DM3、DM11、DM22、識別情報 |
| 境界 | コンポーネントがエンジンの公開 API とツールキットだけを使うこと（`j1939_parts.boundary`、`local.boundary`、`testkit.boundary`、`peer.boundary`、`ecu.boundary`、`simulation.boundary`） |
| `TransferSniffer` | 手で書いたフレームでの決まり（時間切れと猶予、同じ組の新しい告知、欠けのある EndOfMsgACK、BAM、満杯）、エンジンどうしの転送を横から聞いた結果（再送、どちらかがあきらめる時間切れ）、エンジンの受け手に手で書いたフレームを送信した結果（送り手のアドレスの持ち主が変わった後の告知、最後のパケットの直後の別の PGN の告知、前の転送の遅れたパケット）、種を固定した故障注入（パケットの欠落、重複、遅延、並べ替え、送り手の停止と Abort、告知のやり直し）で、同じフレームを受けたエンジンの受信側のノードと、メッセージ（時刻とバイト列まで）と転送の終わり方が一致すること。メモリを確保しないこと。`Network` に依らないこと（`j1939.sniffer_boundary`） |
| `Listener` | エンジンどうしのやり取り（接続、再送と遅れ、断りと時間切れ、同時の複数、BAM、単一フレーム）を横から聞いた結果が、受け手のノードのメッセージと数、順、時刻、バイト列で一致し、同じメッセージが 1 回だけ渡ること。同じ `Network` のノードの送信が、ノードが 1 つでも 2 つでも渡らないことと、`hear_local`。ノードがアドレスを取ったときの `Lost` と、失った後にまた追えること。ハンドラーの順（フレームの時刻で終わったほかの転送が、そのフレームのメッセージより先）、ステップの終わりで決まることとタイマーの順。ハンドラーからの送信と登録、例外でステップが止まること。ハンドラーの解除（見張りを先に壊す、ハンドラーの中から自分とほかを外す、`Listener` や `Network` が先に壊れる）。ノードのある `Network` で、`Listener` のあり・なし（`hear_local` の入と切）でノードの受信、イベント、送信したフレームが変わらないこと。生成と破棄の順。メモリを確保しないこと。`listener.cpp` がエンジンの内部を席のほかに使わないこと（`j1939.sniffer_boundary`） |
| そのほか | ツールキット、Observer、聞き役の席、バスのタイミング（調停と送信時間）、実時間のドライバーでの動作、定常状態のステップでメモリを確保しないこと |

### J1939 と SIL Kit（`j1939_silkit.*`）

同じシナリオ（Request、Address Claim、BAM、RTS/CTS）を仮想バスと SIL Kit（プロセス内のレジストリ、ステップ幅の違う participant）で動かし、トレースが一致することを確認します。SIL Kit の簡易シミュレーションと簡易 CAN Network Simulator の両方で、プロトコルの結果を確認します。

## 統合テストで検証する J1939 のやり取り

Sender は `Peer` を実時間で動かし、J1939 スタックのノードを 1 つ作ります。NAME は industry group 2、function 130、manufacturer 0x7F0、identity 0x1234 です。Receiver が動き出してからノードを追加し、アドレス 0x80 を要求させます。自分のアドレスになったら、PGN 0xFF10 を 5 回ブロードキャストします。フレームはすべて Peer の SIL Kit の CAN ポートを通って送信されます。

Receiver は J1939 スタックを使いません。SIL Kit の CAN API で直接受信し、J1939 の定義から計算した期待値と、順序と内容をバイト単位で照合します。

| 順序 | 内容 | CAN ID | DLC | データ |
|---|---|---|---|---|
| 1 | Address Claim | `0x18EEFF80` | 8 | `34 12 00 FE 00 82 00 20`（NAME `0x20008200FE001234`、リトルエンディアン） |
| 2–6 | PGN 0xFF10 | `0x18FF1080` | 8 | 送信番号から決まるテストデータ |

スタックは自分の Address Claim から始めます。起動時に Request for Address Claim は送信しません。

| 終了コード | なるとき |
|---|---|
| 1 | 検証失敗（下の 5 つのどれか） |
| 2 | タイムアウト（期待するフレームが時間内にそろわない） |
| 3 | 接続や起動に失敗した |

検証失敗になるのは次の場合です。

- 拡張フレームでない
- 順序が違う（Address Claim より前の PGN、2 回目の Address Claim）
- 未知の ID がある
- 期待するフレームがそろう前に、余分なフレームが届く
- ペイロードが一致しない

## J1939 の既知の制限

J1939 スタックの制限と、規格との一致を確認していない点は、このドキュメントの各節に書いています。実際の ECU やツールに接続するときに影響する主なものは次のとおりです。

- ETP（1785 バイトを超えるメッセージ）はありません。
- 停止したときに実行中の転送は、Abort を送信せずに捨てます。
- 受信側は保留（CTS 0）を送信しません。
- DM13 で止まるのは、抑制の状態を読むコンポーネントのブロードキャスト（DM1）だけです。アプリが `Node::send()` で直接送信するメッセージは止まりません。
- 自分の一時停止を終えたときは、再開を告げません（「DM13」）。
- J1939 スタックを XL のチャネルに直接載せた動作（`ExternalPortAdapter`）と、Vector の Network Simulator での動作は確認していません（[bridges.md](../bridges.md) の「検証の範囲」、[can.md](can.md) の「簡易 CAN Network Simulator」）。
