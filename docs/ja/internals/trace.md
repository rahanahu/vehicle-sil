# プロファイリングのトレース（`vehicle_sil::trace`）

[English](../../internals/trace.md)

プロファイリングのトレースは、仮想時間の実行で実時間がどこに使われたかを示します。各ステップを最後に終えた参加者と、それが何を待ったか、シナリオの書き込み 1 回の往復の各部分にかかった時間です。どちらも仮想時刻と書き込みの番号（seq）が要るので、サンプリングのプロファイラーでは分かりません。CPU の重い所は、サンプリングのプロファイラー（Linux は `perf`、Windows は WPR と WPA）で調べます。

このトレースは vehicle-sil を開発するための内部の道具です。ファイルの形式、記録の名前、`scripts/trace-report.py` の出力は、どのリリースでも変わることがあります。これらを前提に作らないでください。速度の基準測定や CI 計測に使える、スキーマ付き・実行影響ゼロの Control Hub SIL Kit トランスポート要約には `vehicle_sil_launch run --control-metrics <file>` を使ってください（[simulation-run.md](../simulation-run.md#control-hub-トランスポートのメトリクスを記録する--control-metrics) の「Control Hub トランスポートのメトリクスを記録する（`--control-metrics`）」）。

## トレースを取る

ランチャーを起動するときに `VEHICLE_SIL_TRACE` にディレクトリーを設定します。ランチャーが起動する ECU はこの変数を引き継ぐので、実行のすべてのプロセスがそこに自分のファイルを書きます。終わったら、そのディレクトリーを要約します。

```sh
VEHICLE_SIL_TRACE=build/trace vehicle_sil_launch run simulation.yaml --scenario scenarios/throttle_step.yaml
scripts/trace-report.py build/trace --merged build/trace/merged.json
```

Windows でも、ランチャーを起動する前に同じようにシェルで変数を設定します。手で起動する ECU や、別のコンピューターで動く ECU には、その環境に変数が要ります。

| 変数 | 意味 |
|---|---|
| `VEHICLE_SIL_TRACE` | ファイルを書くディレクトリー（書くときに作る）。プロセスの起動時に 1 回だけ読む。相対パスは最初に読んだプロセスのカレントディレクトリーから見たもので、そのプロセスは起動するプロセスのために変数を絶対パスに書き換える（ランチャーは ECU を設定ファイルのディレクトリーで起動する）。なければ何も記録しない |
| `VEHICLE_SIL_TRACE_EVENTS` | スレッドごとに残す記録の数。1 から 16777216 まで（既定 262144。2 のべき乗に切り上げ）。記録するスレッドはそれぞれ自分のリングに新しいものを残す。1 件 48 バイト。範囲の外の値は stderr に出して既定を使う。リングを確保できなければプロセスごとに 1 回 stderr に出し、そのスレッドは記録しない |

- 各プロセスは終了時に `trace-<参加者名>-<pid>.json` を書きます（ランチャーは `SimulationController`）。何も記録しなかったプロセス（`--describe` だけを聞かれた ECU など）は書きません。実行ごとに空のディレクトリーを使ってください。`scripts/trace-report.py` は中の `trace-*.json` をすべて読みます。
- 強制終了したプロセスはファイルを書きません。2 回目の割り込みや、シミュレーションの開始前の割り込みで終わった ECU、外から強制終了したプロセスです。
- リングがあふれると、ファイルには新しい記録が残り、ほかは `dropped` として数えられます。要約はそのことを示し、すべてのプロセスに残っているステップだけを見ます。`VEHICLE_SIL_TRACE_EVENTS` を増やしてください。
- トレースは 1 プロセスで 1 回の実行に使います（`vehicle_sil_launch run`）。`vehicle_sil_launch test` はすべてのシナリオを 1 つのプロセスで実行するので、ファイルに実行が混ざり（仮想時刻がそれぞれ 0 から始まる）、各実行のスレッドのリングも最後まで残ります。トレースが有効なら `test` は stderr でそう伝え、`scripts/trace-report.py` はそのファイルを断ります。
- トレースを有効にしたまま、速さの基準を測らないでください。

## 要約の読み方

`scripts/trace-report.py` は部分ごとにまとめて、`--skip-ms`（既定 200）より後で最後の 5 つより前のステップについて、平均、p50、p90、p99 を µs で出します。すべての参加者のステップを含む詳細は `build/logs/trace-report.json`（`--json`）に書きます。

| 行 | 中身 |
|---|---|
| step period | 1 つのステップの開始から次のステップの開始まで（ランチャーが加わるときはランチャーの） |
| last to complete | 各ステップを最後に終えた参加者（クリティカルな参加者）。ステップが終わるのは、ハンドラーが戻ったとき。ランチャーがシナリオのために保持したステップは、ゲートが解放したとき |
| its step (with the hold) | クリティカルな参加者のステップの開始から終わりまで |
| sync (its completion to next start) | その終わりから、次のステップの最初の開始まで。SIL Kit の時刻同期のメッセージと、スレッドの起床 |
| slowest ECU step | ECU（ランチャーを除く）のうち、いちばん長いステップのハンドラー |
| launcher hold | 保持したステップ（書き込みがあるもの、ないもの）の内訳。ランチャーのステップ、シナリオのスレッドの起床、シナリオの書き込み（待たずにハブに渡す）、それらへのエージェントの答えを 1 回で待つ時間（settle）、tick の残り（標本、判定、エンジン）、解放までのゲートのスレッドの起床 |
| write round trip | 書き込みごとの内訳。宛先が複数あるときは最後に答えた ECU で見る。ハブの送信まで、送信（符号化と publish）、ECU のハンドラーまでの行き、ハンドラー、帰り、ハブのハンドラー、同じ tick のほかの書き込みの答えを待つ時間、最後の答えの後のシナリオのスレッドの起床。ECU のステップ中に届いたコマンドの割合も出す |
| clock offset from the launcher | 各 ECU の時計のずれの推定。往復ごとの 4 つの時刻から求める（[時計とほかの道具](#時計とほかの道具)） |

終了コードは、要約できたら 0、要約するものがなければ 1（ファイルがない、ファイルが途中で切れている、ステップが少なすぎる。どうすればよいかをメッセージが示す）、使い方の誤りは 2 です。

## タイムラインを見る

`--merged` は全プロセスを 1 つのファイルにまとめます。[Perfetto](https://ui.perfetto.dev)（ファイルはブラウザーの中で読まれる）か `chrome://tracing` で開きます。プロセスは参加者で、記録するスレッドの名前は `silkit`（SIL Kit のスレッド。ステップと、トランスポートのハンドラー）、`scenario` と `gate`（ランチャーのもの）です。矢印は、ハブが送った各コマンドからエージェントのハンドラーへ（`command`）と、エージェントの答えからハブのハンドラーへ（`answer`）です。1 つの書き込みでも宛先のエージェントごとに矢印があり、その id は書き込みの seq とエージェントのセッションから作ります。

## 記録

各記録は、steady clock の時刻、属するステップの仮想時刻（`vt`、ns。ないときは -1）、整数 1 つ（`arg`）を持ちます。

|---|---|---|---|---|
| `step` | span | `ParticipantRuntime`: SIL Kit のスレッドでのステップ全体。保持の判断まで | ステップ | 保持したとき 1 |
| `step.handler` | span | ステップのハンドラー（参加者自身の処理） | ステップ | |
| `step.release` | instant | 保持したステップの `release_step()` | ステップ | |
| `gate.release` | span | ゲートのスレッドが保持したステップを解放する | ステップ | |
| `scenario.woken` | instant | シナリオのスレッドが保持されたステップを見つける | ステップ | |
| `scenario.tick` | span | 保持されたステップでのシナリオの処理。次のガードまで | ステップ | |
| `scenario.drain` | span | シナリオに渡す標本 | | 標本の数 |
| `scenario.write` | span | シナリオの書き込み 1 回をハブに渡す（送る）まで。エージェントは待たない | 書き込みの時刻 | seq |
| `scenario.settle` | span | tick で渡した書き込みを、すべてのエージェントが受け付けるか断るまで 1 回待つ | | 書き込みの数 |
| `hub.write` | span | `Hub::write()`: 確認してから、コマンドを送る | 書き込みの時刻 | seq |

| `hub.receive_step` | span | ハブが受け取ったエージェントのステップのメッセージ（結果、イベント、標本） | エージェントのステップ | バイト数 |
| `hub.receive_answer` | span | エージェントの答えの受信（`answer` の矢印の終わり） | | seq |

| `agent.step_begin` | span | エージェントが時刻の来たコマンドを適用する | ステップ | コマンドの数 |
| `agent.apply` | instant | コマンド 1 つの適用 | ステップ | seq |
| `agent.late` | instant | 遅れとして断ったコマンド 1 つ | ステップ | seq |
| `agent.step_end` | span | エージェントが標本を取り、ステップのメッセージを送る | ステップ | 標本つきで 1 |
| `agent.publish` | span | ステップのメッセージの符号化と publish | ステップ | 標本つきで 1 |

## 時計とほかの道具

時刻は `std::chrono::steady_clock` です。Linux では `CLOCK_MONOTONIC`、Windows では `QueryPerformanceCounter` です。同じホストのプロセスはすべて同じ時計を読むので、1 つのホストのファイルはそのままそろいます。

- Linux の `perf record -k CLOCK_MONOTONIC` は同じ時計で記録します。たとえば `perf record -e dummy:u --switch-events -k CLOCK_MONOTONIC` で各スレッドが動いていた時間が分かるので、寝ていたスレッドと忙しかったスレッドを見分けられます。
- Windows の WPR と WPA も同じ時計で記録します。
- 複数のホストのファイルは、同じ時計ではありません。`scripts/trace-report.py` は時刻を動かさずにまとめて読み、書き込みの往復から、各 ECU のランチャーとのずれを NTP と同じやり方で推定します。推定は行きと帰りの差（スレッドの起床）だけずれるので、よくても数 µs の精度です。各ファイルには、書いたときの `steady_ns` と `system_ns` の対もあり、システムの時計を通した粗い合わせに使えます。
- 複数のホストのファイルでは、「last to complete」「sync」と往復の行きと帰りは、違う時計の時刻をそのまま比べるので、ずれの分だけ違います。スクリプトはプロセスをファイルで区別するので、ホストが違って同じプロセス ID でも混ざりません。

## 費用と制限

- 無効のとき、記録する各箇所は atomic のフラグを 1 回読んで分岐します。何も確保しません（`trace.a_trace_that_is_off_allocates_nothing`）。
- 有効のとき、span は時計を 2 回読み、スレッドのリングに 48 バイトを書きます。ロックはありません。スレッドのリングは最初の記録で確保し、そのメモリーには記録を書くにつれて触れます。
- ファイルはプロセスの終了時に `atexit` で書きます。実行のスレッドが閉じなかったためにランチャーが `std::_Exit` で終わるときは、その直前に書きます（このときは、もう読まれないかもしれない stderr に何も書きません）。書く時間は記録の数に比例します。
- ランチャーは、SIL Kit のスレッドがまだ記録しているかもしれない間に、自分のファイルを書きます。そのスレッドがちょうど書いた記録は、古い記録と混ざって出るか、書かれないことがあります。

## 変更するときの決まり

- 記録する箇所は、トレースが無効のときに確保、ロック、整形をしないこと。`trace::Span`、`trace::instant()` などには、手元にある値だけを渡します。
- 名前は文字列リテラル（ポインターだけを持つ）で、`<領域>.<何>` の形にします。
- `vehicle_sil::trace` は vehicle-sil のほかのライブラリーをリンクせず、SIL Kit のヘッダーを含みません（`trace.boundary` は include を確かめます）。どの層からも記録できるようにするためです。
- `atexit` を通らずに終わるプロセスは、先に `trace::flush()` を呼びます。
- 記録を足す、名前を変える、なくすときは、[記録](#記録) を直します。`scripts/trace-report.py` が読む記録なら、スクリプトと `tests/scripts/test_trace_report.py` も直します。
