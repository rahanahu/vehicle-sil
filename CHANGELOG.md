# Changelog

Changes of vehicle-sil by version, in the format of [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/): each version has a heading `## [<version>] - <release date>` and its changes under `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed` and `### Security`. Version numbers are `MAJOR.MINOR.PATCH`, with a pre-release part for a release candidate or a test release (`0.2.0-rc.1`; `rc.<n>`, `beta.<n>` or `alpha.<n>`). While the version is 0.x, a version that raises MINOR may break compatibility. A change that breaks compatibility says what users have to do.

The version comes from `project(vehicle_sil VERSION ...)` and `VEHICLE_SIL_VERSION_PRERELEASE` (`""` for a release) in the root `CMakeLists.txt` (`vehicle_sil_launch version` and `vehicle_sil` in the `--describe` output of an ECU print it). When the version is raised, write the same number in `pyproject.toml`, `gui/server/pyproject.toml`, `__version__` in `python/vehicle_sil_control/__init__.py` and in `gui/server/src/vehicle_sil_gui/__init__.py`, `VERSION` in `template/get_tools.py`, `GIT_TAG` in `template/CMakeLists.txt`, the version written in `template/README.md` and `template/README.ja.md`, and the heading in this file, `## [<version>] - Unreleased` until the release. The commit that is tagged `v<version>` replaces `Unreleased` with the release date (`YYYY-MM-DD`). `scripts/package.py version` finds mismatches; with `--expect v<version>`, which the release workflow runs for the tag, it also refuses a heading without the date. The release notes are this version's section.

## [0.2.0-rc.2] - Unreleased

The second release candidate includes the configuration timing migration, faster captured-process startup, targeted GUI stops, the Workbench example, and the GUI client APIs for waveform history and variable editing. The changes below describe 0.2.0 as a whole.

### Breaking changes

#### Mixing releases

- **Control messages version 2**: ECUs built with 0.1.0 still take part in a run under a 0.2.0 `vehicle_sil_launch` (and the other way round), but their variables cannot be read or written. `--describe` and `check --json` report `control.wire_version` 2 (was 1); `check` and `run` report `control-link-version` (and `control-link-dropped` in a run) and say which side to build again, and `check --scenario` refuses a scenario that uses such an ECU's variables (`scenario-variable`). Build the ECUs again with 0.2.0 (#117, #139, #140, #320).
- **GUI API version 3**: The GUI client checks `vehicle_sil_gui` when connecting. A version mismatch stops the connection with instructions to use a client and server from the same release. Version 3 requires server instance IDs in run and session replies so the client can identify which run to stop.
- **The GUI server requires the launcher of its own release**: it refuses, at start, a launcher whose `features` lack `time-commands`, `stdin-run-until`, `state`, `speed`, `start-paused`, `scenario` or `manual-participants`, and no longer answers 400 `unsupported` for time commands. Use the `vehicle_sil_launch` of the same vehicle-sil version (#283, #288).
- **The Python Control API client** (`vehicle_sil_control`) refuses, at its first call, a Control Server of another vehicle-sil release, including a 0.1.0 launcher, with `ControlError` `FAILED_PRECONDITION` and a message that names both releases. Stubs generated before the release field was added are refused with how to generate them again. The 0.1.0 client has no such check and still connects to a 0.2.0 server (#314).
- **The GUI server refuses a launcher of another release**: it compares `vehicle_sil` in the launcher's `version --json` with its own version in full, pre-release part included, and refuses at start (exit code 2) and when the launcher is replaced (`launcher-unusable`). Use the `vehicle_sil_launch` of the same release (#333).

#### Launcher, scenarios and their output

- **Simulation configuration format 2**: configurations in format 1 are refused. Set `vehicle_sil_simulation: 2`; move `stop_at_ms`, `speed`, and `late_tolerance_ms` to run arguments or a run request, and move `start_timeout_ms` and `stop_timeout_ms` to the host options `--participant-start-timeout-ms` and `--participant-stop-timeout-ms`. `time_step_ms` remains an optional configuration key. Omitting a stop time now leaves a run without an automatic stop; use `--stop-at-ms` or a scenario when a run should end automatically.
- **Automatic controller step and scenario limits**: without `time_step_ms`, the launcher resolves the step from the enabled ECU periods and the requested stop time at every speed. A scenario still undecided when its requested stop time is reached is `incomplete` instead of failing an unstarted step as `scenario-out-of-time`; `run` exits 5 and `test` counts it as a failed case. Samples and write application times at or after the boundary do not decide the scenario.
- **GUI server shutdown**: by default, the server waits for the launcher to exit after requesting a graceful stop. Set `--stop-timeout <seconds>` to limit that wait before the server sends a termination signal. A second stop signal also skips the wait.

- **Events format 2** (`vehicle_sil_events`): the `time` event (and `time` in the GUI server's summary) no longer has `paused` and `speed`; read the `state` event, which has them and `paused_at_ms`. `time` is written when virtual time moves, when the run stands still at another time, or when it is late (#223).
- **Run format 2** (`vehicle_sil_run`): a run stopped by a command (`{"command":"stop"}`, `Stop` of the Control API) is no longer "interrupted". It ends with exit code 0 (result `stopped`), or 5 (result `incomplete`) if a scenario was stopped before its end; 130 is left for signals and a lost supervisor (end of stdin, closed output), and a stopped run whose result could not be written exits with 3. The result has `end`, `ok` and `message`; the notes are `stopped`, `scenario-incomplete` and `ended-by-force`. A `stop` that comes only after the simulation has ended, when every required participant had already ended by itself, gives how the simulation ended (`completed` and `passed`, or `failed`) instead of `stopped`; `ended-by-force` names the participants that a stop or an interrupt cut short, also in interrupted runs (#231, #335).
- **One ending for every run that does not start**: every run that began its check ends with the same events, whatever kept it from starting or ended it: a `state` that takes no time command, a `command` refusal (`not-running`) for each time command still waiting, then `phase` `ended`, the last `state` and `result`; `phase` `stopping` only when the registry and the controller were set up. A run whose check failed no longer accepts time commands after its end, and a command that arrives while a run ends is answered before `phase` `ended` or after the last `state`, never between them (#336).
- **A run connected outside the simulation keeps real time**: with an enabled `role: bridge` participant (or `--connect`; `test` too), the run goes at speed 1 by default (`--time-policy realtime`). Another `--speed` or `--start-paused` is the error `outside-real-time` (the note `outside-speed-set` explains when an unspecified speed is set to 1), and pause, step, run_until and a speed other than 1 are refused with the reason `outside-real-time` from stdin, the Control API (`FAILED_PRECONDITION`, reason in the `vehicle-sil-reason` metadata) and the GUI. `--time-policy free` allows them (notes `outside-not-real-time`, `outside-time-changed`). `check --json` has `time_lock` (#192, #200).
- **Time commands while a scenario plays**: pause, resume, step, run_until and speed are accepted from the Control API too (they were refused with `scenario-running`); they do not change the scenario's result or its timeline. Writes from outside are still refused (feature `scenario-time`) (#256).
- **Scenarios judge with a sample of every ECU step**: `run --scenario` starts the ECUs whose values the scenario reads with `--sample-every-step`. Verdicts and step times can change for scenarios that relied on coarse samples (an `expect` at the time of a `set`, `wait_until`/`within_ms`, short ramps), and an ECU that still sends less often than its step fails the run before the first step with `scenario-not-observed`. Write `samples: as_sent` at the top of a scenario to judge with the values as sent; the scenario format version stays 1 (#300).

#### ECU and C++ libraries

- **Simulation timing in C++**: `config::SimulationConfig` no longer holds `stop_at_ms`, `speed`, `late_tolerance_ms`, `start_timeout_ms` or `stop_timeout_ms`; `config::time_step_ms()` and `config::late_tolerance_ms()` are removed. For the launcher, pass the stop time, speed and lateness tolerance in `RunRequest::intent`, and participant timeouts in `RunRequest::host`. Direct runner callers pass these choices in `RunChoices`. Read the resolved controller step from `CheckReport::run_timing` after a run check; a file-only check has no resolved timing. The optional explicit `SimulationConfig::time_step_ms` remains.
- **Reserved variable prefixes**: an ECU can no longer declare a variable whose name starts with `j1939.`, `can.`, `lin.` or `eth.` (as with `peer.` and `ecu.`); `input()`, `output()` and the like throw `std::invalid_argument` (exit code 3 with `ecu_main`, also under `--describe` and `--local`). Rename the variable and the scenarios and settings that use it (#114).
- **A second J1939 `Observer`** on a `Network`, or a second `TapListener` on a `TapPort` (and so a second `testkit::J1939Events` or `FrameLog` on the same network or tap), throws `std::logic_error` instead of silently replacing the first. Share the first one or remove it with `set_observer(nullptr)` / `set_listener(nullptr)` (#115).
- **Control library**: `control::Update` has a new alternative, `AvailabilityUpdate`, and `control::wire::encode_step()` takes a new `availability` argument (#247).
- **CAN bridge parts**: `CanBridge`, `ExternalPortAdapter` and the other parts that do not depend on Vector XL moved from namespace `vehicle_sil::vector_xl` and `vehicle_sil/vector_xl/*.hpp` to `vehicle_sil::can_bridge` and `vehicle_sil/can_bridge/*.hpp`. The target `vehicle_sil::vector_xl_bridge_core` is replaced by `vehicle_sil::can_bridge_core`, and `ExternalPortAdapter` is in its own target, `vehicle_sil::can_external` (link it to use the adapter) (#208, #260).
- **`run_file()` and lent controls**: `run_file()` refuses lent `RunControls` whose `set_control_server()` disagrees with the request (`RunHost::control` or `RunLent::control_endpoint`); a run's own controls now know about a control server the caller lends (#336).

#### Bridges

- **The Ethernet bridge uses promiscuous mode by default** where the interface accepts it, and goes on without it with one warning where the interface refuses it (`--promiscuous` then fails). `--no-promiscuous` turns it off (#157).
- **CAN bridge statistics keys** are named as in the Ethernet bridge: `silkit_to_xl` is `silkit_to_ext`, `xl_to_silkit` is `ext_to_silkit`, `xl_*` is `ext_*`, and `ext_from_devices` is added. Scripts that read the old keys must use the new ones (#217).
- **`--network` is required** by `vehicle_sil_vector_xl_bridge` and `vehicle_sil_socketcan_bridge`; the `J1939_CAN1` default is gone, and a missing `--network` is a usage error (exit code 4), as in the Ethernet bridge (#257).

#### GUI server and client library

- **GUI server HTTP API**: `api/check` and `api/run` answer 400 `invalid-field` for a field they do not take, and for `null` in any field (leave the key out instead of `speed: null` or `scenario: null`) (#184, #245). `api/run` checks the configuration with the run's own arguments first and answers 422 `check-failed` with the findings, starting nothing, when the check fails; a name in both `disable` and `manual`, and `start_paused` with a scenario, are such findings now instead of 400, and `name-like-option` is no longer returned (#187, #245). An `api/run` sent while another one is starting a run gets 409 `starting`, not `already-running` (#194).
- **Reserved paths under `--web`**: a `vsil/` or `timeline/` directory of your own is no longer served; the GUI server serves its own files there (#222).
- **gui-client time types**: `TimeState` drops `controllable`, `beforeStart`, `stepping`, `canPause`, `canResume`, `canStep` and `supported`, and `TimeView` and `TimeReport` drop `speed` and `paused`; use the front door's `controls` and `isHolding()` (#223, #291).
- **gui-client feature constants**: `FEATURE_SPEED`, `FEATURE_START_PAUSED`, `FEATURE_TIME_COMMANDS`, `FEATURE_SCENARIO`, `FEATURE_SCENARIO_CONTROL` and `FEATURE_MANUAL` are removed: the GUI server refuses a launcher without these features, so the client and the screens no longer check them (#291).
- **gui-client requests**: `RunRequest.speed` and the `scenario` of `RunRequest` and `CheckRequest` no longer accept `null` (leave them out), and `RunRequest.start_paused` is optional (#245).
- **gui-client variables**: `VariablesState`, `BoundVariable` and `VariableView` have `availability`, and the launcher's `control` object has `wire_revision`; code that builds these objects itself must add them (#275).
- **gui-client write blocks**: a write that the launcher does not take has `block: 'launcher'`, with the launcher's code and sentence in `BoundVariable.launcherReason` (`why.code` of `client.variable()` is the launcher's, such as `scenario-running`). The client's own value `scenario` is gone, `bind` writes nothing until the launcher has said that it takes writes, and `writeBlock()` takes a required `launcherRefuses` in its `WriteBlockInput` (#280).

#### Control API

- **The always-empty peer status is removed**: `PeerInfo.status` (field 5 and its name are reserved), `Peer.failed` and `Peer.error` in the Python client (the positional order of the later `Peer` fields moves up by two), and `FAILED` in the `peers` and `watch` output of the `vehicle_sil_control` CLI. A participant's failure still shows as a disconnect in `watch`, `SIL Kit: Error` in `peers`, and `failed_participant` with `watch(simulation=True)` (#316).

### Added

- **Run timing choices**: `check` and `run` accept `--stop-at-ms` and `--late-tolerance-ms`; `test` accepts a stop time for each case. The run request, GUI server API and GUI client accept `stop_at_ms` and `late_tolerance_ms`. The standard GUI offers an optional stop time and starts at real-time speed by default.
- **Workbench example**: an English-language GUI built with the public GUI client shows ECU inputs and outputs, supports recording and detached views, and provides a network editor. Build it with npm and start it with `scripts/run-gui.py --workbench`; see the [Workbench README](gui/web/workbench/README.md) for the commands. It is an example and is not part of the prebuilt tools archive.
- **Targeted GUI stop**: the GUI client binds stop and force-stop requests to the server and session the user selected. A changed server or session is refused instead of stopping a different run; existing untargeted API calls remain available.

#### Connecting to real buses

- **`vehicle_sil_launch run --connect <network>=<target>`** (and `check --connect`) connects a network to a real bus: the launcher finds the network's bridge next to itself or on PATH, starts it in its own directory before the ECUs, waits until it runs, and fails the run when the bridge does not start or ends (`connect-failed`, `connect-lost`). A target is `[<backend>:]<selector>` (`tap:`, `packet:`, `npcap:`, `xl:`, `socketcan:`; on Linux `--connect CAN=can0`, `--connect ETH=tap:vsil0`; `virtual:<n>` and `physical:<n>` mean Vector XL); a backend the OS does not have is `connect-backend`, and a bridge of another vehicle-sil release is `connect-tool-failed`. The default Ethernet frame filter is the MAC addresses of the ECUs on the network. `test` refuses `--connect` (#162, #163, #217, #226).
- **What a connected run reports**: the result lists the bridges and the connected networks (`participants[].for_network`, `outside`, `networks[].outside`) with the frames each bridge sent to the real bus and got from a device there (`to_outside`, `from_outside`, `counts`; note `connect-nothing-received`). The `outside` event and the `state` event's `outside[]` show each bridge's link, bus and `condition` (`ok`, `interrupted`, `degraded`) with `reasons`. The warnings `outside-link-down`, `outside-bus-off`, `outside-bus-errors`, `outside-frames-dropped` and `outside-loop-suspected` come from the bridges' link lines and statistics, and a link or bus down for 30 s stops the run (`connect-lost`) (#169, #207, #227).
- **Shared devices**: `check` warns with `connect-target-shared` when two networks are connected to the same device (all `virtual:*` channels count as one), and reports `connect-shared-loop` when ECUs also join the two networks. `run --connect` reports another vehicle-sil bridge on the same device that is not part of the run (`outside-device-shared`, with its process ID on Linux) from the bridge's first link line, before the ECUs start; with `--strict` the run does not start on a shared device and stops once a device has been shared for 3 s (#204, #213, #305).
- **`vehicle_sil_launch connections [--json] [--network <name>] <file>`** lists where each network can be connected on this computer, as `--connect` lines to copy (exit code 0 also when a bridge is simply not installed). With `--request <file>` it says whether each target of the request file's `connect` is usable, and exits with 1 if one is not. The `connect-target` and `connect-failed` findings point to it (#164, #243).
- **`external` on a network** in the configuration file (`bitrate` for CAN, `ethertypes` or `all_frames` for Ethernet) says how the network behaves when it is connected to a real bus; where it is connected is not written in the file (`connect` there is an error) (#161).
- **Bridges in the configuration file**: bridges answer `--describe` and take `--name` and `--start-timeout-ms`, so a bridge can be written in a configuration file with `role: bridge` and `required: false` and started by `vehicle_sil_launch`. `check` tells a bridge whose arguments were refused to fix its command (the launcher adds `--name`), and reports a participant that Windows could not start for a missing DLL as such instead of a crash; the launcher no longer lets Windows show a missing-DLL message box (#156, #159).
- **`vehicle_sil_socketcan_bridge`**: a Linux bridge between a SIL Kit CAN network and a SocketCAN interface (a CAN adapter or `vcan`), with `--list-channels`, which lists the kernel's kind of each interface. It is in the Linux tools archive, and `run --connect` starts it ([docs/socketcan-bridge.md](docs/socketcan-bridge.md)) (#219, #226, #237).
- **Bridge lists, links and statistics**: bridges list their targets as JSON (`vehicle_sil_ethernet_bridge --list-interfaces --json`, `vehicle_sil_vector_xl_bridge --list-channels --json`), and the Ethernet bridge uses the backend of its OS (`packet` on Linux, `npcap` on Windows) when `--backend` is left out. Bridges print a machine-readable `link` line (`link=up|down|unknown`, `bus=active|passive|bus-off|unknown`) before the SIL Kit lifecycle starts and whenever the value changes, and can write their statistics line while running (`--stats-every-ms`); the Ethernet line has `ext_from_devices`, and both bridges warn once when nothing has come from a device 10 s after they first sent there (#160, #168, #203).
- **Device marks**: bridges mark the device they open and report other vehicle-sil bridges on it, at the start and while running (the link line's `device`, `marked`, `shared` and `peers`, a warning, and `in_use`, `in_use_by` and `in_use_count` in the interface and channel lists) (#205, #237).
- **The prebuilt tools archive** includes the Ethernet bridge `vehicle_sil_ethernet_bridge` in `bin/`, next to `vehicle_sil_launch`, so `run --connect` finds it without PATH changes (Npcap and libpcap are not included; the Vector XL CAN Bridge is still built by the user) (#167).

#### Launcher, configuration and check

- **Run request files**: `run --request <file>` and `check --request <file>` read what to run from a JSON file (variant, params, scenario, disable, enable, manual, connect, time_policy, speed, start_paused, strict); arguments win field by field, and `--connect <network>=none` takes the file's target away. A `params` name that the file's own scenario lacks is a usage error (exit code 4); otherwise unused params are the note `request-params-unused`, and a network the configuration lacks is the note `connect-network-unused`. Findings about a connected run name `connect in <file>` when the file gave it. Schema `run-request.schema.json`, feature `request` (#241, #246, #264).
- **The `state` event** (`run --events`): phase, pause, hold, speed, pacing, stop requests, and which operations the run accepts now, with reason codes. `command` events carry `reason` and `id` (stdin commands take an `id` that comes back), and the `command` event of an accepted `step` has `at_ms`, where the run pauses after the step (#193, #202).
- **`run_until` on stdin**: `run --stdin-commands` takes `{"command":"run_until","at_ms":<ms>}`, the same as the Control API's `RunUntil`, without `--control` (feature `stdin-run-until`) (#196).
- **J1939 traffic per network**: `run` says per network who sent and who received J1939 frames (the `traffic:` line and table, `traffic` in `--json`), and lists participants it cannot place (`traffic.unplaced`, reason `no_control_link` or `no_counters`) instead of reporting `delivered: false` for their networks (#91, #135).
- **Network names**: `network_names` on a participant in the configuration file (also per variant) maps the network names an ECU's code uses to the simulation's names (findings `network-map-*`; example `examples/integrate_ecus/simulation.network-names.yaml`), and an ecu_main executable takes `--map-network <code name>=<simulation name>` (#80, #86).
- **J1939 node addresses and NAMEs from outside the code**: `j1939_nodes` on a participant in the configuration file, and `--j1939-node` of an ECU executable, give a J1939 node another address and NAME fields, so one ECU executable can be in a simulation twice without rebuilding it (`--describe` lists `j1939-node` in `features`). A refused override starts nothing. `address-conflict`, `address-shared` and `name-conflict` suggest a `j1939_nodes` entry, and the integration guide shows two instances of one ECU (`simulation.second-engine.yaml`) (#95, #112, #124, #137).
- **Checks without starting ECUs**: `check` reads the configuration's text from stdin (`--text-from-stdin`), saves the participants' `--describe` outputs (`--write-descriptions`) and checks against saved outputs with `--descriptions` (a participant without one is `not_described`). `check --compare-commands <file>` says in the `commands` key of `check --json` whether the commands that run are the same as in another configuration file (`"same"`, `"changed"`, `"not_compared"`, or `null` when not asked) (#298, #308).
- **`registry_uri` with port 0** lets the registry take a free port; `run --json` reports the registry's real URI in `registry_uri`, and a registry that cannot listen gets a hint that fits the cause (#135, #143).
- **Profiling trace**: `VEHICLE_SIL_TRACE=<dir>` writes a trace of virtual-time steps and scenario writes across the launcher and the ECU processes, which `scripts/trace-report.py` summarizes; it is off by default (#325).

#### Scenarios

- **Scenario timelines**: `run --scenario … --timeline <file>` records a scenario run (steps, checks, failures with every write of the failed request and whether the ECU applied it, the lines of each input, value series; schema `schema/timeline.schema.json`, feature `timeline-lines`). Every key is written in every file (`null` where it does not apply) (#82, #88, #135, #140, #143).
- **Dither**: `dither` overlays a small endless waveform on an input, declared in `inputs` or changed by a `dither` step, and stays on while a `ramp` or `wave` moves the base. `check --json` and `run --json` `lines[]` have `step`, `time_source` and `shape` (#90).
- **`points` from a CSV file**: a `wave` can read its `points` from a CSV file beside the scenario (`points: { file, value, time, time_unit }`; feature `scenario-points-file`) (#77).
- **Samples of every step**: the ECU argument `--sample-every-step` (describe feature `sample-every-step`), `Ecu::sample_every_step()`, the launcher feature `scenario-samples` and the check findings `scenario-samples-unsupported` and `scenario-samples-as-sent` (#300).
- **A rejected write of a multi-variable `set`**: the variables before it stay applied, and the Agent's reason starts with the rejected variable's name (#90).

#### ECU library, J1939 and the Spy

- **Listening to other ECUs**: `j1939::Listener` lets an ECU hear what other participants say to each other (`on_frame`, `on_message`, `on_transfer`, `on_transfer_end()`), with `ListenerSubscription` to remove a handler. `j1939::TransferSniffer` follows the transport-protocol transfers between other ECUs (RTS/CTS and BAM) and gives the same message the engine's receiver would (`SniffResult`; `SniffedTransfer::conflicting_packets` counts packets that disagreed) (#81, #85, #120).
- **`vehicle_sil::spy::Spy` and `Scope`** (`libs/spy`): a test participant that listens to the J1939 traffic of other ECUs and publishes what it saw and what it missed as ECU variables (`spy.missed`, `spy.timed_out` and their counters). `Spy::watch<M>()` (`vehicle_sil/spy/watch.hpp`) publishes a typed message's signals with its count, `last_ms`, `period_ms`, `size`, `invalid` and `stale`. The J1939 guide says what `spy.missed` at 0 promises, and shows a hand-written watcher that judges each request by its answer (#89, #127, #128, #129, #130).
- **J1939 monitoring variables**: `j1939.<network>.*` gains `transport_timeouts`, `transport_rejected`, `transport_bam_dropped` and `transport_bam_replaced` (#128).
- **J1939 transport timing**: the transport timeouts T1 to T4, the retransmission requests per window and the wait after an address claim can be set with `NetworkOptions::timing` (defaults unchanged, not checked against the standard); a `Listener`'s sniffer timeouts follow its Network's timing unless set (#119).
- **Variable availability**: ECU variables can report whether they are in use (`VariableOptions::availability`, `Ecu::set_availability()`), and the hub passes this on to subscriptions that ask (`SubscriptionOptions::availability`). `--describe` reports `control.wire_revision`, and `check` notes an ECU of an older revision (`control-link-revision`) (#247).
- **`vehicle_sil::NameInUseError`** (a `SilKit::ProtocolError`) is thrown when the registry keeps refusing a participant's name; the configuration functions are also declared in `vehicle_sil/core/participant_configuration.hpp` (#106).

#### Control API

- **Which writes took effect**: `TargetResult.applied_writes` and `failed_write` say how many writes of a command took effect and which one was refused; the Python client, the `vehicle_sil_control` CLI and the GUI's operation messages show them (#140, #143).
- **Availability**: `VariableInfo.availability` in ListPeers and Watch, and `PeerAvailability` updates for a Watch with `availability = true` (#255).
- **`WatchRequest.operation_clients_excluded`** leaves out the operations of the named clients (not sent, not counted in `Update.dropped`); the scenario's client name is `scenario` (#292).
- **Ping returns the server's release** (`vehicle_sil`) (#314).

#### Browser GUI and client library

- **The timeline page** (`gui/timeline/timeline.html`, English and Japanese) draws the file of `run --scenario --timeline`; on a failed run it opens on the failure (the step, the time, the reason, the values the conditions saw, and which writes the ECU applied). The GUI's Scenario card links each scenario run's timeline, and the tools archive ships the page (#100, #123).
- **`<vehicle-sil-timeline>`**: the timeline as a custom element that any screen can show with one script and one tag, with attributes, properties and events for the cursor, the chosen step, the view, the lanes, labels, texts, theme (`--vst-*` colour properties; `theme="auto"` follows the page's `color-scheme`) and compact mode. The GUI server, the tools archive and `@vehicle-sil/gui-client/timeline` ship it (#142, #147).
- **GUI parts** (`@vehicle-sil/gui-client/elements`): custom elements that build a screen in plain HTML on the page's shared connection: `<vsil-status>`, `<vsil-run-controls>`, `<vsil-time-controls>`, `<vsil-value>`, `<vsil-slider>`, `<vsil-write>`, `<vsil-scenario-select>`, `<vsil-scenario-result>`, `<vsil-connect>`, `<vsil-outside>` and `<vsil-timeline>`. `setReasonText(fn)` replaces the sentences of reasons, and `label-*` attributes rename the buttons. The GUI server serves the library and the parts at `/vsil/vehicle-sil-gui-client.mjs` and `/vsil/vehicle-sil-gui-elements.mjs` without a token, and the tools archive has them in `client/` (#209, #222, #229, #233, #234, #254).

## [0.2.0-rc.1] - 2026-11-20

A release candidate of 0.2.0: real buses connected from the launcher (`run --connect`, `connections`, the SocketCAN bridge), run request files, scenario timelines, ECU variable availability, the GUI parts and the client's front door, and the Network design screen.

### Breaking changes

#### Mixing releases

- **Control messages version 2**: ECUs built with 0.1.0 still take part in a run under a 0.2.0 `vehicle_sil_launch` (and the other way round), but their variables cannot be read or written. `--describe` and `check --json` report `control.wire_version` 2 (was 1); `check` and `run` report `control-link-version` (and `control-link-dropped` in a run) and say which side to build again, and `check --scenario` refuses a scenario that uses such an ECU's variables (`scenario-variable`). Build the ECUs again with 0.2.0 (#117, #139, #140, #320).
- **GUI API version 2**: `vehicle_sil_gui` is 2. A client made for 0.1.0 is refused with a message that says so, instead of misreading the summary (#302).
- **The GUI server requires the launcher of its own release**: it refuses, at start, a launcher whose `features` lack `time-commands`, `stdin-run-until`, `state`, `speed`, `start-paused`, `scenario` or `manual-participants`, and no longer answers 400 `unsupported` for time commands. Use the `vehicle_sil_launch` of the same vehicle-sil version (#283, #288).
- **The Python Control API client** (`vehicle_sil_control`) refuses, at its first call, a Control Server of another vehicle-sil release, including a 0.1.0 launcher, with `ControlError` `FAILED_PRECONDITION` and a message that names both releases. Stubs generated before the release field was added are refused with how to generate them again. The 0.1.0 client has no such check and still connects to a 0.2.0 server (#314).
- **The GUI server refuses a launcher of another release**: it compares `vehicle_sil` in the launcher's `version --json` with its own version in full, pre-release part included, and refuses at start (exit code 2) and when the launcher is replaced (`launcher-unusable`). Use the `vehicle_sil_launch` of the same release (#333).

#### Launcher, scenarios and their output

- **Events format 2** (`vehicle_sil_events`): the `time` event (and `time` in the GUI server's summary) no longer has `paused` and `speed`; read the `state` event, which has them and `paused_at_ms`. `time` is written when virtual time moves, when the run stands still at another time, or when it is late (#223).
- **Run format 2** (`vehicle_sil_run`): a run stopped by a command (`{"command":"stop"}`, `Stop` of the Control API) is no longer "interrupted". It ends with exit code 0 (result `stopped`), or 5 (result `incomplete`) if a scenario was stopped before its end; 130 is left for signals and a lost supervisor (end of stdin, closed output), and a stopped run whose result could not be written exits with 3. The result has `end`, `ok` and `message`; the notes are `stopped`, `scenario-incomplete` and `ended-by-force`. A `stop` that comes only after the simulation has ended, when every required participant had already ended by itself, gives how the simulation ended (`completed` and `passed`, or `failed`) instead of `stopped`; `ended-by-force` names the participants that a stop or an interrupt cut short, also in interrupted runs (#231, #335).
- **One ending for every run that does not start**: every run that began its check ends with the same events, whatever kept it from starting or ended it: a `state` that takes no time command, a `command` refusal (`not-running`) for each time command still waiting, then `phase` `ended`, the last `state` and `result`; `phase` `stopping` only when the registry and the controller were set up. A run whose check failed no longer accepts time commands after its end, and a command that arrives while a run ends is answered before `phase` `ended` or after the last `state`, never between them (#336).
- **A run connected outside the simulation keeps real time**: with an enabled `role: bridge` participant (or `--connect`; `test` too), the run goes at speed 1 by default (`--time-policy realtime`). Another `--speed` or `--start-paused` is the error `outside-real-time` (the note `outside-speed-set` says when the file's speed is replaced), and pause, step, run_until and a speed other than 1 are refused with the reason `outside-real-time` from stdin, the Control API (`FAILED_PRECONDITION`, reason in the `vehicle-sil-reason` metadata) and the GUI. `--time-policy free` allows them (notes `outside-not-real-time`, `outside-time-changed`). `check --json` has `time_lock` (#192, #200).
- **Time commands while a scenario plays**: pause, resume, step, run_until and speed are accepted from the Control API too (they were refused with `scenario-running`); they do not change the scenario's result or its timeline. Writes from outside are still refused (feature `scenario-time`) (#256).
- **Scenarios judge with a sample of every ECU step**: `run --scenario` starts the ECUs whose values the scenario reads with `--sample-every-step`. Verdicts and step times can change for scenarios that relied on coarse samples (an `expect` at the time of a `set`, `wait_until`/`within_ms`, short ramps), and an ECU that still sends less often than its step fails the run before the first step with `scenario-not-observed`. Write `samples: as_sent` at the top of a scenario to judge with the values as sent; the scenario format version stays 1 (#300).

#### ECU and C++ libraries

- **Reserved variable prefixes**: an ECU can no longer declare a variable whose name starts with `j1939.`, `can.`, `lin.` or `eth.` (as with `peer.` and `ecu.`); `input()`, `output()` and the like throw `std::invalid_argument` (exit code 3 with `ecu_main`, also under `--describe` and `--local`). Rename the variable and the scenarios and settings that use it (#114).
- **A second J1939 `Observer`** on a `Network`, or a second `TapListener` on a `TapPort` (and so a second `testkit::J1939Events` or `FrameLog` on the same network or tap), throws `std::logic_error` instead of silently replacing the first. Share the first one or remove it with `set_observer(nullptr)` / `set_listener(nullptr)` (#115).
- **Control library**: `control::Update` has a new alternative, `AvailabilityUpdate`, and `control::wire::encode_step()` takes a new `availability` argument (#247).
- **CAN bridge parts**: `CanBridge`, `ExternalPortAdapter` and the other parts that do not depend on Vector XL moved from namespace `vehicle_sil::vector_xl` and `vehicle_sil/vector_xl/*.hpp` to `vehicle_sil::can_bridge` and `vehicle_sil/can_bridge/*.hpp`. The target `vehicle_sil::vector_xl_bridge_core` is replaced by `vehicle_sil::can_bridge_core`, and `ExternalPortAdapter` is in its own target, `vehicle_sil::can_external` (link it to use the adapter) (#208, #260).
- **`run_file()` and lent controls**: `run_file()` refuses lent `RunControls` whose `set_control_server()` disagrees with the request (`RunHost::control` or `RunLent::control_endpoint`); a run's own controls now know about a control server the caller lends (#336).

#### Bridges

- **The Ethernet bridge uses promiscuous mode by default** where the interface accepts it, and goes on without it with one warning where the interface refuses it (`--promiscuous` then fails). `--no-promiscuous` turns it off (#157).
- **CAN bridge statistics keys** are named as in the Ethernet bridge: `silkit_to_xl` is `silkit_to_ext`, `xl_to_silkit` is `ext_to_silkit`, `xl_*` is `ext_*`, and `ext_from_devices` is added. Scripts that read the old keys must use the new ones (#217).
- **`--network` is required** by `vehicle_sil_vector_xl_bridge` and `vehicle_sil_socketcan_bridge`; the `J1939_CAN1` default is gone, and a missing `--network` is a usage error (exit code 4), as in the Ethernet bridge (#257).

#### GUI server and client library

- **GUI server HTTP API**: `api/check` and `api/run` answer 400 `invalid-field` for a field they do not take, and for `null` in any field (leave the key out instead of `speed: null` or `scenario: null`) (#184, #245). `api/run` checks the configuration with the run's own arguments first and answers 422 `check-failed` with the findings, starting nothing, when the check fails; a name in both `disable` and `manual`, and `start_paused` with a scenario, are such findings now instead of 400, and `name-like-option` is no longer returned (#187, #245). An `api/run` sent while another one is starting a run gets 409 `starting`, not `already-running` (#194).
- **Reserved paths under `--web`**: a `vsil/` or `timeline/` directory of your own is no longer served; the GUI server serves its own files there (#222).
- **gui-client time types**: `TimeState` drops `controllable`, `beforeStart`, `stepping`, `canPause`, `canResume`, `canStep` and `supported`, and `TimeView` and `TimeReport` drop `speed` and `paused`; use the front door's `controls` and `isHolding()` (#223, #291).
- **gui-client feature constants**: `FEATURE_SPEED`, `FEATURE_START_PAUSED`, `FEATURE_TIME_COMMANDS`, `FEATURE_SCENARIO`, `FEATURE_SCENARIO_CONTROL` and `FEATURE_MANUAL` are removed: the GUI server refuses a launcher without these features, so the client and the screens no longer check them (#291).
- **gui-client requests**: `RunRequest.speed` and the `scenario` of `RunRequest` and `CheckRequest` no longer accept `null` (leave them out), and `RunRequest.start_paused` is optional (#245).
- **gui-client variables**: `VariablesState`, `BoundVariable` and `VariableView` have `availability`, and the launcher's `control` object has `wire_revision`; code that builds these objects itself must add them (#275).
- **gui-client write blocks**: a write that the launcher does not take has `block: 'launcher'`, with the launcher's code and sentence in `BoundVariable.launcherReason` (`why.code` of `client.variable()` is the launcher's, such as `scenario-running`). The client's own value `scenario` is gone, `bind` writes nothing until the launcher has said that it takes writes, and `writeBlock()` takes a required `launcherRefuses` in its `WriteBlockInput` (#280).

#### Control API

- **The always-empty peer status is removed**: `PeerInfo.status` (field 5 and its name are reserved), `Peer.failed` and `Peer.error` in the Python client (the positional order of the later `Peer` fields moves up by two), and `FAILED` in the `peers` and `watch` output of the `vehicle_sil_control` CLI. A participant's failure still shows as a disconnect in `watch`, `SIL Kit: Error` in `peers`, and `failed_participant` with `watch(simulation=True)` (#316).

### Added

#### Connecting to real buses

- **`vehicle_sil_launch run --connect <network>=<target>`** (and `check --connect`) connects a network to a real bus: the launcher finds the network's bridge next to itself or on PATH, starts it in its own directory before the ECUs, waits until it runs, and fails the run when the bridge does not start or ends (`connect-failed`, `connect-lost`). A target is `[<backend>:]<selector>` (`tap:`, `packet:`, `npcap:`, `xl:`, `socketcan:`; on Linux `--connect CAN=can0`, `--connect ETH=tap:vsil0`; `virtual:<n>` and `physical:<n>` mean Vector XL); a backend the OS does not have is `connect-backend`, and a bridge of another vehicle-sil release is `connect-tool-failed`. The default Ethernet frame filter is the MAC addresses of the ECUs on the network. `test` refuses `--connect` (#162, #163, #217, #226).
- **What a connected run reports**: the result lists the bridges and the connected networks (`participants[].for_network`, `outside`, `networks[].outside`) with the frames each bridge sent to the real bus and got from a device there (`to_outside`, `from_outside`, `counts`; note `connect-nothing-received`). The `outside` event and the `state` event's `outside[]` show each bridge's link, bus and `condition` (`ok`, `interrupted`, `degraded`) with `reasons`. The warnings `outside-link-down`, `outside-bus-off`, `outside-bus-errors`, `outside-frames-dropped` and `outside-loop-suspected` come from the bridges' link lines and statistics, and a link or bus down for 30 s stops the run (`connect-lost`) (#169, #207, #227).
- **Shared devices**: `check` warns with `connect-target-shared` when two networks are connected to the same device (all `virtual:*` channels count as one), and reports `connect-shared-loop` when ECUs also join the two networks. `run --connect` reports another vehicle-sil bridge on the same device that is not part of the run (`outside-device-shared`, with its process ID on Linux) from the bridge's first link line, before the ECUs start; with `--strict` the run does not start on a shared device and stops once a device has been shared for 3 s (#204, #213, #305).
- **`vehicle_sil_launch connections [--json] [--network <name>] <file>`** lists where each network can be connected on this computer, as `--connect` lines to copy (exit code 0 also when a bridge is simply not installed). With `--request <file>` it says whether each target of the request file's `connect` is usable, and exits with 1 if one is not. The `connect-target` and `connect-failed` findings point to it (#164, #243).
- **`external` on a network** in the configuration file (`bitrate` for CAN, `ethertypes` or `all_frames` for Ethernet) says how the network behaves when it is connected to a real bus; where it is connected is not written in the file (`connect` there is an error) (#161).
- **Bridges in the configuration file**: bridges answer `--describe` and take `--name` and `--start-timeout-ms`, so a bridge can be written in a configuration file with `role: bridge` and `required: false` and started by `vehicle_sil_launch`. `check` tells a bridge whose arguments were refused to fix its command (the launcher adds `--name`), and reports a participant that Windows could not start for a missing DLL as such instead of a crash; the launcher no longer lets Windows show a missing-DLL message box (#156, #159).
- **`vehicle_sil_socketcan_bridge`**: a Linux bridge between a SIL Kit CAN network and a SocketCAN interface (a CAN adapter or `vcan`), with `--list-channels`, which lists the kernel's kind of each interface. It is in the Linux tools archive, and `run --connect` starts it ([docs/socketcan-bridge.md](docs/socketcan-bridge.md)) (#219, #226, #237).
- **Bridge lists, links and statistics**: bridges list their targets as JSON (`vehicle_sil_ethernet_bridge --list-interfaces --json`, `vehicle_sil_vector_xl_bridge --list-channels --json`), and the Ethernet bridge uses the backend of its OS (`packet` on Linux, `npcap` on Windows) when `--backend` is left out. Bridges print a machine-readable `link` line (`link=up|down|unknown`, `bus=active|passive|bus-off|unknown`) before the SIL Kit lifecycle starts and whenever the value changes, and can write their statistics line while running (`--stats-every-ms`); the Ethernet line has `ext_from_devices`, and both bridges warn once when nothing has come from a device 10 s after they first sent there (#160, #168, #203).
- **Device marks**: bridges mark the device they open and report other vehicle-sil bridges on it, at the start and while running (the link line's `device`, `marked`, `shared` and `peers`, a warning, and `in_use`, `in_use_by` and `in_use_count` in the interface and channel lists) (#205, #237).
- **The prebuilt tools archive** includes the Ethernet bridge `vehicle_sil_ethernet_bridge` in `bin/`, next to `vehicle_sil_launch`, so `run --connect` finds it without PATH changes (Npcap and libpcap are not included; the Vector XL CAN Bridge is still built by the user) (#167).

#### Launcher, configuration and check

- **Run request files**: `run --request <file>` and `check --request <file>` read what to run from a JSON file (variant, params, scenario, disable, enable, manual, connect, time_policy, speed, start_paused, strict); arguments win field by field, and `--connect <network>=none` takes the file's target away. A `params` name that the file's own scenario lacks is a usage error (exit code 4); otherwise unused params are the note `request-params-unused`, and a network the configuration lacks is the note `connect-network-unused`. Findings about a connected run name `connect in <file>` when the file gave it. Schema `run-request.schema.json`, feature `request` (#241, #246, #264).
- **The `state` event** (`run --events`): phase, pause, hold, speed, pacing, stop requests, and which operations the run accepts now, with reason codes. `command` events carry `reason` and `id` (stdin commands take an `id` that comes back), and the `command` event of an accepted `step` has `at_ms`, where the run pauses after the step (#193, #202).
- **`run_until` on stdin**: `run --stdin-commands` takes `{"command":"run_until","at_ms":<ms>}`, the same as the Control API's `RunUntil`, without `--control` (feature `stdin-run-until`) (#196).
- **J1939 traffic per network**: `run` says per network who sent and who received J1939 frames (the `traffic:` line and table, `traffic` in `--json`), and lists participants it cannot place (`traffic.unplaced`, reason `no_control_link` or `no_counters`) instead of reporting `delivered: false` for their networks (#91, #135).
- **Network names**: `network_names` on a participant in the configuration file (also per variant) maps the network names an ECU's code uses to the simulation's names (findings `network-map-*`; example `examples/integrate_ecus/simulation.network-names.yaml`), and an ecu_main executable takes `--map-network <code name>=<simulation name>` (#80, #86).
- **J1939 node addresses and NAMEs from outside the code**: `j1939_nodes` on a participant in the configuration file, and `--j1939-node` of an ECU executable, give a J1939 node another address and NAME fields, so one ECU executable can be in a simulation twice without rebuilding it (`--describe` lists `j1939-node` in `features`). A refused override starts nothing. `address-conflict`, `address-shared` and `name-conflict` suggest a `j1939_nodes` entry, and the integration guide shows two instances of one ECU (`simulation.second-engine.yaml`) (#95, #112, #124, #137).
- **Checks without starting ECUs**: `check` reads the configuration's text from stdin (`--text-from-stdin`), saves the participants' `--describe` outputs (`--write-descriptions`) and checks against saved outputs with `--descriptions` (a participant without one is `not_described`). `check --compare-commands <file>` says in the `commands` key of `check --json` whether the commands that run are the same as in another configuration file (`"same"`, `"changed"`, `"not_compared"`, or `null` when not asked) (#298, #308).
- **`registry_uri` with port 0** lets the registry take a free port; `run --json` reports the registry's real URI in `registry_uri`, and a registry that cannot listen gets a hint that fits the cause (#135, #143).
- **Profiling trace**: `VEHICLE_SIL_TRACE=<dir>` writes a trace of virtual-time steps and scenario writes across the launcher and the ECU processes, which `scripts/trace-report.py` summarizes; it is off by default (#325).

#### Scenarios

- **Scenario timelines**: `run --scenario … --timeline <file>` records a scenario run (steps, checks, failures with every write of the failed request and whether the ECU applied it, the lines of each input, value series; schema `schema/timeline.schema.json`, feature `timeline-lines`). Every key is written in every file (`null` where it does not apply) (#82, #88, #135, #140, #143).
- **Dither**: `dither` overlays a small endless waveform on an input, declared in `inputs` or changed by a `dither` step, and stays on while a `ramp` or `wave` moves the base. `check --json` and `run --json` `lines[]` have `step`, `time_source` and `shape` (#90).
- **`points` from a CSV file**: a `wave` can read its `points` from a CSV file beside the scenario (`points: { file, value, time, time_unit }`; feature `scenario-points-file`) (#77).
- **Samples of every step**: the ECU argument `--sample-every-step` (describe feature `sample-every-step`), `Ecu::sample_every_step()`, the launcher feature `scenario-samples` and the check findings `scenario-samples-unsupported` and `scenario-samples-as-sent` (#300).
- **A rejected write of a multi-variable `set`**: the variables before it stay applied, and the Agent's reason starts with the rejected variable's name (#90).

#### ECU library, J1939 and the Spy

- **Listening to other ECUs**: `j1939::Listener` lets an ECU hear what other participants say to each other (`on_frame`, `on_message`, `on_transfer`, `on_transfer_end()`), with `ListenerSubscription` to remove a handler. `j1939::TransferSniffer` follows the transport-protocol transfers between other ECUs (RTS/CTS and BAM) and gives the same message the engine's receiver would (`SniffResult`; `SniffedTransfer::conflicting_packets` counts packets that disagreed) (#81, #85, #120).
- **`vehicle_sil::spy::Spy` and `Scope`** (`libs/spy`): a test participant that listens to the J1939 traffic of other ECUs and publishes what it saw and what it missed as ECU variables (`spy.missed`, `spy.timed_out` and their counters). `Spy::watch<M>()` (`vehicle_sil/spy/watch.hpp`) publishes a typed message's signals with its count, `last_ms`, `period_ms`, `size`, `invalid` and `stale`. The J1939 guide says what `spy.missed` at 0 promises, and shows a hand-written watcher that judges each request by its answer (#89, #127, #128, #129, #130).
- **J1939 monitoring variables**: `j1939.<network>.*` gains `transport_timeouts`, `transport_rejected`, `transport_bam_dropped` and `transport_bam_replaced` (#128).
- **J1939 transport timing**: the transport timeouts T1 to T4, the retransmission requests per window and the wait after an address claim can be set with `NetworkOptions::timing` (defaults unchanged, not checked against the standard); a `Listener`'s sniffer timeouts follow its Network's timing unless set (#119).
- **Variable availability**: ECU variables can report whether they are in use (`VariableOptions::availability`, `Ecu::set_availability()`), and the hub passes this on to subscriptions that ask (`SubscriptionOptions::availability`). `--describe` reports `control.wire_revision`, and `check` notes an ECU of an older revision (`control-link-revision`) (#247).
- **`vehicle_sil::NameInUseError`** (a `SilKit::ProtocolError`) is thrown when the registry keeps refusing a participant's name; the configuration functions are also declared in `vehicle_sil/core/participant_configuration.hpp` (#106).

#### Control API

- **Which writes took effect**: `TargetResult.applied_writes` and `failed_write` say how many writes of a command took effect and which one was refused; the Python client, the `vehicle_sil_control` CLI and the GUI's operation messages show them (#140, #143).
- **Availability**: `VariableInfo.availability` in ListPeers and Watch, and `PeerAvailability` updates for a Watch with `availability = true` (#255).
- **`WatchRequest.operation_clients_excluded`** leaves out the operations of the named clients (not sent, not counted in `Update.dropped`); the scenario's client name is `scenario` (#292).
- **Ping returns the server's release** (`vehicle_sil`) (#314).

## [0.1.0] - 2026-11-15

The first version.

Breaking changes: none (the first version).

### Added

#### Overview

- A library for writing ECUs (`vehicle_sil::Ecu`, `ecu_main()`, the J1939 stack and its parts, typed messages, LIN, ECU variables), a launcher that runs ECU executables together on SIL Kit (`vehicle_sil_launch check`, `run`, scenarios, the Control API), and a browser GUI.
- Prebuilt tools (one archive per OS: `vehicle_sil_launch`, the GUI server and web UI, the Python client of the Control API, the GUI client library, the starter for your own web UI `gui_starter/`, the JSON Schema of the dashboard) and a template for an ECU project (`template/`; in a release, `vehicle-sil-template-0.1.0.zip`).

#### ECU library, J1939 and Ethernet

- **SIL Kit controllers** start at the point SIL Kit recommends (CommunicationReady). The bitrate and the start of a coordinated participant reach the CAN network simulator regardless of the start order. Code that uses `Peer`, `Ecu` or `Simulation` gets this without any change. Code that uses `SilKitCanPort` or `SilKitEthPort` directly calls `runtime.add_communication_ready_handler([&port] { port.start(); })`, and code that uses `CanBridge` or `EthernetBridge` directly calls `start_controller()` from the same place (without the call, the first step is an error that says what to call). After `ParticipantRuntime::stop()` returns, this handler is not called.
- **SIL Kit participant configuration** can be passed: `--silkit-config <file>` of an ecu_main executable, and `SilKitOptions::participant_configuration`. It is for adding the listen addresses for a run on several PCs, or logging settings. The defaults of vehicle-sil (listen addresses, TCP on Windows, fixed step) are also added to a passed configuration, only for keys it does not set. A configuration that sets another participant name, another registry or `DynamicSimulationStep: true` is an error before connecting, and the error names the key to remove (`vehicle_sil_can_bus_simulator --participant-configuration` behaves the same). A file with `Includes` finds the files next to it. A build without rapidyaml uses the passed configuration as it is ([docs/ecu-executable.md](docs/ecu-executable.md)).
- **Raw Ethernet frames in an ECU**: `Ecu::ethernet()`, `kind: ethernet` in the configuration, and the example `examples/ethernet`. The virtual network (`LocalBench`) and SIL Kit (`Peer`, virtual time only) give the same record, and no frame is dropped as long as the frames that arrive in one step do not exceed `receive_capacity`. `ecu.connected` also works for Ethernet. An ECU declares the MAC address it was given in `networks[].mac` of `--describe` (it also appears in `check --json`); a duplicate on the same network is the error `ethernet-duplicate-mac`, and an ECU that does not declare one gives the note `ethernet-mac-unknown` ([docs/internals/ethernet.md](docs/internals/ethernet.md)).
- **Base libraries for raw Ethernet frames**: `vehicle_sil::eth` (a channel that sends and receives inside a step, and an in-process virtual network; no SIL Kit) and `vehicle_sil::eth_silkit` (a port for SIL Kit Ethernet, virtual time). Frames that arrive at the same time are delivered in the order of the sender address, so the virtual network and SIL Kit give the same record ([docs/internals/ethernet.md](docs/internals/ethernet.md)).
- `parse_dtc_list()` in J1939 reads the DM1 / DM2 list (lamps and trouble codes) that another node sent. It returns a view that does not allocate. The most significant bit of the fourth byte of a trouble code is not interpreted and is passed on raw.
- `vehicle_sil::signal` offers the calculations of the scenario step `wave` to C++ code.
- **Participants created by vehicle-sil** do not follow the dynamic step size of SIL Kit (`Experimental.TimeSynchronization.DynamicSimulationStep`). When a participant that sets it to `true` joins (for example the network simulator of another tool), the step size of the ECUs does not change.
- **Frames received before the simulation starts**: when an ECU in virtual time receives a frame from a participant that does not take part in time synchronization (such as the Vector XL CAN Bridge) before the simulation starts, the time of the frame is 0. A J1939 BAM or RTS/CTS that arrives across the start does not time out immediately.
- **When an ECU ends**, it waits until the last notice, which carries cancelled writes among other things, has reached the launcher (the launcher answers, and the ECU waits 500 ms at most; normally it ends at once). A write that the ECU cancelled at the end of a run is settled as `Cancelled`, not `Unknown`. The end of the ECU is delayed by 500 ms only when the launcher has already ended.
- `SilKitEthPort` pads a frame shorter than 60 bytes with zeros before sending it. `refresh_peer_statuses()` and `wait_for_peer()` can be called from several threads at the same time.

#### Launcher, configuration and check

- `simulation.live.yaml` in `examples/ecu_main` and in the template is a configuration that runs at real-time speed until it is stopped.
- **JSON Schema for configuration files and scenarios** (`schema/`; also shipped in the template and in the tools). Completion and validation in editors work from the first line of the YAML files of the examples and the template.
- **Variable map**: with `variables` on a participant in the configuration file, scenarios and the Control API read and write variables under the same names and values even when the names, units and value representations differ between executables (renaming, linear expressions, value names, variables that an executable does not have). `participants[].variables` of `check --json` lists the variables after mapping, and `variable_map` shows both names. A variable in the Control API has `source`, its name in the executable ([docs/simulation-config.md](docs/simulation-config.md)).
- **Variants and scenario parameters**: `variants` in the configuration file describes the differences per variant (executables, variable map, whether a participant is present, parameters), and `--variant <name>` selects one for `check` and `run` (omitting it for a configuration with variants prints the list of names and ends with exit code 4). A scenario uses parameters as `${name}`; values are overridden in the order `params` of the scenario, the configuration, the variant, `--param name=value`. `only` in a scenario limits the variants it runs for. A scenario step that uses a variable the variant does not have (`absent: true`), or a variable of a participant the variant does not have, is skipped and reported instead of being an error (`skipped`; time still advances by `over_ms` and `hold_for_ms`, so the times of later steps do not depend on the variant). When every checking step is skipped, the warning is `scenario-nothing-checked` ([docs/simulation-config.md](docs/simulation-config.md), [docs/scenario.md](docs/scenario.md)).
- `role` (`ecu`, `test`, `bridge`) on a participant in the configuration. `check` does not count a test participant for `single-participant`, and warns when a test participant that has a J1939 node is on a network that a bridge carries (or may carry) to real hardware (`test-participant-talks-on-bridged-network`). A participant in `check --json` has `role`.
- **Listen addresses**: when `registry_uri` is a loopback address, the registry and the participants created by vehicle-sil listen only on the loopback address. With any other address, the setup is taken to span several PCs: they listen on all addresses, and `check` and `run` give the note `registry-on-network`. `run` passes `VEHICLE_SIL_LISTEN_ON_NETWORK` to the participants it starts ([docs/simulation-run.md](docs/simulation-run.md#listen-addresses)).
- **Format version of the ECU self-description** (`--describe`): it is raised only when the meaning of a key changes or a key is removed. When only values were added, ECUs and launchers of different versions can be mixed. A value the launcher does not know is the error `describe-unknown-value`, for that ECU only.
- `run --events`: a run that ends by `--timeout-ms` or by the failure of a participant while paused also emits a last `time` with `paused` false (the same as the other ways of ending).
- `run --events`: when a `step` or `run_until` that was accepted before the start finishes quickly, the first `time` (`sim_ms` 0) does not have `paused: true`.
- **Findings in text output**: each finding of `check`, `run` and `test` ends with its code (`… [single-participant]`). `unknown-network` names other networks of the same kind that may be the same bus, and says that the ECU's author must change the name, because the configuration cannot rename a network.
- **A run that stands still before the first step** (`--start-paused` with `--control`) may stand still for any time; its ECUs do not give up waiting for the start.

#### Scenarios

- `vehicle_sil_launch test <file> --scenarios <directory or file>` runs the scenarios one by one for each variant, summarizes them in a table and in JSON (`vehicle_sil_test`), and gives the verdict as the exit code (`--variant`, `--param`, `--fail-fast`, `--strict`). It fails when some combination was not run (except after an interruption), and with `--strict` when no combination was run. When the configuration has a `manual` participant, it refuses at the start. The command it prints for running a failed combination again carries over the arguments given to `test`.
- **Step `wave`** (`sine`, `triangle`, `sawtooth`, `square`, `pulse`, `noise`, `chirp`, `lag`, `chatter`, `points`). `check --scenario` warns about a waveform that is finer than the step of the ECU; `undersampled: ok` silences the warning. `features` of `version --json` has `scenario-wave`.
- `expect:` can be written beside a `ramp` or `wave` step (it must hold all the time from the time of the step to the simulation step in which the final value takes effect; `features` has `scenario-motion-expect`). For a variant without the variable, only the `expect` is skipped, and the output of `check`, `run` and `test` counts it (`unchecked_expects`).
- **A `ramp` without `from`** starts from the last value the scenario wrote to that variable, if the scenario has written to it; the start does not change when another writer, such as the ECU, changes the value. If the scenario has not written to it yet, the ramp starts from the value of the latest sample. `around` of `wave` follows the same rule.
- **Hexadecimal values** (`0x1F`) can be written for integer and enum variables in a scenario (`set`, `ramp`, `wave`, comparisons, parameters). Output stays decimal.

#### Control API

- **A run that plays a scenario** also accepts Control API clients (`run --scenario` with `--control`). A client can only read, wait and stop; calls that write and calls that move time are refused.
- `vehicle_sil_launch run --control unix:<path>` ends with exit code 4 when the path is too long, and gives the length and the limit.
- **The time answer of the Control API** does not have both `ended` and `paused` true at the moment the run ends.
- **A control port that is taken**: a second `vehicle_sil_launch run --control <port>` on a port another launcher listens on ends with exit code 3 instead of sharing the port.

#### Browser GUI

- `scripts/run-gui.py` starts the GUI from the repository with one command (for anything missing, it prints the command that builds it; a `--launcher` or a configuration file that does not exist is exit code 2).
- **Your own web UI** can be served by the browser GUI (`vehicle-sil-gui --web <dir>`). The client library is also distributed as a typed npm package, `vehicle-sil-gui-client-<version>.tgz`. `client.variables.bind` delivers the value of one variable, its freshness, whether it can be written and the state of a write as a single value, from any framework.

#### Bridges and the CAN network simulator

- `vehicle_sil_ethernet_bridge`, the Ethernet bridge executable, carries frames in both directions between a SIL Kit Ethernet network and an external interface. On Linux, `--backend tap` (a TAP device) and `--backend packet` (a network interface) are available and keep VLAN tags. `--backend pcap` on Linux (libpcap) and `--backend npcap` on Windows (Npcap) load the library at run time (vehicle-sil does not ship Npcap; when it is missing or old, the bridge says where to get it and ends with exit code 3 before touching SIL Kit). `npcap` looks for `wpcap.dll` and the DLLs it depends on only in the Npcap and system directories, and opens the adapter in a way that does not receive its own transmissions. `--list-interfaces` prints the interfaces that can be opened (also on Windows). `packet` counts frames with an unfinished checksum sent by the OS of the same PC in `ext_checksum_incomplete` and warns once how to fix it. Use `tap` when the other side is the network stack of the OS of the same PC ([docs/ethernet-bridge.md](docs/ethernet-bridge.md)).
- **Ethernet bridge libraries**: the port for an external interface, which does not use SIL Kit, with its filter (`vehicle_sil::eth_link`; EtherType, what follows the VLAN tag, the MACs on the SIL Kit side, maximum length), and `EthernetBridge`, which carries frames to and from SIL Kit Ethernet (`vehicle_sil::ethernet_bridge_core`). A second bridge between the same networks, and a MAC that is on both sides, are detected where the source MAC makes that possible; frames of that address are then dropped in both directions with a warning (the documentation lists the cases that cannot be detected). The libraries include the statistics line, the monitoring lines and the argument parsing ([docs/ethernet-bridge.md](docs/ethernet-bridge.md)).
- **Vector XL CAN Bridge**: reports bus anomalies, at most one line per second (`--no-bus-monitor` turns this off). It ends with exit code 1 when the device is unplugged. It counts the frames that went out on the bus by transmit receipts (`own_tx_dropped`), and on stopping prints the number it could not send in `xl_tx_unsent`. With `--tx-timeout-ms`, it drops new frames while the bus is congested (`xl_tx_dropped`). When bus-off persists, it activates the channel again (`--bus-off-restart-ms`, default 1000, 0 disables). The last two take effect only with `--bitrate` (init access).
- **Vector XL CAN Bridge, start-up**: the bridge fails only when the participant is stopping or has ended; it does not end with `FAIL: SIL Kit participant left Running (state ReadyToRun)` and exit code 1 right after start under high load. If the participant is still starting and has not reached Running after 15 seconds, the bridge says so and ends with exit code 1 ([docs/bridges.md](docs/bridges.md#participant-state-while-running)). In addition, `ParticipantRuntime::start()` returns only after the state is Running, also for a participant without time synchronization (so `state()` right after it returns is not ReadyToRun).
- **Vector XL CAN Bridge**: when the registry does not answer, it says where it looked and how to fix it. For a usage error, it prints only two lines instead of the whole usage text.
- **Messages of the Ethernet bridge**: an error in the arguments prints only two lines. The message for a registry that cannot be reached says what to check when the address is not a loopback address or is `0.0.0.0`. When the Npcap list has only the loopback interface, it gives the possible reasons.
- **Simple CAN Network Simulator** (`vehicle_sil_can_bus_simulator`): drops and counts transmissions of a controller that has not been started (no acknowledgement; one warning per network). `Reset()` cancels the waiting frames with `Canceled`. Reception does not depend on the mode of the receiver.
- **Arguments on Windows**: `vehicle_sil_can_bus_simulator` and the Vector XL CAN Bridge read their arguments as UTF-8 (a file with a non-ASCII name can be passed).
- **Non-ASCII names on Windows**: the Ethernet bridge handles its arguments and connection names as UTF-8. The bridges and `vehicle_sil_can_bus_simulator` print non-ASCII names in a readable form regardless of the console code page (UTF-8 to files and pipes).
- **Warnings before stopping**: the bridges (Vector XL, Ethernet) print the warnings raised just before stopping ahead of the statistics.

#### Build, packaging and tools

- `scripts/doctor.py` checks whether this PC has what building and testing vehicle-sil needs (read-only; for anything missing, it prints how to install it; `--json`). It also has a line "CMake for gRPC", which a build with the Control Server needs (optional).
- **Preset `linux-gcc-control`**: a GCC Debug build with the Control Server (gRPC from the PC if present, otherwise a fixed version through FetchContent).
- **CMake option `VEHICLE_SIL_STATIC`**: links SIL Kit and the C++ runtime library statically into the ECU executables, so that each can be distributed as a single file (default OFF).
- **Configuring** (`cmake --preset …`) prints in one line the SIL Kit commit that is built, the patches applied and the location of the copy.
- `template/get_tools.py` fetches the prebuilt tools of the template's version and checks them against `SHA256SUMS`. When the release has no archive for this PC, it says to pass a file you already have with `--archive <file>`, or to build vehicle-sil from its sources.

#### Documentation

- **The manual is in English**, with a Japanese edition (`README.ja.md`, `docs/ja/`). The guides go step by step, with a check after each step and a troubleshooting table: a first ECU, integrating ECUs, scenario tests, operating signals, your own GUI screen, and design choices. The examples they use are in the repository (`examples/first_ecu`, `examples/integrate_ecus`, `examples/scenario_tests`, `examples/launch_control`), and tests run them against the guides.
- **Comments in the code handed to users** are in English: the GUI client library (including its type declarations), the screen template `examples/gui_starter` and the client examples `examples/gui_client`.

### Fixed

#### Fixes to SIL Kit carried as patches

- **Patch 0004**: fixes a rare case in which a run with the simple CAN Network Simulator started with every controller still in SIL Kit's trivial mode (the bitrate and the controller mode did not reach the simulator, and there was no error or warning).
- **Patch 0005**: fixes a rare case in which a participant that joined right after another participant had ended waited 5 seconds and then failed with a handshake timeout to the registry (same name).
